
## MySQL의 구조

* MySQL 엔진과, 스토리지 엔진이 있다.
* MySQL 엔진이 Handler API를 사용해 스토리지 엔진을 사용하여 데이터를 읽고 씀

### MySQL 엔진

클라이언트의 연결을 담당하고 요청한 쿼리를 분석하여 처리하는 역할을 함. 핸들러를 통해 스토리지 엔진을 사용하여 데이터를 처리함  또한 쿼리 옵티마이저를 통해 쿼리를 최적화도 시켜줌

### 스토리지 엔진

처리한 쿼리에 필요한 데이터를 읽거나 쓰는 역할을 담당. 여러 종류의 스토리지 엔진을 사용하고 있으며 현재는  MyISAM보단 InnoDB를 사용하고 있음

## MySQL Thread 종류

MySQL은 여러개의 프로세스를 운영하는게 아닌 3종류의 Thread를 운영하고 있음

### 포그라운드 Thread

클라이언트의 연결과 쿼리를 처리를 담당함 보통 클라이언트 연결 개수만큼 Thread가 활성화 도미

### 백그라운드 Thread

클라이언트가 요청한 데이터 읽기 쓰기를 담당하며, InnoDB 같은경우 데드락 혹은 Log 데이터 읽기쓰기를 담당하고 있음 

InnoDB인 경우 데이터를 쓸 때 한번에 처리하기 위해 버퍼에 저장하기도 하며 쓰기 지연은 있지만 읽기 지연은 없도록 설계되었음
### Thread cache

클라이언트 요청이 완료되면 포그라운드 스레드가 2가지 상황에 따라 처리 방식이 결정된다.

* 시스템에서 설정한 cache 개수만큼 쓰레드가 존재할 경우 바로 Thread가 종료 되기도 한다.
* Thread cache 개수가 부족할 경우 포그라운드 thread는 thread cache로 이동한다.

## MySQL 메모리 종류

### 글로벌 메모리 영역

모두가 함께 쓰는 메모리 공간, 테이블을 캐싱할 때 사용 (TBD), 테이블의 데이터의 정합성을 만족시키기 위해 리두 로그같은걸 관리하고 있음(뇌피셜)
### 로컬 메모리 영역

Join Memory, Sort Memory 
* 클라이언트의 쿼리를 처리할 때 임시로 사용하는 메모리로서 `Order By`나 `Group By`를 사용 할 때 활용

* 각 포그라운드 쓰레드 별로 격리된 메모리 공간 (클라이언트트 서로의 메모리를 침범할 수 없음)

### 플러그인 엔진

플러그인을 이용해 MySQL의 데이터를 좀더 세밀하게 운영할 수 있음. 쿼리를 실행하기 전에 검증 로직을 추가하는 등 클라이언트 처리를 플러그인을 이용해 데이터를  변환하거나 검증하는등 기능을 꼈다 붙였다 할 수 있음

### 컴포넌트

플러그인을 대체하기 위해 사용되며 8.0에 새로 나왔다.

플러그인의 단점은 아래와 같다.
```
플러그인끼리 통신 불가능
sql 서버 변수를 직접 호출함
상호 의존성 관계를 설정할 수 없음
```

### 쿼리 실행 구조

쿼리 실행은 MySQL 엔진(쿼리 파서 -> 전처리기 -> 옵티마이저 -> 쿼리 실행기) -> 스토리지 엔진 순서로 전달됨

쿼리 파서 : 사용자 요청으로 들어온 쿼리 문장을 토큰으로 쪼개는 역할을 한다. 토큰으로 변환 도중 오류 발생시 사용자에게 오류 메시지를 전달함

전처리기 : 실제 쿼리 실행에 대한 접근 권한을 확인하거나, 쿼리에 구조적인 문제점이 있는지 확인한다.

옵티마이저: 쿼리 실행을 빠르게 처리할 수 있도록 최적화 과정을 거친다. **real MySQL에서 가장 많이 다룰  주제**

쿼리 실행기: 옵티마이저의 명령으로 적재적소의 핸들러를 이용해 쿼리를 실행하는 주체 아래와 같은 실행을 핸들러를 통해 진행함

* 임시 테이블 생성
* WHERE절에 일치하는 레코드 읽기

### 복제

#### 쿼리 캐시

디스크 읽는 횟수를 줄여 빠르게 응답할 수있게 SQL 실행 결과를 메모리에 저장하는 것 그러나 테이블 데이터가 변경되면 캐시를 초기화 하는 비용이 있기에 오히려 성능저하를 일으켰었어서 8.0 버전에는 존재하지 않음
#### 스레드 풀
엔터프라이즈에서만 제공하는 스레드 풀 기능은 커뮤니티 버전에서 제공하지 않는다. 커뮤니티 버전은 Percona Server의 스레드 풀 기능을 사용하면 된다.

스레드 풀의 목적은 쿼리를 처리하는 스레드의 개수를 최적화 하여 서버의 부담을 줄이는 것을 목적으로 둔다.

Persona Server 스레드 풀 플러그인은  선순위 큐와 후순위 큐를 이용해 특정 쿼리 및 트렌젝션을 최적화 하여 처리한다.

### 트렌젝션  지원 메타데이터

5.7 버전까지는 MySQL이 비정상적으로 종료되면 데이터가 깨지는 현상이 발생했다. 이를  MySQL 8.0 부터는 InnoDB의 테이블에 저장하도록 개선했다.

테이블 안에는 시스템 테이블 및 데이터 딕셔너리 정보가 담겨있다.

MySQL의 모든 데이터는 mysql.ibd이름의 테이블 스페이스에 저장된다. (제일 중요한 파일)

제일 중요한 메타데이터라, 직접 접근은 할 수 없지만 `information_schema` 테이블을 통해 간접적으로 데이터를 불러올 수 있다.

mysql.table이 해당 메타데이터이며 `mysql.inforschema`시스템 계정으로 이를 관리하고 있다. 

sdi(Serialized Dictionary Information)파일 형태를 이용해 innoDB의 메타데이터 마이그레이션을 할 수 있다. 또는 InnoDB의 데이터 테이블을 sdi로 변환 가능하다. 이때 사용하는 명령어는 `ibd2sdi` 이다. 메타데이터의 출력 형식은 `json`임


### InnoDB 스토리지 엔진 아키텍처

* 다른 엔진과 다르게 레코드 기반 잠금(데이터 행 잠금)을 제공하고 동시성 처리가 안정적이며 성능이 뛰어남 

#### InnoDB엔진의 특징

##### 기본키에 의한 클러스터링 가능

테이블은 기본키를 기준으로 클러스터링 되어 저장한다.

클러스터링 되어 저장한다는 의미는 테이블을 순서대로 저장한다는 뜻이고 이를 기반으로 쿼리의 데이터를 빨리 불러올 수 있는 것이다. (클러스터링 인덱싱은 8장에서 공부할 예정~)

##### 외래 키 지원

MyISAM같은 경우 외래키 제약조건을 걸지 못했지만 InnoDB는 외래키 제약 조건을 걸 수 있다.
외래키를 사용할때 부모 테이브로가 자식 테이블의 데이터를 체크할 때 잠금이 전파되므로 외래키의 존재에 주의해햐 한다.

외래키에 대한 검증 작업을 시스템 변수로 관리할 수도 있는데 `foregin_key_checks`변수를 OFF를 하면 제약조건이 걸려있어도 데이터를 자유롭게 변경할 수 있다고 한다. 다만, 큰 힘은 큰 책임이 있는법. 작업을 완료하면 제약 조건을 거는 것도 잊지 말아야 한다.

##### MVCC(Multi Version Concurrency Control)

격리 수준이 READ_COMMITED(커밋하지 않아도 갱신된 데이터 접근 가능)일때 데이터를 갱신하면 Undo Log에 이전 데이터를 저장하고  InnoDB 버퍼풀에 갱신한다. 이때 버퍼풀의 변경 내용은 InnoDB 백그라운드 스레드에서 관리한다. 중요한 사실은 **디스크에는 어떤 데이터가 갱신될지는 모르는 일이다**

이때 데이터를 조회할 때 트렌젝션의 격리 수준에 따라서 데이터의 결과값은 달라진다. READ_UNCOMMITTED인 경우 InnoDB의 버퍼풀에서 즉시 읽기 때문에 갱신된 데이터를 반환하고, REPEATABLE_READ나 SERIALIZABLE인 경우는 commit이 되지 않았기 때문에 Undo 로그의 데이터를 반환한다. 즉 InnoDB는 두 가지의 버전을 관리하고 있고 이를 MVCC라고 표현한다.

이는 트렌젝션이 많아 질 수 록 **두가지 뿐만 아니라 여러가지 버전을 관리할 수도 있다**.

이렇게 MVCC기능이 있기 때문에 COMMIT을 하더라도 롤백을 할 때 언두 로그에서 이전 데이터를  불러와 원상 복구 시킬 수 있다. 언두 영역에 있는 데이터가 삭제되는 시점은 트렌젝션이 더이상 언두 로그의 데이터를 필요로 하지 않을때 비로서 삭제된다.

##### 잠금 없는 일관된 읽기 Non-Locking Consistent Read

MVCC를 이용해 잠금을 걸지 않고 읽기 작업을 수행하기 때문에 다른 트렌젝션이 가지고 있는 읽기 잠금을 기다리지 않고 읽기가 가능하다. 이는 트렌젝션 격리 수준이 SERIALIZABLE이 아닌 이상 모두가 해당되는 성질이다.

오랫동안 트렌젝션이 유지하게 되면 언두로그가 쌓이게 되는데, 이는 성능저하로 이어질 수 있다. 따라서 트렌젝션의 범위를 좁히는 부분이 성능 최적화로 가는 길이다.
##### 자동 데드락 감지

데드락 감지를 위해 잠금 대기 목록을 그래프 형태로 관리한다. 어떤 트렌젝션을 종료할지 판단하는 기준은 **트랜젝션의 언두 로그 양이며 레코드가 더 적게 가진 트렌젝션이 롤백 대상이 된다**`innodb_table_locks`시스템 변수를 활성화면  데드락 감지 수준이 올라간다. (테이블  레벨의 잠금까지 감지)

`innodb_lock_wait_timeout`과 `innodb_deadlock_detect` 시스템 변수를 활용해 데드락 감지를 최적화 할 수 있다.  많은 동시성 처리가 있는 서비스가 존재할 경우 `innodb_deadlock_detect`를 비활성화 하여 데드락 감지 리소스를 쓰지 않는다면 성능을 좀 더 개선시킬 수 있다.
##### 자동화된 장애 복구

`innodb_force_recovery` 변수를 이용해 복구 레벨을 설정할 수 있다.

### InnoDB 버퍼 풀

디스크의 데이터 파일 및 인덱스 정보를 메모리에 캐시 해 두는 공간이다. INSERT, UPDATE, DELETE와 같이 무작위의 위치의 데이터를 디스크에 엑세스 하는 것이 아닌 한 메모리에 관리하여 쓰기 작업을 지연시키거나 일괄적으로 처리할 수 있도록 도와준다.

버퍼 공간은 전체 커넥션의 수 및 읽고 쓰는 데이터의 양에따라 유동적으로 변한다. 버퍼의 크기는 DB로 사용하는 시스템 메모리의 50%정도 사용하다 점차 늘리면 성능을 크게 증가시킬 수 있다. 이는 `innodb_buffer_pool_size` 변수로 관리할 수 있다.

버퍼풀은 동시성 제어로 세마포어를 활용하는데 잠금 시간을 줄이기 위해 여러개로 쪼개어 관리할 수 있음`innodb_buffer_pool_instance` 변수를 이용해 그 개수를 설정할 수 있음. 메모리 5GB당 인스턴스 1개를 설정하는 것이 적절하다고 함

##### 버퍼풀의 구조

**LRU(Least Recently Used) List**
* LRU(Old sublist) + MRU(Recently Used) 리스트가 결합된 형태
* 데이터 페이지를 자주 읽으면 페이지가 New sublist로 이동하고, 사용자가 자주 읽지 않으면 Old sublist쪽으로 이동한다.
* 디스크 I/O를  최소화 하기 위해 사용

**Flush List**
* 디스크에 동기화 되지 않은 데이터를 가진 페이지(Dirty Page)의 변경 시점 기준의 페이지 목록을 관리함.
* 주로 데이터 변경 시 해당 데이터를 Flush List에서 관리한다고 볼 수 있음
* 변경이 되면 InnoDB의 리두 로그에 이전 버전의 데이터가 기록됨
* 변경된 데이터가 속한 페이지도 변경 내용을 기록하게 되는데 리두 로그가 해당 페이지의 포인터를 저장함
* 리두로그의 데이터 페이지 포인터 더티 페이지의 내용이 동기화 되지 않을경우 스토리지 엔진이 체크포인트를 발생시켜 두 값의 상태를 동기화 시킴

**Free List**
실제 사용자 데이터로 채워지지 않은  비어있는 페이지들의 목록. 사용자 쿼리가 디스크 데이터 페이지를 읽어와야 하는 경우 사용
