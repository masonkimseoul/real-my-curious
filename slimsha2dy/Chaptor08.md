## 디스크 읽기 방식

데이터 저장 매체는 컴퓨터에서 가장 느린 병목 지점 → 데이터베이스 성능 튜닝은 어떻게 디스크 I/O를 줄이느냐가 관건일 때가 많음

### HDD와 SSD

하드 디스크 드라이브는 기계식 장치이므로 항상 데이터베이스 서버에서 병목이 된다
→ 이를 대체하기 위한 전자식 저장 매체 SSD가 많이 출시되는 중

- SSD는 기존 HDD에서 데이터 저장용 플래터를 제거하고 플래시 메모리를 장착하고 있음
→ 원판을 회전시킬 필요가 없어 I/O 속도가 아주 빠름
    - 또한 전원이 공급되지 않아도 데이터가 삭제되지 않음!
    - D-RAM보다는 느리지만 HDD보다는 훨씬 빠름
    - 요즘은 SSD가 대중화되어 DBMS용 서버에 대부분 채택
- 디스크 헤더를 움직이지 않고 한 번에 많은 데이터를 읽는 순차 I/O에선 큰 차이가 나지 않을 수 있음
    - 다만 랜덤 I/O는 차이가 많이 남ㅋ
    - 데이터베이스 서버에선 랜덤 I/O가 대부분임

### 랜덤 I/O와 순차 I/O

디스크 성능은 디스크 헤더의 위치 이동 없이 얼마나 많은 데이터를 한 번에 기록하느냐에 의해 결정

→ 그래서 랜덤 I/O 작업의 부하가 훨씬 큼

데이터베이스 대부분 작업은 작은 데이터를 빈번히 읽고 쓰므로 MySQL 서버에는 그룹 커밋, 바이너리 로그 버퍼, InnoDB 로그 버퍼 등의 기능이 내장됨

그렇다면 원판이 없는 SSD에선 랜덤 I/O와 순차 I/O의 차이가 없을까?

그렇지 않음. 랜덤 I/O의 throughput이 여전히 더 떨어짐

그럼에도 쿼리를 튜닝해서 랜덤 I/O → 순차 I/O로 실행할 방법은 적음

쿼리 튜닝은 랜덤 I/O 자체를 줄여주는 것(꼭 필요한 데이터만 읽도록)이 목적이라 할 수 있음

<aside>
💡

참고) 인덱스 레인지 스캔은 랜덤 I/O, 풀 테이블 스캔은 순차 I/O

</aside>

## 인덱스란

칼럼의 값을 주어진 순서로 미리 정렬 보관해서 찾기 쉽게 함

- 인덱스가 많은 테이블은 데이터 변경 처리(`INSERT`, `UPDATE`, `DELETE`)가 느려짐
- 대신 `SELECT` 는 빨라짐

- 데이터 관리 방식과 중복 값 허용 여부 등에 따라 여러 가지로 나눌 수 있음
    - **프라이머리 키**: 레코드를 대표하는 칼럼의 값으로 만들어진 인덱스
        - 레코드를 식별할 수 있는 식별자
        - NULL 값과 중복을 허용하지 않음
    - **세컨더리 인덱스**: 프라이머리 키를 제외한 모든 인덱스
- 데이터 저장 방식 별
    - **B-Tree 인덱스**
        - 칼럼의 값을 변형하지 않고 원래의 값을 이용해 인덱싱
        - 인덱스에서 가장 일반적으로 사용됨
    - **Hash 인덱스**
        - 칼럼의 값으로 해시값을 계산해서 인덱싱
        - 매우 빠른 검색을 지원
        - 값의 일부를 검색하거나 범위를 검색할 수 없음
        - 메모리 기반 데이터베이스에서 많이 사용
- 데이터 중복 허용 여부
    - **유니크 인덱스**
    - **Non-Unique 인덱스**
    - 단순히 값이 1개만 존재하는지만 의미하지만 옵티마이저에게 중요한 문제가 됨
        - 동등 조건으로 검색하면 항상 한 레코드만 찾으면 된다는 것을 알고 있으므로
    - 처리 방식의 변화나 차이점이 상당히 많음
- 기능별 분류
    - 전문 검색용 인덱스, 공간 검색용 인덱스 등

## B-Tree 인덱스

여러 가지 변형된 형태의 알고리즘이 있는데, 일반적으로 DBMS에선 B+-Tree, B*-tree가 사용됨

<aside>
💡

B는 binary가 아니라 balanced이다!

</aside>

### 구조 및 특성

인덱스의 **리프 노드**는 항상 실제 데이터 레코드를 찾아가기 위한 **주솟값**을 가지고 있음

(221p 그림 참고)

인덱스의 키 값은 정렬되어 있지만 데이터 파일의 레코드는 정렬돼 있지 않음
→ 만약 레코드가 삭제되어 빈 공간이 생기면 그 다음의 `INSERT` 는 삭제된 공간을 재활용하도록 설계되기 때문에

<aside>
💡

주의) InnoDB 테이블에선 레코드가 **클러스터**되어 저장되므로 **프라이머리 키 순서로 정렬**되어 저장됨

</aside>

- 리프 노드에 저장된 값 차이
    - **MyISAM**: 레코드 주소 = 생성 옵션에 따라 테이블에 삽입된 순서나 데이터 파일 내 위치(offset)
    - **InnoDB**: 프라이머리 키
    - 즉 MyISAM은 물리 주소를, InnoDB는 논리 주소(프라이머리 키)를 가진다고 볼 수 있음
    - 그래서 InnoDB에서 인덱스를 통해 레코드를 읽을 때는 바로 데이터 파일을 찾아가지 못하고 프라이머리 키 인덱스를 통해 다시 리프 노드를 찾아가야 함

### 인덱스 키 추가 및 삭제

- **인덱스 키 추가**
    - 새로운 키 값이 저장될 때 스토리지 엔진에 따라 키 값이 즉시 인덱스에 저장될 수도 아닐 수도 있음
    - B-Tree에 저장될 때 키 값을 이용해 적절한 B-Tree 상 위치를 검색하고 키 값과 대상 레코드의 주소 정보를 리프 노드에 저장함
    → 근데 리프 노드가 꽉 차서 저장할 수 없으면 리프 노드가 분리되어야 하는데 이는 **상위 노드까지 처리** 범위가 넓어짐
    → 따라서 **쓰기 작업**에 **비용이 많이** 드는 것으로 알려짐
    - MyISAM, MEMORY에선 즉시 새로운 키 값을 B-Tree 인덱스에 변경함
    - InnoDB는 인덱스 키 추가 작업을 지연 처리(4.2.10 체인지 버퍼 참조)
        - 프라이머리 키나 유니크 인덱스의 경우는 중복 체크가 필요하므로 즉시 B-Tree에 반영
- **인덱스 키 삭제**
    - 해당 키 값이 저장된 리프 노드를 찾아서 **삭제 마크**
    - 이 인덱스 키 공간은 그대로 방치하거나 재활용 가능
    - 물론 이것도 디스크 I/O가 필요함
    - 지연 처리는 추가와 마찬가지
- **인덱스 키 변경**
    - 먼저 키 값을 삭제한 후 다시 추가하는 형태로 처리
    - 위와 마찬가지의 지연 처리
- **인덱스 키 검색**
    - 트리 탐색을 통해 `INSERT`, `UPDATE`, `DELETE` 를 처리
    - B-Tree를 이용한 검색은 전부 일치 혹은 값의 앞부분 일치하는 경우에 사용 가능(+ 범위)
    - 뒷부분만 검색하는 용도로는 당연히 사용 불가
    - 키 값이 변형된 후 비교되는 경우에는 당연히 사용할 수 없음 → 함수나 연산 결과로 정렬하거나 검색하는 작업에서 사용할 수 없다~
    - InnoDB에서는 인덱스를 사용하지 않을 시 레코드 잠금이나 넥스트 키락이 너무 많은 레코드를 잠그므로 인덱스 설계가 중요함ㅋㅋ

### B-Tree 인덱스 사용에 영향을 미치는 요소

인덱스를 구성하는 칼럼의 크기, 레코드 건수, 유니크한 인덱스 키 값의 개수 등이 성능에 영향을 줌

- **인덱스 키 값의 크기**
    - InnoDB에서 디스크에 데이터를 저장하는 가장 기본 단위는 **페이지** or **블록**
    ← 디스크 읽기/쓰기 작업의 **최소 작업 단위**
    - B-Tree는 자식 노드의 개수가 가변적인데 여기선 몇개까지 가능?(자최몇)
    ← 이는 **페이지 크기**와 **키 값의 크기**에 의해 결정됨
        - 페이지 크기는 시스템 변수로 설정할 수 있지만 기본값은 16KB
            - 만약 인덱스 키가 16바이트, 자식 노드 주소 영역이 12 바이트라면
            - 하나의 인덱스 페이지에 585개를 저장할 수 있음
            → 자식 노드를 585개 가질 수 있는 B-Tree가 된다
        - 인덱스 키 값이 커진다면 이 자식 노드 개수는 줄어들 것
        - 이로 인해 한 번 읽을 때 필요한 인덱스 페이지 개수가 달라지기도 함
    - 또한 인덱스 키 값의 길이가 길어진다는 것은 **전체적인 인덱스의 크기가 커진다**는 것을 의미
        - 인덱스 캐시 영역인 버퍼풀/키캐시영역은 크기가 제한적이므로 캐시할 수 있는 레코드 수가 줄어들 것! → 메모리 효율도 ㅜㅜ
- **B-Tree 깊이**
    - 중요하지만 제어할 수는 없음
    - 깊이가 3인 경우 페이지 당 키 개수가 585개면 최대 2억(585^3) 개의 키 값을 담을 수 있지만 372개라면 5천만 개로 줄어듬
    - 인덱스 키 값의 크기가 커지면 인덱스 페이지가 담을 수 있는 키 개수가 적어지고, 같은 레코드 개수를 저장하기 위해 더 깊어지게 된다
    → **디스크 읽기가 더 많이 필요해진다**
    - 실제로는 깊이가 5 이상으로 깊어지는 경우는 흔치 않음
- **선택도(기수성)**
    - 모든 인덱스 키 값 가운데 **유니크한 값의 수**
    - 중복된 값이 많아질수록 기수성(Cardinality)는 낮아짐
    - 인덱스는 선택도가 높을수록 **검색 대상이 줄어들게 되므로 빠르게 처리**됨
    
    <aside>
    💡
    
    참고) 선택도가 안 좋아도 정렬, 그루핑 등의 작업을 위해 인덱스가 유리한 경우도 있음
    
    </aside>
    
    - 기수성이 높을수록 어떤 조건으로 검색되는 레코드 개수가 많아짐 → 실제로 사용하지 않는 데이터의 수도 많아질 것 → 비효율적
- **읽어야 하는 레코드의 건수**
    - **인덱스를 통해 읽는 작업**은 바로 테이블의 레코드를 읽는 것보다 **비용이 많이 듬**
    - 일반적인 옵티마이저에선 인덱스를 통해 읽는 것이 테이블에서 직접 읽는 것보다 4~5배 정도 비용이 더 드는 것으로 예측
    → 인덱스를 통해 읽어야 할 레코드의 건수가 전체의 20~25%를 넘어서면 인덱스를 이용하지 않는 것이 효율적

### 인덱스를 통한 데이터 읽기

- **인덱스 레인지 스캔**
    - 대표적 접근 방법
    - 여기선 일단 한 건만 읽는 것과 한 건 이상 읽는 것을 묶어서 설명
    - **검색해야 할 인덱스의 범위가 결정됐을 때** 사용하는 방법
    1. **인덱스 탐색**: 트리 검색을 통해 시작 지점을 찾고
    2. **인덱스 스캔**: 탐색된 위치부터 필요한 만큼 차례대로 쭉 읽음
    3. 매번 **데이터 파일에서 레코드를 읽어오는 과정**이 필요함
        - 레코드 한 건 단위로 랜덤 I/O가 한 번씩 일어남ㅋㅋ
    - 쿼리가 필요로 하는 데이터에 따라 3번은 필요하지 않을 수도
    → 커버링 인덱스
        - 디스크의 레코드를 읽지 않아도 되므로 성능이 빨라짐
- **인덱스 풀 스캔**
    - 인덱스 **처음부터 끝까지** 읽기
    - 쿼리의 조건절에 사용된 칼럼이 인덱스의 첫 칼럼이 아닌 경우
    - 인덱스의 크기는 테이블의 크기보다 작으므로 테이블 풀 스캔보다는 효율적
    - 쿼리가 **인덱스에 명시된 칼럼만으로 조건을 처리할 수 있는 경우** 주로 사용
        - 데이터 레코드도 읽어야 하면 절대 안씀
- **루스 인덱스 스캔**
    - 오라클의 인덱스 스킵 스캔 기능과 비슷
    - 앞의 두 방식은 이 방식과 구분되어 타이트 인덱스 스캔으로 분류
    - 레인지 스캔과 비슷하지만 **필요하지 않은 키 값은 무시하고 넘어가는** 형태
    - 그룹바이 집합 함수 가운데 MAX(), MIN() 함수에 대해 최적화를 하는 경우 사용
    - 여러 가지 조건을 만족해야 함
- **인덱스 스킵 스캔**
    - 루스 인덱스 스캔과 비슷하지만 WHERE 조건절의 검색을 위해 사용 가능하도록 용도가 훨씬 넓어진 것
    - (a, b)로 인덱스가 걸려있는데 b로 검색하는 경우
        - 필요 없는 부분은 스킵하면서 b로 레인지 스캔을 한다
        - 내부적으로 a로 조건을 검색한 경우의 여러 쿼리를 실행한 것과 비슷한 형태로 최적화
    - 조건이 있음
        - 선행 칼럼(a)의 유니크한 값 개수가 적어야 함
        - 쿼리가 인덱스의 칼럼만으로 처리 가능해야 함(커버링 인덱스)

### B-Tree 인덱스의 정렬 및 스캔 방향

인덱스 생성 시 설정한 정렬 규칙에 따라 오름차순/내림차순으로 정렬되어 저장됨

8.0부터 칼럼 단위로 정렬 순서를 혼합해서 인덱스를 생성할 수도 있음

```sql
CREATE INDEX teamname_userscore ON employees (team_name ASC, user_score DESC);
```

하지만 오름차순이라고 오름차순으로만 읽을 수 있단 뜻은 아님
← 거꾸로 읽으면 되니까

쿼리가 그 인덱스를 사용하는 시점에 인덱스를 읽는 방향에 따라 원하는 정렬 방향 효과를 얻을 수 있겠지?

어느 방향으로 읽을지는 옵티마이저가 만드는 실행 계획에 따라 결정

그럼 내림차순 정렬은 필요 없나?

- 복합 정렬이 필요할 경우
    - ASC, DESC가 필요한 경우 ASC, ASC로는 안됨
- 실제로는 역순 스캔이 좀 더 느림
    - 페이지 잠금이 인덱스 정순 스캔에 적합한 구조라서
    - 페이지 내에서 인덱스 레코드가 단방향 연결이라(페이지 간은 양방향)

### B-Tree 인덱스의 가용성과 효용성

어떤 조건에서 인덱스를 사용할 수 있고 없는지

인덱스를 100% 활용할 수 있는지 아닌지 알아보자

- 다중 칼럼 인덱스에서 칼럼 순서와 사용된 조건(=, <, >)에 따라 인덱스 칼럼의 활용 형태와 효율이 달라짐
    - 필터링: 인덱스를 통해 읽은 레코드가 나머지 조건에 맞는지 비교하면서 선택하는 작업
    - 필터링 과정을 줄일 수 있는 순서가 효율적
    - 비교 작업의 범위를 줄이지 못하고 거름종이 역할만 하는 필터링 조건/체크 조건은 많다고 해서 쿼리 성능을 높이지 못함
- B-Tree 인덱스는 왼쪽 값 기준해서 오른쪽 값이 정렬됨
    - 오른쪽 값을 기준으로 인덱스를 찾으려 하면 쓸 수 없다
    - 복합 인덱스여도 왼쪽 값만 사용하는 경우에는 재활용할 수 있다

- 사용할 수 없는 조건(251p 참고)
    - NOT-EQUAL
    - LIKE ‘%??’
    - 스토어드 함수나 다른 연산자로 인덱스 칼럼이 변형된 후 비교
    - NOT-DETERMINISTIC 속성의 스토어드 함수가 비교 조건에 사용된 경우
    - 데이터 타입이 서로 다른 비교
    - 문자열 데이터 타입의 콜레이션이 다른 경우

참고로 NULL에 대해서도 사용 가능하다

- 다중 칼럼 인덱스
    - 첫 칼럼이 조건에 없는 경우 사용 불가
    - 1~i-1까지 동등 비교, i에 대해 {동등 비교, 대소비교, LIKE 좌측 일치 패턴} 중 하나로 비교 시 사용 가능
