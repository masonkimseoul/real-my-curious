
### 인덱스란 무엇인가?
DBMS의 데이터를 빠르게 찾기위해 만든 "자료구조".
인덱스는 정렬된 상태로 유지해야 하기 때문에 인덱스 데이터를 저장하는 과정이 복잡하고 느리지만, 이미 정렬되어 있기 때문에 데이터를 빠르게 찾을 수 있게 도와준다.

즉, 인데스를 설정한 테이블은 수정(`INSERT`, `UPDATE`, `DELETE`)하는 속도는 느려지지만, 읽기 속도(`SELECT`)는 증가시켜주는 기능이다.

인덱스는 테이블 내 컬럼에 설정할 수 있는데, 해당 테이블 내에 대표하는 컬럼에 설정하는 인덱스를 **프라이머리 키**라고 불리고 나머지 인덱스를 **보조 키**라고 부른다.

인덱스를 설정하는 법은 아래와 같이 설정할 수 있다.
```
ALTER TABLE [테이블명]
ADD INDEX [인덱스명] (컬럼1, 컬럼2);
```

인덱스의 적용 여부는 아래와 같이 확인할 수 있다.
```
EXPLAIN [SELECT 쿼리문];
```

결과 중 `type` 컬럼에 `ALL`,`index`라고 되어 있으면 인덱스가 적용되어 있지 않다는 뜻이고, `range`는 적용되었다는 것이다. 자세한 건 **인덱스를 검색할 때**를 참고하자

제일 앞에 있는 인덱스(`컬럼1`)가 프라이머리 키이고, 뒤는 보조 키 이다.

### 인덱스의 종류
인덱스를 저장하는 방식(알고리즘)에 따라 분류가 가능하다. 
데이터 중복 허용하는 인덱스와 그렇지 않은 인덱스로도 분류도 가능하다.
마지막으로 기능 별로 분류가 가능한데 전문(full-text) 검색용, 공간 검색용으로 분리될 수 있다.

### B-Tree 인덱스
B-Tree의 B의 뜻은 Balanced이며 트리가 균형을 유지하면서 저장한다. 인덱스를 저장할 때 값을 변환하지 않고 있는 그대로 저장한다. 저장한 데이터를 이용해 인덱싱을 하는것이 특징이다. 주로 B+ Tree 알고리즘을 사용한다.

#### 인덱스의 구조
B-Tree는 최상단의 루트 노드, 중간 단계인 브렌치 노드를 거쳐, 마지막으로 실제 데이터의 위치를 갖고있는 리프 노드로 구성된다. 

#### B-tree인덱스의 특징
B-Tree 답게 값이 항상 정렬되어 있다.
B-Tree에 인덱스를 저장하기 위해서는 저장될 키 위치를 검색한 후 최종적으로 리프 노드에 저장된다.

#### 인덱스의 크기
노드 단위는 페이지 혹은 블록 단위이며 `innodb_page_size`에서 페이지의 크기를 확인할 수 있다. 기본 값은 16KB이고, 이 값은 변경이 가능하다.

B-Tree 인덱스는 자기 주소와 자식노드의 주소를 갖고 있는데 대략 자신의 주소가 16 byte 자식 노드 주소가 12byte이다. 따라서, 한 페이지에 저장할 수 있는 인덱스 개수는 **16 x 1024/(16+12) = 585**개 정도 저장할 수 있다.

#### 인덱스를 삽입할 때

브렌치 노드에서 더이상 리프 노드로 들어갈 수 없을 때 리프노드가 분리되는데, 이 때 상위에 있는 브랜치 노드까지 영향을 받아 쓰기 작업 속도가 느려진다.

#### 인덱스를 삭제할 때

트리를 유지하면서 리프 노드의 값이 삭제되었음을 표시해주면 된다. InnoDB에서는 버퍼링 되어 지연 처리가 되어 상대적으로 MyISAM보다 빠르다.

#### 인덱스를 검색할 때

검색 조건이 100% 일치하는 값 혹은 앞 부분(Left-most part)만 일치하는 경우 인덱스의 효과를 볼 수 있다.

아래와 같은 조건문 일 경우 인덱스를 적용할 수 없다.
```
1. NOT-EQUAL로 비교할 경우 인덱스로 사용할 수 없음
2. LIKE '%문장'
3. SUBSTRING() = 'X'
4. determinisic_function()
5. 서로 다른 데이터 타입 비교
```

아래와 같은 조건문 일 경우 인덱스를 적용할 수 있다.
```
1. 동등비교 ('=', IN)
2. 크다 작다 형태 (>,<)
3. LIKE '문장%' 
```

인덱스를 적용하기 위해서는 조건 문에 프라이머리 키가 있는 쿼리를 사용해야 한다. 조건문에 인덱스를 설정하지 않은 컬럼으로만 검색하게 되면 인덱스가 적용되지 않는다.

##### 검색 방식

**인덱스 레인지 스캔**

리프노드까지 도달한 후 순차적으로 조건에 맞는 레코드를 검색한다.  자세한 과정은 다음과 같다.
```
1. 조건을 만족하는 값의 위치를 찾는다.(Index seek)
2. 1.에서 탐색된 위치부터 필요한 인덱스만큼 순차적으로 스캔한다.(Index scan)
3. 찾은 인덱스를 바탕으로 실제 레코드 페이지를 가져오고 값을 읽는다. (이 과정을 커버링 인덱스를 통해 생략할 수도 있다.)
```

레인지 스캔을 얼만큼 했는지 확인할 수 있는 변수는 다음과 같다.

```
Handler_read_key = 1 단계 실행 횟수
Handler_read_next, Handler_read_prev = 2단계 실행 횟수
Handler_read_first, Handler_read_last = 3단계 첫 번째 레코드와 마지막 레코드를 읽은 횟수
```

**인덱스 풀 스캔**
레인지 스캔과 다르게 처음부터 끝까지 스캔한다. 조건문의 칼럼이 두 세번째 인덱스일 경우 사용한다.
쿼리가 인덱스로만 조건을 처리할 수 있을 경우 이 방식이 사용된다.

자세한 과정은 아래와 같다.

```
1.리프 노드의 처음이나 끝에 시작해서 순차적으로 스캔한다.
```

**루스(loose) 인덱스 스캔**

레인지 스캔과 비슷학게 동작하나, 중간에 필요하지 않은 인덱스가 있을 경우 탐색을 건너뛴다. **Group By, Min, MAX**를 최적화 할 때 사용한다.

**인덱스 스킵 스캔**
MySQL 8.0부터 생긴 기능이다. 옵티마이저가 쿼리를 보고 인덱스를 살펴보는데, 프라이머리키 인덱스가 아닌 보조키 인덱스 조건으로만 실행되는 걸 알게 될 때 인데스 검색이 가능하도록 변경해준다.

실행 원리는 아래와 같다.
```
1. 옵티마이저가 프라이머리 키를 이용해 루스 인덱스를 실행하여 프라이머리 인덱스를 전부 검색한다.
2. 프라이머리 인덱스 조건절을 추가한 쿼리를 생성하고 레인지 인덱스 스캔을 한다.
```

이 스캔에 효과를 보기 위해선 아래와 같은 조건이 필요하다.

```
프라이머리 키 유니크 값이 적어야 한다.
쿼리 조건문이 인덱스로만 처리가 가능해야 한다.
```

#### 인덱스를 변경할 때
기존 인덱스를 삭제한 후 새 인덱스를 삽입한다. InnoDB에서는 체인지 버퍼로 지연 처리 될 수 있다.

#### 선택도(Selectivity)와 기수도(Cardinality)
중복되지 않은 값을 의미하며, 중복된 값이 인덱스에 저장하게 되면 선택도가 떨어지며 선택도가 떨어지면 검색 효율이 떨어진다.

10개 고유(A) vs 1000개 고유(B) 

10000개의 레코드가 저장되어 있는 경우 

A 상황 : 1000개가 일치하다고 나올 것이고 이는 999건을 더 찾아봐야 함
B 상황 : 10개가 일치하다고 나올 것이고 9건을 더 찾아봐야 함

#### 인덱스의 효율
검색을 할 때 최종 결과가 전체의 20~ 25%를 넘어서면 인덱스를 이용하지 않는게 효율적임

### 다중 컬럼 Index

인덱스의 키가 2개 이상 연결되어 있는 인덱스를 이야기함. 복합 컬럼 인덱스라고도 불림.
각 페이지는 인덱스 키들을 저장하는데, 프라이머리 키를 기준으로 보조키가 정렬되어 저장한다.

### Index의 순서

인덱스는 순서가 중요한 만큼 각 인덱스 별로 오름 혹은 내림차순을 설정할 수도 있다.
```
CREATE INDEX [인덱스 명] ON [테이블 명] (컬럼1 ASC, 컬럼2 DESC ...);
```

### Index의 탐색 방향

인덱스를 설정하면, 이미 정렬되이 있기 때문에 정렬 비용을 없앨 수 있다. 다만, 조건문이 인덱스가 걸려 있어야 하는 점이 중요하다.

### 전문(full-text) 검색 인덱스
내용 검색을 인덱싱하기 위해 필요한 방식 `전문 검색 알고리즘`이라는 특수한 알고리즘을 사용한다. 

#### 전문 검색 알고리즘의 종류

어근 분석 알고리즘
* 가치가 없는 단어를 필터링하여 제거하는 불용어를 처리한 뒤 검색어의 원형을 찾는 작업을 한다.
* 찾을 때 필요한 데이터는 국가 별 사전 데이터와, 문장 구조 인식 데이터가 필요하다.

n-gram 알고리즘
* 전문을 무조건 몇 글자씩 잘라서 인덱싱을 하는 방식이다. 국가별 언어의 이해를 필요로 하지 않아도 되지만 인덱스의 크기가 큰 편이다.
* 인덱싱을 할 최소 글자가 필요한데 보통 2글자로 인덱스를 생성하는 편이다. (이를 Bi-gram, 2-gram 라고도 한다)
* 불용어를 필터링하여 최종 인덱스를 만드로 이를 B-Tree 인덱스에 저장한다고 한다.

불용어를 n-garm알고리즘에서도 처리하는데 mysql에서 사용하는 데이터는 i`nformation_schema.INNODB_FT_DEFAULT_STOPWORD`에 있다. 그러나 해당 데이터는 불용어가 아닌데, 불용어로 인식될 수 있어 유저가 정의한 불용어를 사용할 수 있다.

```
ft_stopword_file = [파일 경로]
```

#### 전문 검색 인덱스 적용
전문 검색 알고리즘을 적용하기 위해서는 아래의 쿼리를 작성한다.
```
ALTER TABLE [테이블명] ADD FULL INDEX 테이블명(컬럼1,컬럼2) WITH PARSER ngarm;
```

전문 검색 인덱스를 적용하기 위해서 아래의 조건을 만족해야 한다.
```
1. 쿼리 문장이 전문 검색을 위한 문법인지 확인
> WHERE MATCH(인덱스 적용 컬럼) AGINST ('단어' IN BOOLEAN MODE);
```

### 멀티 밸류 인덱스
하나의 레코드에 여러개의 인덱스를 가지는 것을 이야기한다. 사용하기 위해선 아래와 같이 설정할 수 있다.
```
INDEX 인덱스명 (배열 타입의 값)
```

사용할 때는 아래의 조건문을 사용해야 한다.
```
1. MEMBER OF ()
2. JSON_CONTAINS()
3. JSON_OVERLAPS()
```

### 클러스터링 인덱스
프라이머리 키가 비슷한 것들끼리 저장되는 방식을 말한다.
클러스터링 인덱스로 저장된 테이블은 프라이머리 키 기반으로 검색할 때 성능이 매우 빠르다고 한다.

리프노드에 랜덤한 레코드 포인터가 저장되어 있는 형태가 아닌 리프노드에 정렬된 레코드 자체가 저장되어 있다.

InnoDB에서는 레코드를 저장할 때 인덱싱을 걸지 않아도 자기가 알아서 클러스터링 인덱스 형태로 저장하는 건가? 프라이머리 키가 길 수록, 보조 키가 많을 수록 저장 용량이 지수함수마냥 증가한다.

**주의사항**
* 프라이머리 키는 반드시 명시 할 것 - 안쓰는 일련번호가 내부적으로 생성되기 때문

### 유니크 인덱스

유일성이 보장되는 컬럼에 대해서 유니크 인덱스를 생성하는 것이 좋다. 기본 인덱스와 중복으로 설정이 가능하나 꼭 그럴 필요하는 없다.

### 외래키 인덱스

InnoDB에서는 외래키 설정이 가능하며, 외래키를 맺은 테이블은 자동으로 외래키 인덱스가 적용된다.

이 외래키 인덱스를 통해 잠금을 관리하는 것으로 보인다.

자식 테이블이 부모 테이블에 외래키 제약 조건이 걸릴 경우, 자식의 외래키로 사용하는 부모 컬럼이 변경될 때 자식 레코드는 부모 외래키 변경이 끝날 때 까지 잠금이 걸린다. 
반대로 자식 테이블의 외래 키 값이 변경될 때 부모 테이블이 수정 중에 있으면 부모 테이블의 수정이 완료 될 때 까지 기다려야 한다.
