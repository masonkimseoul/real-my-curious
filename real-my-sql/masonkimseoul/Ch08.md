# 8장 - 인덱스

# 8.1 디스크 읽기 방식

## 8.1.1 하드 디스크 드라이브(HDD)와 솔리드 스테이트 드라이브(SSD)

- SSD는 DRAM보다 느리고 HDD보다 빠르다.
- 순차 I/O에서는 SSD와 HDD가 근소한 차이를 보일 때도 있지만, 랜덤 I/O에서는 SSD가 매우 빠르다.
- DB 서버에는 랜덤 I/O가 대부분이니, SSD가 최적이다.

## 8.1.2 랜덤 I/O와 순차 I/O

- 순차 I/O는 N개 페이지의 디스크 기록을 위해 시스템 콜을 1회 요청하지만, 랜덤I/O는 N회 요청한다. 각 시스템 콜마다 디스크 헤더가 1회씩 움직인다고 생각하면 된다.
- 이 때문에 MySQL 서버에는 그룹 커밋, 바이너리 로그 버퍼, InnoDB 로그 버퍼 등 기능이 내장되어 있다.
- SSD도 랜덤 I/O가 순차 I/O보다 오래 걸리긴 한다.
- 물론 랜덤 I/O과 순차 I/O 모두 파일 쓰기 시 동기화 작업이 필요하기 때문에, 순차 I/O도 랜덤 I/O만큼 비효율적일 수도 있다. RAID 컨트롤러의 캐시 메모리가 이를 상쇄시켜줄 수도 있다.
- 쿼리 튜닝으로 랜덤 I/O를 순차 I/O로 바꿔줄 방법은 적다.(꼭 필요한 데이터만 읽도록 쿼리를 개선하는걸 의미)
- 인덱스 레인지 스캔은 주로 랜덤 I/O, 풀 테이블 스캔은 순차 I/O를 사용한다. 그래서 큰 테이블의 레코드 대부분을 읽는 작업은 인덱스보다 풀 테이블 스캔을 사용하는게 이득일 수도 있다. 순차 I/O가 랜덤 I/O보다 더 빨리 많은 레코드를 읽어올 수 있기 때문.

# 8.2 인덱스란?

- 쉽게 말하면, 인덱스는 색인이다.
- 칼럼의 값과 해당 레코드가 저장된 주소를 Key-Value로 저장한다. 또한 최대한 빠르게 탐색할 수 있도록 미리 정렬해서 보관한다.
- 데이터의 저장(INSERT, UPDATE, DELETE) 성능을 희생하고 데이터의 조회(SELECT) 속도를 높임
- 테이블 인덱스를 하나 더 추가할지 말지는 데이터의 저장 속도를 어디까지 희생할 수 있는지, 읽기 속도를 얼마나 더 빠르게 만들어야 하느냐에 따라 결정해야 한다. 전부 인덱스로 생성하면 데이터 저장 성능이 떨어지고 인덱스 크기가 비대해져 역효과가 발생한다.
- 데이터를 관리하는 방식(알고리즘)과 중복 값 허용 여부 등에 따라 여러 가지로 분류할 수 있다.
1. 역할에 따른 분류
    1. 프라이머리 키(인덱스)
        - 프라이머리 키로 만들어진 인덱스
        - 해당 레코드를 식별하는 기준값이기에 식별자로고도 부르고, NULL 값과 중복을 허용하지 않는다.
    2. 세컨더리 키(인덱스)
        - 프라이머리 키를 제외한 나머지 모든 인덱스
        - 유니크 인덱스는 프라이머리 키와 성격이 비슷하며 프라이머리 키를 대체할 수도 있어서 대체 키라고도 하는데, 별도로 분류할 수도 있고 세컨더리 키로 분류할 수도 있다.
2. 데이터 저장 방식(알고리즘)에 따른 분류
    1. B-Tree 인덱스
        - 가장 일반적으로 사용
        - 칼럼의 값을 변형하지 않고 원래 값으로 인덱싱
        - 변형으로 R-Tree도 있음
    2. Hash 인덱스
        - 칼럼의 값으로 해시값을 계산하여 인덱싱
        - 매우 빠르지만 값을 변형하여 인덱싱하므로 전방(Prefix) 일치와 같이 값 일부만 검색하거나 범위를 검색할 땐 못쓴다.
        - 주로 메모리 기반 DB에 많이 쓴다.
    3. Fractal-Tree
    4. Merge-Tree
    5. 등등....
3. 데이터 중복 허용 여부에 따른 분류
단순히 같은 값이 1개만 존재한다는 조건은 옵티마이저에게 1개 값만 찾으면 더이상 탐색하지 않아도 된다고 알려주는 역할을 한다.
    1. Unique 인덱스
    2. Non-Unique 인덱스

# 8.3 B-Tree 인덱스

- Balanced-Tree Index
- B+-Tree, B*-Tree
- 칼럼의 원래 값을 변형시키지 않고(값의 앞부분만 잘라서 관리하긴 함) 항상 인덱스 구조체 내에서 정렬된 상태를 유지한다.

## 8.3.1 구조 및 특성

- 트리 구조이며, 최상위 루트 노드, 최하위 리프 노드, 나머지 브랜치 노드가 존재
- 인덱스와 실 데이터가 저장된 데이터는 따로 관리되는데, 리프 노드는 항상 실 데이터 레코드를 찾아가기 위한 주솟값을 갖고 있다.
- 인덱스의 키 값은 모두 정렬되어 있지만 실 데이터는 정렬되어 있지 않다.
    - InnoDB 테이블에서 레코드는 클러스터되어 디스크에 저장되므로 기본적으로 프라이머리 키 순서로 저장된다. 디폴트 값이 클러스터링 테이블이다.(비슷한 값을 최대한 모아서 저장하는 방식)
- 인덱스는 테이블 키 칼럼만 가지고 있으므로 나머지 칼럼을 읽으려면 데이터 파일에서 해당 레코드를 찾아야 함.
- MyISAM 테이블은 세컨더리 인덱스가 물리적인 주소를 가지는 반면 InnoDB 테이블은 프라이머리 키를 주소처럼 사용하기 때문에 논리적인 주소를 가진다고 볼 수 있음
- 그래서 InnoDB 테이블에서는 인덱스에 저장되어 있는 프라이머리 키 값으로 프라이머리 키 인덱스를 한 번 더 검색한 후, 프라이머리 키 인덱스의 리프 페이지에 저장되어 있는 레코드를 읽는다.
- 즉, 세컨더리 인덱스 검색에서 데이터 레코드를 읽으려면 반드시 프라이머리 키를 저장하는 B-Tree를 다시 한 번 검색해야 한다.

## 8.3.2 B-Tree 인덱스 키 추가 및 삭제

### 8.3.2.1 인덱스 키 추가

- B-Tree에 새 키 값을 저장할 때 저장될 키 값으로 B-Tree 상의 적절한 위치를 검색한다. 저장될 위치가 결정되면 레코드의 키 값과 대상 레코드의 주소 정보를 B-Tree 리프 노드에 저장한다. 리프노드가 꽉 차서 저장할 수 없으면 리프 노드는 분리되어야 하며, 이 과정에서 상위 브랜치 노드까지 처리 범위가 넓어진다. 그래서 상대적으로 쓰기 작업에 더 비용이 든다.
- 인덱스의 추가로 INSERT나 UPDATE 문장이 받는 영향은 테이블의 칼럼 수, 칼럼 크기, 인덱스 칼럼의 특성 등을 확인해야 정확히 알 수 있다.
- 대략적으로 확인하는 방법은, 일반적으로 테이블에 레코드를 추가하는 비용을 1이라 할 때, 인덱스에 키를 추가하는 건 1.5 정도이다.
- 만약 인덱스가 3개(모두 B-Tree라 가정)라면 (1.5 * 3 + 1)로 5.5 정도로 볼 수 있다.
- 이러한 비용의 대부분은 CPU와 메모리가 처리하는 시간이 아니라 디스크에서 인덱스 페이지를 읽고 써야 해서 걸리는 시간이다.
- MyISAM이나 MEMORY 스토리지 엔진을 사용하는 테이블은 INSERT 문장 실행 시 즉시 새 키 값을 B-Tree 인덱스에 반영하지만, InnoDB는 필요 시 인덱스 키 추가 작업을 지연하여 실행한다. 프라이머리 키나 유니크 인덱스는 중복 체크가 필요하므로 즉시 B-Tree에 추가하거나 삭제한다.

### 8.3.2.2 인덱스 키 삭제

- 해당 키 값이 저장된 B-Tree 리프 노드를 찾아서 삭제 마크만 하면 된다.
- 삭제 마킹된 인덱스 키 공간은 방치하거나 재활용할 수 있다.
- 이 작업도 디스크 쓰기가 필요한 작업이다.
- MySQL 5.5 이상의 InnoDB에서는 이것 또한 버퍼링되어 지연 처리될 수도 있다. 처리가 지연된 인덱스 키 삭제는 사용자에게 악영향 없이 MySQL 서버 내부적으로 처리된다.

### 8.3.2.3 인덱스 키 변경

- 인덱스 키 값에 따라 리프 노드에 저장될 위치가 결정되므로, 단순히 값만 변경하는건 불가하다.
- 그래서 키를 삭제한 후, 다시 새 키 값을 추가하는 형태로 이뤄진다.
- InnoDB를 사용하는 테이블은 체인지 버퍼를 활용해 지연 처리할 수 있다.

### 8.3.2.4 인덱스 키 검색

- 인덱스 트리 탐색은 SELECT 뿐만아니라 UPDATE, DELETE 작업 시에도 진행한다.
- B-Tree 검색은 부등호 비교 조건이거나, 값의 앞부분만 일치하거나, 100% 일치하는 경우에 사용할 수 있다.
- 키 값의 뒷 부분만 검색하는 용도는 사용할 수 없다.
- 인덱스의 키 값이 변형된 후에 비교되는 경우에는 절대 B-Tree의 빠른 검색 기능을 사용할 수 없다. 이미 변형된 값은 B-Tree 인덱스에 존재하지 않기 때문이다. 그러므로 함수나 연산 수행 결과로 정렬하거나 검색하는 작업은 B-Tree의 장점을 이용할 수 없다.
- InnoDB에서는 레코드 락이나 갭 락이 검색을 수행한 인덱스를 잠근 후 테이블의 레코드를 잠근다. 그래서 UPDATE나 DELETE가 실행될 때 적절히 활용할 인덱스가 없다면 불필요하게 많은 레코드를 잠그게 된다. 그러므로 인덱스 설계가 중요하겠지?

## 8.3.3 B-Tree 인덱스 사용에 영향을 미치는 요소

인덱스를 구성하는 칼럼의 크기, 레코드 건수, 유니크한 인덱스 키 값의 개수 등

### 8.3.3.1 인덱스 키 값의 크기

- 페이지(Page) : InnoDB가 디스크에 데이터를 저장하는 가장 기본 단위. 블록이라고도 함.
    - 디스크의 모든 읽기 및 쓰기 작업의 최소 단위
    - InnoDB의 버퍼 풀에서 데이터를 버퍼링하는 기본 단위
    - 인덱스도 페이지 단위로 관리된다.
    - 루트, 브랜치, 리프 노드를 구분한 기준도 페이지
- B-Tree의 B는 Binary가 아니기에, 자식 노드의 수는 가변적이다.
    - 이는 인덱스의 페이지 크기와 키 값의 크기에 따라 결정된다.
    - 페이지의 크기는 MySQL 5.7 버전부터 innodb_page_size 시스템 변수로 4KB ~ 16KB 사이 값을 선택할 수 있지만, 기본값은 16KB이다.
    - 인덱스의 키가 16바이트라고 가정하자. 복합적인 정보가 담긴 `자식 노드 주소`는 페이지 종류에 따라 6 ~ 12바이트로 다양한 크기의 값을 가질 수 있다.
    
    | 인덱스 페이지 구성 요소 | 인덱스 키 | 자식 노드 주소 |
    | --- | --- | --- |
    | 크기 | 16(8 + 8) 바이트 | 6~12 바이트(여기선 12바이트로 가정) |
- 1개의 인덱스 페이지(16KB)에는 몇 개의 키를 저장할 수 있나?
    - 16*1024/(16+12) = 585개의 자식 노드를 가질 수 있다.
- 인덱스의 키 값이 커지면?
    - 키 값이 32바이트가 됐을 때, 16*1024/(32+12) = 372개의 자식 노드를 가질 수 있다.
    - 즉, 1회에 읽어올 수 있는 레코드의 양이 줄어든다는 뜻, 그만큼 탐색이 느려진다.
    - 또한 인덱스의 전체적인 크기가 커지므로, 메모리에 캐시해 둘 수 있는 레코드 수가 줄어든다.

### 8.3.3.2 B-Tree 깊이

- 깊이는 중요하지만 직접 제어할 수 없다.
- 깊이가 3이고 키 값이 16바이트면 최대 585**3개의 키 값을 담을 수 있지만, 키 값이 32바이트로 늘어나면 372**3개로 줄어든다.
- 즉, 몇 번이나 랜덤하게 디스크를 읽어야 하는지와 직결된다.(한 인덱스 페이지에 담을 수 있는 양이 줄어듦)
- 그러나 아무리 대용량 DB라도 B-Tree 깊이는 5 이상 깊어지기 어렵다. 인덱스 키 값을 작게 만들라는 의미임.

### 8.3.3.3 선택도(Selectivity)(기수성, Cardinality)

- 모든 인덱스 키 값 가운데 유니크한 값의 수(전체 인덱스 키 값 100개 중 유니크 값이 10개면, 기수성은 10)
- 중복 값이 많아지면 기수성(선택도)은 낮아진다.
- 인덱스는 선택도가 높을수록 검색 대상이 줄어들기에, 낮은 선택도일수록 빠르다.
- 그러나 선택도가 안좋더라도 정렬, 그루핑과 같은 작업을 위해 인덱스를 만드는 게 나을 수도 있다. 항상 검색용은 아니니 적절히 설계해라.

```sql
-- 1만 건의 레코드, country와 city (둘 다 VARCHAR(10), 인덱스는 country에 걸림)
SELECT *
FROM tb_test
WHERE country='KOREA' AND city='SEOUL';
```

- 위 쿼리에서 country 칼럼의 유니크 값이 10개면, `country='KOREA'` 와 일치하는 값이 1,000개다. 정확히 `country='KOREA' AND city='SEOUL'` 인 레코드가 1개라면, 불필요한 값 999개를 읽게 된다.
- 위 쿼리에서 country 칼럼의 유니크 값이 1,000개면, `country='KOREA'` 와 일치하는 값이 10개다. 정확히 `country='KOREA' AND city='SEOUL'` 인 레코드가 1개라면, 불필요한 값 9개를 읽게된다.
- 즉, 읽어오는 레코드의 양이 유니크 값이 적을수록 많아진다. 그 중 정확히 일치하는 값은 적을테니, 불필요하게 읽는 양을 줄이기 위해 Cardinality가 높은(유니크한 값이 많은) 칼럼에 인덱스를 걸자.

### 8.3.3.4 읽어야 하는 레코드의 건수

- 인덱스를 사용하여 레코드를 읽는 작업은 비용이 꽤 드는 작업이다.
- 일반적인 DBMS 옵티마이저에서는 인덱스를 통해 레코드 1건을 읽는 것이 테이블에서 직접 레코드 1건을 읽는 것보다 4~5배 비용이 많이 드는 것으로 예측한다.
- 즉, 인덱스로 읽어야 하는 레코드 수(옵티마이저가 판단)가 전체 테이블의 20~25%가 넘어서면 테이블을 모두 직접 읽어서 필요한 레코드만 필터링하는 방식이 더 좋다.
- 전체 테이블의 20~25%가 넘어가는 경우 강제로 인덱스를 사용하도록 힌트를 추가해도 이점이 없다. 물론 MySQL의 옵티마이저는 이런 경우 알아서 힌트를 무시하고 테이블을 직접 읽는다.

## 8.3.4 B-Tree 인덱스를 통한 데이터 읽기

### 8.3.4.1 인덱스 레인지 스캔

- 가장 대표적인 접근 방식
- 검색해야 할 인덱스의 범위가 결정되었을 때 사용
- 루트 노드부터 탐색을 시작해 브랜치 노드를 거쳐 리프 노드를 찾는다. 스캔을 시작할 위치를 찾으면, 끝낼 위치까지 순서대로 읽기만 하면 된다. 쭉 스캔한 후 사용자에게 반환하여 쿼리를 끝낸다.
- 위처럼 실제 인덱스만 읽을 수도 있지만, 실제 데이터 파일의 레코드도 읽어와야 하는 경우도 있다.
    - 인덱스는 자체적으로 정렬되는 특성이 있기에, 순차적으로 읽으면 어떤 방식으로 스캔하든 정렬된 레코드 값을 읽어올 수 있다.
    - 인덱스의 리프 노드에서 검색 조건에 일치하는 건들은 데이터 파일에서 읽어오는 과정이 필요하다. 레코드 한 건 단위로 랜덤 I/O가 발생한다. 그래서 비용이 많이 드는 거임
- 정리
    1. 인덱스 탐색 - 조건을 만족하는 값이 저장된 위치를 탐색한다.
    2. 인덱스 스캔 - 탐색한 위치부터 필요한 만큼 인덱스를 순차적으로 읽는다. (1, 2를 합쳐서 인덱스 스캔으로 말할 수도 있음)
    3. 읽어온 인덱스 키와 레코드 주소를 이용해 레코드가 저장된 페이지를 가져오고, 최종 레코드를 읽는다.
        - 커버링 인덱스로 처리되는 쿼리는 디스크 레코드를 읽지 않아도 되기 때문에, 랜덤 읽기가 상당히 줄고 성능이 빨라진다.
        - 
        - `Handler_read_key` : 상태 값은 인덱스 탐색을 실행한 횟수
        - `Handler_read_next` : 인덱스 스캔으로 읽은, 근데 정순으로 읽은 레코드 건수
        - `Handler_read_prev` : 인덱스 스캔으로 읽은, 근데 역순으로 읽은 레코드 건수
        - `Handler_read_first` : 인덱스의 첫 번째 레코드를 읽은 횟수
        - `Handler_read_last` : 인덱스의 마지막 레코드를 읽은 횟수
        - `Handler_read_first` 와 `Handler_read_last` 는 MIN(), MAX()로 읽은 경우만 증가한다.
        - 이 상태 값들은 테이블의 레코드 값을 읽었는지, 인덱스만 읽었는지 구분하지 않는다.

### 8.3.4.2 인덱스 풀 스캔

- 인덱스 처음부터 끝까지 모두 읽는 방식
- 쿼리 조건절에 사용된 칼럼이 인덱스의 첫 번째 칼럼이 아니면 사용된다. 인덱스는 (A, B, C)지만 쿼리 조건절이 B나 C로 검색하는 경우…
- 쿼리가 인덱스에 명시된 칼럼만으로 조건을 처리할 수 있는 경우 주로 이 방식을 쓴다.
- 그러나 인덱스뿐만 아니라 데이터 레코드까지 모두 읽어야 하면 절대 이 방식 안 쓴다.
- 인덱스 리프 노드의 제일 앞 또는 제일 뒤로 이동한 후, 인덱스 리프 노드를 읽는 링크드 리스트를 따라 처음부터 끝까지 스캔하는 방식이다.
- 테이블 풀 스캔보단 효율적이고, 인덱스 레인지 스캔보다는 효율이 떨어진다.
- 인덱스에 포함된 칼럼만으로 쿼리를 처리하면 테이블의 레코드를 읽을 필요가 없기 때문….
- 그래서 얘로 인덱스 사용하는 건 그리 효율적이진 못함

### 8.3.4.3 루스 인덱스 스캔

- 오라클의 `인덱스 스킵 스캔` 과 비슷하다.
- MySQL 5.7까진 제한적이었지만, 8.0부터는 최적화를 조금씩 지원한다.
- `인덱스 레인지 스캔` 과 `인덱스 풀 스캔` 은 타이트 인덱스 스캔으로 분류한다.(루스(Loose)와 상반된…)
- 인덱스 레인지 스캔과 비슷하게 작동하지만, 중간에 불필요한 인덱스 키 값은 무시하고 다음으로 넘어간다.
- 주로 GROUP BY, MAX(), MIN()에 최적화를 하는 경우 사용한다.

```sql
SELECT dept_no, MIN(emp_no)
FROM dept_emp
WHERE dep_no BETWEEN 'd002' AND 'd004'
GROUP BY dept_no;
```

- (dept_no, emp_no) 조합으로 인덱스가 설정되어 있으므로, dept_no 그룹별로 첫 레코드의 emp_no 값만 읽으면 된다. 이미 정렬이 되어 있기에 첫 값이 MIN 값이기 때문.
- 전 범위를 스캔하지 않아도 되는걸 옵티마이저는 알기에 조건에 맞지 않으면 스킵하고 다음 레코드로 이동한다.

### 8.3.4.4 인덱스 스킵 스캔

```sql
ALTER TABLE employees
	ADD INDEX ix_gender_birthdate (gender, birth_date);
```

- 위 인덱스를 사용하기 위해 WHERE에 gender 칼럼에 대한 비교 조건이 필요하다.

```sql
-- 인덱스 못 쓰는 쿼리, 이런 경우 birth_date로 인덱스 새로 생성 필요
SELECT * FROM employees WHERE birth_date>='1965-02-01';

-- 인덱스 쓸 수 있는 쿼리
SELECT * FROM employees WHERE gender='M' AND birth_date>='1965-02-01';
```

- 그런데 8.0부터는 옵티마이저가 gender 칼럼을 건너뛰어서 birth_date 칼럼만으로 인덱스 검색이 가능하도록 하는 인덱스 스킵 스캔 최적화 기능이 도입되었다.
- 루스 인덱스 스캔이랑 비슷하지만, 이는 GROUP BY를 위해 인덱스를 쓸 때만 사용할 수 있었다. 근데 인덱스 스킵 스캔은 WHERE 절의 검색을 위해 사용 가능하도록 용도가 넓어졌다.
- `SET optimizer_switch='skip_scan=[ on | off ]';` 으로 인덱스 스킵 스캔을 켜고 끌 수 있다.
- 인덱스 스킵 스캔 시 MySQL 옵티마이저는 gender 칼럼에서 유니크한 값을 모두 조회한 후, 주어진 쿼리에 gender 칼럼의 조건을 추가해 쿼리를 다시 실행하는 방식으로 처리한다.
- 위 방법은 MySQL 8.0에서 다음과 같은 단점이 있다.
    - WHERE 조건절에 조건이 없는 인덱스의 선행 칼럼의 유니크한 값의 개수가 적어야 함
        - 유니크한 값의 개수가 너무 많으면 MySQL 옵티마이저는 인덱스에서 스캔해야 할 시작 지점을 검색하는 작업이 많이 필요해져서, 쿼리 처리 성능이 오히려 느려질 수도 있다.
    - 쿼리가 인덱스에 존재하는 칼럼만으로 처리 가능해야 함(커버링 인덱스)
        - 인덱스에 존재하는 칼럼 외의 칼럼도 필요로 하면 풀 테이블 스캔으로 실행 계획을 수립하게 된다.

## 8.3.5 다중 칼럼(Multi-column) 인덱스

- 2개 이상 칼럼으로 구성된 인덱스. 복합 칼럼 인덱스, Concatenated Index라고도 한다.
- 다중 칼럼 인덱스에서는 인덱스의 앞쪽에 위치한 칼럼이 먼저 정렬되고, 그 다음 칼럼은 앞쪽 칼럼에 의존하여 정렬된다.
- (1, 1, 1), (1, 1, 2), (1, 2, 1), (1, 2, 2), (2, 1, 1)… 같은 방식을 생각하면 될 것 같다.

## 8.3.6 B-Tree 인덱스의 정렬 및 스캔 방향

- 인덱스를 어떤 방향으로 읽을지는 쿼리에 따라 옵티마이저가 실시간으로 만드는 실행 계획에 따라 결정된다.

### 8.3.6.1 인덱스의 정렬

- 일반 DBMS에서는 인덱스 생성 시점에 인덱스를 구성하는 각 칼럼의 정렬을 오름 또는 내림차순으로 설정할 수 있다.
- MySQL 5.7까지는 칼럼 단위로 정렬 순서를 혼합할 수 없었기에 -1을 곱하기도 했다. 근데 MySQL 8.0부터는 섞어서 해도 된다.

```sql
CREATE INDEX ix_teamname_userscore
```

### 8.3.6.1.1 인덱스 스캔 방향

- 인덱스 생성 시점에 오름차순 또는 내림차순으로 정렬이 결정되지만, 쿼리가 인덱스를 사용하는 시점에 어느 방향으로 읽는지에 따라 정렬 효과를 얻을 수 있다.
- 오름차순으로 정렬된 놈 거꾸로 읽으면 그것이 내림차순…
- MySQL 옵티마이저가 알아서 읽기 방향을 전환해준다.

### 8.3.6.1.2 내림차순 인덱스

인덱스 역순 스캔은 아래의 이유들 때문에 정순 스캔에 비해 약 30% 정도 시간이 더 걸린다.

1. 페이지 잠금이 인덱스 정순 스캔에 적합한 구조다.
2. 한 페이지 내의 인덱스 레코드는 단방향으로만 연결된 구조이기 때문에, 자주 사용되는 정렬 순서로 인덱스를 생성하는 것이 효율적이다.

## 8.3.7 B-Tree 인덱스의 가용성과 효율성

### 8.3.7.1 비교 조건의 종류와 효율성

```sql
SELECT * FROM dept_emp
WHERE dept_no='d002' AND emp_no >= 10114;
```

- 케이스 A : INDEX (dept_no, emp_no)
- 케이스 B : INDEX (emp_no, dept_no)
- 케이스 A는 dept_no가 ‘d002’인 레코드를 먼저 찾고, emp_no가 10114 이상인 레코드만 찾아오면 된다.
- 근데 케이스 B는 emp_no가 10114 이상인 레코드 중 dept_no가 ‘d002’인 레코드를 찾아야 하기에 불필요한 레코드 읽기가 발생한다.
- 작업 범위 결정 조건, 필터링 조건(체크 조건) - 공식적인 용어는 아님!
- 케이스 A의 dept_no, emp_no, 케이스 B의 emp_no는 작업 범위 결정 조건, 케이스 B의 dept_no는 필터링 조건이다.
- 작업 범위 결정 조건은 많을수록 쿼리 처리 성능이 증가하지만, 필터링 조건은 많다고 해서 쿼리 처리 성능이 올라가진 않는다.

### 8.3.7.2 인덱스의 가용성

- B-Tree 인덱스는 왼쪽 값에 기준하여 오른쪽 값이 정렬되어 있다.
- 하나의 칼럼으로 검색해도 값이 왼쪽 부분이 없으면 인덱스 레인지 스캔이 불가능하다.
- 다중 칼럼 인덱스에서 왼쪽 칼럼의 값을 모르면 인덱스 레인지 스캔이 불가능하다.

### 8.3.7.3 가용성과 효율성 판단

- B-Tree 인덱스에서 작업 범위 결정 조건으로 사용할 수 없는 조건들(경우에 따라 체크 조건으로 사용 가능)
    1. NOT-EQUAL로 비교된 경우(”<>”, “NOT IN”, “NOT BETWEEN”, “IS NOT NULL”)
        - MySQL에는 NULL 값도 인덱스에 저장되기 때문에, 작업 범위 결정 조건으로 사용 가능
    2. LIKE ‘%??’(앞부분이 아닌 뒷부분 일치) 형태로 문자열 패턴이 비교된 경우
    3. 스토어드 함수나 다른 연산자로 인덱스 칼럼이 변형된 후 비교된 경우
    4. NON-DETERMINISTIC 속성의 스토어드 함수가 비교 조건에 사용된 경우
    5. 데이터 타입이 서로 다른 비교(인덱스 칼럼의 타입을 변환해야 비교가 가능한 경우)
    6. 문자열 데이터 타입의 콜레이션이 다른 경우
- 다음과 같은 인덱스가 있을 때, 작업 범위 결정 조건으로 사용이 가능하거나 불가능한 경우들

```sql
INDEX ix_test (column_1, column_2, column_3, ..., column_n)
```

1. 작업 범위 결정 조건으로 인덱스를 사용하지 못하는 경우
    1. column_1 칼럼에 대한 조건이 없는 경우
    2. column_1 칼럼의 비교 조건이 인덱스 사용 불가 조건 중 하나인 경우
2. 작업 범위 결정 조건으로 인덱스를 사용하는 경우(2 < i < n)
    1. column_1 ~ column(i-1) 칼럼까지 동등 비교 형태(”=”이나 “IN”)로 비교
    2. column_i 칼럼에 대해 다음 연산자 중 하나로 비교
        1. 동등 비교(”=”이나 “IN”)
        2. 크다 작다 형태(”>” 또는 “<”)
        3. LIKE로 좌측 일치 패턴(LIKE ‘경원%’)
- 위 두 가지 조건을 모두 만족하는 쿼리는 column_1부터 column_i까지는 작업 범위 결정 조건으로 사용되고, column_(i+1)부터 column_n까지의 조건은 체크 조건으로 사용된다.

# 8.5 전문(Full Text) 검색 인덱스

## 8.5.1 인덱스 알고리즘

- 어근 분석, n-gram 분석 알고리즘

### 8.5.1.1 어근 분석 알고리즘

- 다음 두 가지 중요한 과정을 거쳐 색인 작업이 수행된다.
    1. 불용어(Stop Word) 처리
    2. 어근 분석(Stemming)
- 불용어 처리
    - 검색에서 별 가치가 없는 단어를 모두 필터링하여 제거하는 작업
    - 불용어의 개수는 적어서 상수로 정의하여 사용하는 경우가 많으며, 사용자가 별도로 정의할 수도 있다.
- 어근 분석
    - 검색어로 선정된 단어의 뿌리인 원형을 찾는 작업
    - 오픈 소스 형태소 분석 라이브러인 MeCab을 플러그인 형태로 사용 가능하도록 지원
    - 근데 학습시키는 과정이 까다로움

### 8.5.1.2 n-gram 알고리즘

- 전문적인 검색 엔진을 고려하는게 아니라면 MeCab을 위한 형태소 분석은 범용적으로 적용하기 쉽지 않다. 이를 보완하는 것이 n-gram이다.
- 키워드를 검색해내기 위한 인덱싱 알고리즘
- 본문을 무조건 몇 글자씩 잘라서 인덱싱하는 방법
- 일반적으로 2글자씩 끊어서 인덱싱하는 2-gram 방식을 많이 사용
- 각 단어를 공백과 마침표를 기준으로, 2글자씩 중첩하여 토큰으로 분리하는 방식
- 이때 불용어를 포함하거나 불용어와 동일하면 걸러서 버린다. 불용어는 `information_schema.innodb_ft_default_stopword` 테이블에서 확인할 수 있다.
- MySQL 서버는 이렇게 구분된 토큰을 B-Tree 인덱스에 저장한다.
- 상세한 과정은 책을 참고하자.

### 8.5.1.3 불용어 변경 및 삭제

- 이미 등록된 불용어 때문에 혼동이 오는 경우가 있을 수 있다.

### 전문 검색 인덱스의 불용어 처리 무시

1. MySQL 서버 설정 파일(my.cnf)의 `ft_stopword_file` 시스템 변수에 빈 문자열을 설정
    1. 저 시스템 변수에 사용자가 직접 정의한 불용어 목록 파일을 지정할 수도 있다.
2. InnoDB 테이블의 전문 검색 인덱스의 불용어 처리를 무시하기 위해 `innodb_ft_enable_stopword`  시스템 변수를 OFF로 설정
    1. MyISAM과 같이 다른 스토리지 엔진을 쓰는 테이블은 여전히 내장 불용어 처리를 사용하지만, InnoDB 테이블은 사용하지 않는다.
    2. 동적인 시스템 변수라 MySQL 서버가 실행 중일 때도 변경 가능하다. `SET GLOBAL innodb_ft_enable_stopword=OFF;` 

### 사용자 정의 불용어 사용

- MySQL 서버 설정 파일(my.cnf)의 `ft_stopword_file` 시스템 변수에 파일 경로를 등록
    - `ft_stopword_file='~~~~'`
- InnoDB에서만 사용할 수 있는데, 불용어 목록을 테이블로 저장
    - 불용어 목록 변경 후 전문 검색 인덱스를 생성해주자. 그래야 불용어가 적용됨

```sql
SET GLOBAL innodb_ft_server_stopword_table='mydb/my_stopword';
ALTER TABLE tb_bi_gram
	ADD FULLTEXT INDEX fx_title_body(title, body) WITH PARSER ngram;
```

- 여러 전문 검색 인덱스가 서로 다른 불용어를 사용해야 한다면 테이블로 불용어 목록을 지정해주는 방법을 선택하자.

## 8.5.2 전문 검색 인덱스의 가용성

- 전문 검색 인덱스의 사용을 위해 두 가지 조건을 반드시 갖춰야 한다.
    - 쿼리 문장이 전문 검색을 위한 문법(MATCH … AGAINST …)을 사용
        - 전문 검색 인덱스를 구성하는 칼럼들은 MATCH 절의 괄호 안에 모두 명시되어야 한다.
        - `SELECT * FROM tb_test WHERE MATCH(doc_body) AGAINST('애플' IN BOOLEAN MODE);`
    - 테이블이 전문 검색 대상 칼럼에 대해서 전문 인덱스 보유

# 8.7 멀티 밸류 인덱스

- 전문 검색 인덱스를 제외한 모든 인덱스는 인덱스 키 값과 데이터 레코드가 1 : 1 관계이다. 그러나 멀티 밸류 인덱스는 하나의 데이터 레코드가 여러 개의 키 값을 가질 수 있는 형태의 인덱스이다.
- 정규화에 위배되는 형태로 보일 수도 있지만, 최근 RDBMS들이 JSON 타입을 지원하며 JSON의 배열 타입 필드에 저장된 원소들에 대한 인덱스 요건이 발생한 것이다.

```sql
CREATE TABLE user (
	user_id BIGINT AUTO_INCREMENT PRIMARY KEY,
	first_name VARCHAR(10),
	last_name VARCHAR(10),
	credit_info JSON,
	INDEX mx_creditscores( (CAST(credit_info->'$.credit_scores' AS UNSIGNED ARRAY)) )
);

INSERT INTO user VALUES (1, 'Matt', 'Lee', '{"credit_scores" : [360, 353, 351]}');
```

- 멀티 밸류 인덱스를 사용하려면 다음 함수들을 사용해야 한다.
    - MEMBER OF()
    - JSON_CONTAINS()
    - JSON_OVERLAPS()

```sql
SELECT * FROM user WHERE 360 MEMBER OF(credit_info -> '$.credit_scores');
EXPLAIN SELECT * FROM user WHERE 360 MEMBER OF(credit_info->'$.credit_scores');
```

# 8.8 클러스터링 인덱스

- InnoDB에서만 지원

## 8.8.1 클러스터링 인덱스

- “프라이머리 키” 값이 비슷한 레코드끼리 묶어서 저장하는 것을 의미
- 프라이머리 키 값에 의해 레코드 저장 위치가 결정된다. 그래서 프라이머리 키 값이 변경되면 그 레코드의 물리적인 저장위치도 바뀌어야 한다.
- 프라이머리 키 값으로 클러스터링된 테이블은 프라미어리 키 값 자체에 대한 의존도가 상당히 크기 때문에 신중히 결정해야 한다.
- 클러스터링의 기준이 되는 프라이머리 키는 클러스터링 키라고도 표현한다.
- InnoDB와 같이 항상 클러스터링 인덱스로 저장되는 테이블은 프라이머리 키 기반의 검색이 매우 빠르며, 대신 레코드 저장이나 프라이머리 키의 변경이 상대적으로 느리다.
- 클러스터링 테이블의 구조 자체는 일반 B-Tree와 비슷하지만, 세컨더리 인덱스를 위한 B-Tree 리프 노드와는 달리 클러스터링 인덱스의 리프 노드에는 레코드의 모든 칼럼이 같이 저장되어 있음을 알 수 있다.

### 만약 PK가 없다면 InnoDB 테이블은 어떻게 클러스터링 테이블로 구성될까?

- 다음 우선순위대로 PK를 대체할 칼럼을 선택한다.
    1. 프라이머리 키가 있으면 기본적으로 프라이머리 키를 클러스터링 키로 선택
    2. NOT NULL 옵션의 유니크 인덱스 중에서 첫 번째 인덱스를 클러스터링 키로 선택
    3. 자동으로 유니크한 값을 가지도록 증가되는 칼럼을 내부적으로 추가한 후, 클러스터링 키로 선택
- 적절한 클러스터링 키 후보를 찾지 못하면 InnoDB 내부적으로 레코드의 일련번호 칼럼을 생성한다. 이 칼럼은 사용자에게 노출되지 않으며 쿼리 문장에 명시적으로 사용할 수 없다.
- 그러니까 명시적으로 PK를 생성하자!

## 8.8.2 세컨더리 인덱스에 미치는 영향

- InnoDB 테이블의 세컨더리 인덱스가 실제 레코드가 저장된 주소를 가지고 있다면?
    - 클러스터링 키 값이 변경될 때마다 데이터 레코드의 주소가 변경되고 그때마다 해당 테이블의 모든 인덱스에 저장된 주소값을 변경해야 한다.
    - 이런 오버헤드를 제거하기 위해 InnoDB 테이블의 모든 세컨더리 인덱스는 해당 레코드가 저장된 주소가 아니라 프라이머리 키 값을 저장하도록 구현되어 있다.

### 8.8.3 클러스터링 인덱스의 장점과 단점

| 장점 | - 프라이머리 키(클러스터링 키)로 검색할 때 처리 성능이 매우 빠름(특히, 프라이머리 키를 범위 검색하는 경우 매우 빠름)
- 테이블의 모든 세컨더리 인덱스가 프라이머리 키를 가지고 있기 때문에 인덱스만으로 처리될 수 있는 경우가 많음(커버링 인덱스) |
| --- | --- |
| 단점 | - 테이블의 모든 세컨더리 인덱스가 클러스터링 키를 갖기 때문에 클러스터링 키 값의 크기가 클 경우 전체적으로 인덱스의 크기가 커짐
- 세컨더리 인덱스를 통해 검색할 때 프라이머리 키로 다시 한 번 검색해야 하므로 처리 성능이 느림
- INSERT할 때 프라이머리 키에 의해 레코드의 저장 위치가 결정되기 때문에 처리 성능이 느림
- 프라이머리 키를 변경할 때 레코드를 DELETE하고 INSERT하는 작업이 필요하기 때문에 처리 성능이 느림 |
- 클러스터링 인덱스의 장점 대부분은 빠른 읽기며, 단점은 느린 쓰기다.
- 온라인 트랜잭션 환경은 쓰기와 읽기 비율이 2:8 혹은 1:9 정도기 때문에 조금 느린 쓰기를 감수하고 읽기를 빠르게 유지하는건 중요하다.

### 8.8.4 클러스터링 테이블 사용 시 주의사항

### 8.8.4.1 클러스터링 인덱스 키의 크기

- 클러스터링 테이블은 모든 세컨더리 인덱스가 프라이머리 키 값을 포함하는데, 프라이머리 키의 크기가 커지면 세컨더리 인덱스의 크기도 자동으로 커진다.
- 프라이머리 키의 크기가 10바이트에서 50바이트로 커지면, 레코드가 1천만 건일 때 1.9GB가 증가하게 된다.

### 8.8.4.2 프라이머리 키는 AUTO-INCREMENT보다는 업무적인 칼럼으로 생성(가능한 경우)

- InnoDB의 PK는 클러스터링 키로 사용되며, 이 값에 의해 레코드의 위치가 결정된다.
- 그래서 PK로 검색하는 경우 매우 빠르게 처리할 수 있다.
- 업무적인 칼럼으로 생성하라는 의미는, 중요한 역할을 하며 빈번하게 검색에 사용되니 크기가 커지더라도 대표할 수 있을만한 내용으로 설정하라는 뜻이다.

### 8.8.4.3 프라이머리 키는 반드시 명시할 것

- InnoDB 테이블에서 PK가 없으면 InnoDB 내부적으로 일련번호 칼럼을 추가한다. 근데 이렇게 추가된 칼럼은 사용자가 확인할 수 없기에 전혀 접근할 수 없다.
- 또한 ROW 기반 복제나 InnoDB Cluster에서 모든 테이블이 PK를 가져야 정상적인 복제 성능을 보장할 수 있으므로, AUTO_INCREMENT도 좋으니 일단 설정하자.

### 8.8.4.4 AUTO-INCREMENT 칼럼을 인조 식별자로 사용할 경우

- 여러 개의 칼럼이 복합적으로 PK로 만들어진다면 PK의 크기가 커질 수도 있다. 세컨더리 인덱스가 필요하지 않다면, 그냥 크기가 커진 PK를 쓰는게 좋다.
- 근데 세컨더리 인덱스도 필요하다? 그러면 AUTO_INCREMENT 칼럼을 추가하고 이를 PK로 설정하라.
- 이렇게 기존 PK를 대체하여 인위적으로 추가된 PK를 인조 식별자(Surrogate Key)라고 한다.
- 또한 로그 테이블처럼 INSERT가 더 빈번한 테이블은 AUTO_INCREMENT를 이용한 인조 식별자를 PK로 설정하는게 성능 향상에 좋다.

# 8.9 유니크 인덱스

- 제약조건에 가깝다. 테이블이나 인덱스에 중복된 값이 저장되지 못하게 한다.
- MySQL에서는 인덱스 없이 유니크 제약을 설정할 수 없다.
- 유니크 인덱스에서 NULL 저장은 허용된다. 특정 값이 아니기 때문…
- MySQL의 프라이머리 키는 기본적으로 NOT NULL을 설정하는 유니크 속성이 자동으로 부여된다.

## 8.9.1 유니크 인덱스와 일반 세컨더리 인덱스의 비교

### 8.9.1.1 인덱스 읽기

- 유니크 인덱스와 유니크하지 않은 세컨더리 인덱스 사이 성능상 차이는 거의 없다.
    - I/O가 일어나는 것이 아니라 CPU에서 칼럼 값을 비교하는 작업이기 때문.
    - 단지 유니크하지 않은 세컨더리 인덱스가 읽을 내용이 좀 더 많기에 느리게 보이는 것일 뿐, 단위 레코드 당 읽는 속도는 큰 차이 없다.
- 하나의 값을 검색하는 경우, 유니크 인덱스와 일반 세컨더리 인덱스는 사용되는 실행 계획이 다르다.
    - 그러나 인덱스 성격의 유니크 여부에 따른 차이일 뿐, 성능 상 차이는 없다.

### 8.9.1.2 인덱스 쓰기

- 유니크 인덱스의 키 값을 쓸 땐 중복된 값이 있는지 없는지 체크하는 과정이 하나 더 필요하기에, 유니크하지 않은 세컨더리 인덱스의 쓰기보다 느리다.
- 그런데 MySQL에서 유니크 인덱스의 중복 검사 시 읽기 잠금을 쓰고, 쓰기 작업 시 쓰기 잠금을 사용한다. 이 과정에서 데드락이 빈번히 발생한다.
- InnoDB에는 인덱스 키의 저장을 버퍼링하기 위해 체인지 버퍼를 쓰는데, 유니크 인덱스는 반드시 중복 체크가 필요해서 작업 자체를 버퍼링할 수 없다.
- 따라서, 유니크 인덱스가 일반 세컨더리 인덱스보다 변경 작업이 느리다!

## 8.9.2 유니크 인덱스 사용 시 주의사항

- 성능 향상을 위해 불필요한 유니크 인덱스 생성은 삼가라.
- 유니크 인덱스와 일반 인덱스를 한 테이블의 같은 칼럼에 중복해서 생성할 필요는 없다. 이미 같은 역할을 하기 때문…
- 또한 같은 칼럼에 대해 PK와 유니크 인덱스를 동일하게 설정하지 말자.
- 다시 말해, 유일성이 꼭 보장되어야 하는 칼럼은 유니크 인덱스를 생성하되, 필수가 아니라면 유니크하지 않은  세컨더리 인덱스를 생성하는 것도 고려하자.

# 8.10 외래키

- InnoDB에서만 생성할 수 있으며, 외래키 제약이 설정되면 자동으로 연관되는 테이블의 칼럼에 인덱스가 생성된다.
- 외래키가 제거되지 않은 채로 자동으로 생성된 인덱스를 삭제할 수 없다.
- 테이블의 변경(쓰기 잠금)이 발생하는 경우에만 잠금 경합(잠금 대기)이 발생한다.
- 외래키와 연관되지 않은 칼럼의 변경은 최대한 잠금 경합(잠금 대기)을 발생시키지 않는다.

## 8.10.1 자식 테이블의 변경이 대기하는 경우

1. 부모 테이블의 업데이트
2. 쓰기 잠금 획득(부모 테이블)
3. 자식 테이블이 해당 부모를 참조하도록 FK 수정
4. 3에서 잠금 경합 발생 → 대기
5. 1번 트랜잭션이 롤백되거나 커밋됨
6. 3번 작업이 수행된다.

## 8.10.2 부모 테이블의 변경 작업이 대기하는 경우

1. 자식 테이블 업데이트
2. 쓰기 잠금 획득(자식 테이블)
3. 자식 테이블이 참조하는 부모 테이블의 레코드 삭제 (`ON DELETE CASCADE` 걸려 있는 상태)
4. 3에서 잠금 경합 발생 → 대기
5. 1번 트랜잭션이 롤백되거나 커밋됨
6. 3번 작업이 수행된다.
