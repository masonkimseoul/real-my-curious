# 10장 - 실행 계획
`EXPLAIN` 명령으로 확인 가능
# 10.1 통계 정보
- MySQL 5.7까지는 테이블, 인덱스에 대한 개괄적인 정보만 사용하여 실행 계획 수립
	- 테이블 칼럼 값들의 실제 분포에 대한 정보가 없어서 정확도가 낮음
- 8.0 부터 인덱스되지 않은 칼럼에 대해서도 분포도를 수집해 저장하는 히스토그램 정보 도입
## 10.1.1 테이블 및 인덱스 통계 정보
- 비용 기반 최적화에서 통계 정보는 가장 중요함, 잘못된 방향으로 쿼리를 실행할 수도 있기 때문

### 10.1.1.1 MySQL 서버의 통계 정보
- 5.6 버전부터 InnoDB 테이블에 대한 통계 정보를 영구적으로 관리할 수 있다.
- `innodb_index_stats`, `innodb_table_stats` 테이블에 저장
- `STATS_PERSISTENT` 옵션으로 영구적인 통계 정보를 테이블 단위로 유지할 수 있음
	- STATS_PERSISTENT = 0 : 테이블에 저장 안함
	- STATS_PERSISTENT = 1 : 테이블에 저장함
	- STATS_PERSISTENT = DEFAULT : 옵션 설정하지 않은 것과 같으며 `innodb_stats_persistent` 시스템 변수 값으로 결정
	 - `ALTER TABLE ~~ STATS_PERSISTENT = ?` 처럼 설정 가능
- `innodb_index_stats`(통계정보)의 각 칼럼은 다음 값들을 저장하고 있다.
	- `stat_name='n_diff_pfx%'` : 인덱스가 가진 유니크한 값 개수
	- `stat_name='n_leaf_pages'` : 인덱스의 리프 노드 페이지 개수
	- `stat_name='size'` : 인덱스 트리의 전체 페이지 개수
	- `n_rows`: 테이블 전체 레코드 건수
	- `clustered_index_size` : 프라이머리 키의 크기(InnoDB 페이지 개수)
	- `sum_of_other_index_sizes` : 프라이머리 키를 제외한 인덱스의 크기(InnoDB 페이지 개수)
		- 이 값은 `STATS_AUTO_RECALC` 옵션에 따라 0으로 보일 수도 있는데, `ANALYZE TABLE` 명령으로 통계값을 저장할 수 있다.
- 5.5 버전까지 테이블 통계 정보가 메모리에만 저장돼서 서버 재시작 시 통계 정보가 초기화된다. 그래서 매 시작 시 마다 다시 수집해야 했다.
- 또한 사용자, 관리자가 모르는 순간 다음 이벤트가 발생하면 자동으로 통계 정보가 갱신됐다.
	- 테이블이 새로 오픈되는 경우
	- 테이블 레코드가 대량으로 변경되는 경우(테이블 전체 레코드 중 1/16 정도의 UPDATE, INSERT, DELETE가 실행될 때)
	- ANALYZE TABLE이 실행될 때
	- SHOW TABLE STATUS 또는 SHOW INDEX FROM 명령이 실행될 때
	- InnoDB 모니터가 활성화될 때
	- `innodb_stats_on_metadata` 시스템 설정이 ON 일 때 SHOW TABLE STATUS가 실행될 때
- 자주 테이블의 통계정보가 갱신된다면 쿼리 실행 시 인덱스를 사용하지 않게 될 수도 있다.
- `innodb_stats_auto_recalc` 시스템 설정 변수의 값을 OFF로 설정하여 통계정보 자동 갱신을 막을 수 있다. 이 변수의 기본 값은 ON이다.
	- `STATS_AUTO_RECALC=1` : 테이블 통계 정보를 5.5 이전 방식으로 자동 수집
	- `STATS_AUTO_RECALC=0` : 테이블 통계 정보를 `ANALYZE TABLE` 명령 실행 시만 수집
	- `STATS_AUTO_RECALC=DEFAULT` : 따로 설정하지 않은 것과 동일
	- InnoDB 테이블 블록을 몇 개나 샘플링할 지 결정하는 옵션으로, `innodb_stats_transient_sample_pages`와 `innodb_stats_persistent_sample_pages` 시스템 변수가 있다.
		- `innodb_stats_transient_sample_pages` : 자동 통계 정보 수집 시 임의로 샘플링할 페이지의 개수, 기본값은 8
		- `innodb_stats_persistent_sample_pages` : ANALYZE TABLE 명령 실행 시 샘플링하여 분석 후 그 결과를 통계 정보 테이블에 저장할 페이지의 개수, 기본값은 20
- 영구적인 통계 정보를 쓴다면 서버 사용량이 적은 시간에 더 정확히 정보를 수집할 수 있겠다. `innodb_stats_persistent_sample_pages` 변수에 높은 값을 설정하여 더 정확히 수집할 수 있겠지만 정보 수집 시간이 길어진다.
## 10.1.2 히스토그램
### 10.1.2.1 히스토그램 정보 수집 및 삭제
- 8.0에서 히스토그램 정보는 칼럼 단위로 관리된다.
	- `ANALYZE TABLE ... UPDATE HISTOGRAM` 명령으로 수동 수집 및 관리
- 수집된 히스토그램 정보는 시스템 딕셔너리에 함께 저장
- MySQL 서버 시작 시 딕셔너리의 히스토그램 정보를 `information_schema` 데이터베이스의 `column_statistics` 테이블로 로드(이 테이블에 SELECT 날리면 확인 가능)
- Singleton(싱글톤 히스토그램) : 칼럼값 개별로 레코드 건수를 관리하는 히스토그램. Value-Based 히스토그램 또는 도수 분포라고 불림
- Equi-Height(높이 균형 히스토그램) : 칼럼값의 범위를 균등한 개수로 구분하여 관리 ,Height-Based라고도 불림
- 버킷 단위로 구분되어 레코드 건수, 칼럼값 범위가 관리됨
	- 싱글톤은 칼럼이 가지는 값별로 버킷이 할당, 각 버킷이 칼럼 값과 발생 빈도 비율을 가짐. 총 2개 값
	- 높이 균형은 개수가 균등한 칼럼값의 범위별로 버킷이 할당, 각 버킷이 범위 시작 값과 마지막 값, 발생빈도율과 유니크한 값의 개수를 가짐. 총 4개 값
- 레코드 건수 비율은 누적으로 표시됨
- `information_schema.column_statistics` 테이블의 `HISTOGRAM`칼럼의 필드들
	- `sampling-rate`: 히스토그램 정보 수집을 위해 스캔한 페이지 비율, 0.35면 35% 스캔한 것, 샘플링 비율 높을수록 시스템 부하가 높다. `histogram_generation_max_mem_size` 시스템 변수에 설정된 메모리 크기에 맞게 샘플링을 진행한다. 기본값은 20MB
	- `histogram-type` : 히스토그램 종류 저장
	- `member-of-buckets-specified` : 히스토그램 생성 시 설정한 버킷 개수를 저장. 별도로 지정 안하면 기본값은 100개다. 최대 1024개를 설정할 수 있지만 일반적으로 100개면 충분하다.
- 8.0.19 미만 버전까진 히스토그램 생성에 풀 테이블 스캔을 진행했지만, 이제는 그렇지 않다.
- 히스토그램은 `DROP HISTOGRAM ON ?` 명령으로 삭제할 수 있다. 테이블 데이터를 참조하는 게 아니라 딕셔너리 내용만 삭제하기 때문에 다른 쿼리 처리 성능에 영향을 주지 않고 즉시 완료된다. 그러나 실행계획이 달라질 수 있으니 주의가 필요하다.
- 삭제하지 않고 옵티마이저가 히스토그램을 안 쓰게 하려면 `optimizer_switch` 시스템 변수 값을 변경하면 된다.

### 10.1.2.2 히스토그램의 용도
- 실제 어플리케이션의 데이터는 항상 균등한 분포도를 가지지 않기 때문에, 각 범위(버킷)별로 레코드 건수와 유니크 값 개수에 대한 정보가 있기에, 단순 통계 정보를 쓰는 것 보다 좀 더 정확한 예측이 가능
- 히스토그램이 없으면 옵티마이저는 데이터가 균등히 분포되어 있을 것으로 예측한다. 있으면 특정 범위 데이터가 많고 적음을 식별할 수 있음
- 조인의 드라이빙 테이블을 무엇으로 정할 지 등... 조인 횟수도 줄일 수 있다.

### 10.1.2.3 히스토그램과 인덱스
- 쿼리 실행계획 수립 시 사용 가능한 인덱스들로부터 조건절에 일치하는 레코드 건수를 대략 파악 후 가장 나은 실행 계획을 선택하는데, 조건절에 일치하는 레코드 건수를 예측하기 위해 옵티마이저가 실제 인덱스의 B-Tree를 샘플링하여 살펴본다. `인덱스 다이브`
- 히스토그램은 주로 인덱스되지 않은 칼럼에 대한 데이터 분포도를 참조하는 용도로 사용
	- 인덱스 된 칼럼에는 인덱스 다이브를 실시하는데, 실제 검색 조건의 대상 값에 대한 샘플링을 실행하므로 항상 히스토그램보다 정확한 결과를 기대할 수 있음
	- 그러나 인덱스 다이브는 비용이 있으며, IN 절에 값이 많이 있으면 실행 계획 수립만으로 큰 부하가 됨.

### 10.1.3 코스트 모델(Cost Model)
- MySQL 서버가 쿼리를 처리할 때 전체 쿼리의 비용을 계산한 결과를 바탕으로 실행 계획을 수립한다.
- 이때 전체 쿼리 비용 계산 시 필요한 단위 작업 비용들을 코스트 모델이라고 한다.
- MySQL 8.0 서버의 코스트 모델은 다음 2개 테이블에 저장되어 있는 설정 값을 사용한다.
	- server_cost : 인덱스를 찾고 레코드를 비교하고 임시 테이블 처리에 대한 비용 관리
	- engine_cost : 레코드를 가진 데이터 페이지를 가져오는 데 필요한 비용 관리
	- 두 테이블은 다음 칼럼들을 가지고 있다.
		- cost_name : 코스트 모델의 각 단위 작업
		- default_value : 각 단위 작업 비용. 소스코드에 설정되어 있다.
		- cost_value : DBMS 관리자가 설정한 값. NULL이면 default_value 칼럼의 비용 사용
		- last_updated : 단위 작업의 비용이 변경된 시점
		- comment : 비용에 대한 추가 설명
	- engine_cost 테이블에 추가로 있는 칼럼들
		- engine_name : 비용 적용된 스토리지 엔진
		- device_type : 디스크 타입

|             | cost_name                    | defalut_value | 설명                 |
| ----------- | ---------------------------- | ------------- | ------------------ |
| engine_cost | io_block_read_cost           | 1.00          | 디스크 데이터 페이지 읽기     |
|             | memory_block_read_cost       | 0.25          | 메모리 데이터 페이지 읽기     |
| server_cost | disk_temptable_create_cost   | 20.00         | 디스크 임시 테이블 생성      |
|             | dist_temptable_row_cost      | 0.50          | 디스크 임시 테이블의 레코드 읽기 |
|             | key_compare_cost             | 0.05          | 인덱스 키 비교           |
|             | memory_temptable_create_cost | 1.00          | 메모리 임시 테이블 생성      |
|             | memory_temptable_row_cost    | 0.10          | 메모리 임시 테이블의 레코드 읽기 |
|             | row_evaluate_cost            | 0.10          | 레코드 비교             |
- `row_evaluate_cost`는 스토리지 엔진이 반환한 레코드가 쿼리 조건에 일치하는지 평가하는 단위 작업이다. 이 값이 증가할수록 풀 테이블 스캔과 같이 많은 레코드를 처리하는 쿼리 비용이 높아지고, 레인지 스캔 같이 상대적으로 적은 수의 레코드를 처리하는 쿼리 비용은 낮아진다.
- `key_compare_cost`는 키 값 비교 작업에 필요한 비용을 의미한다. 이 값이 증가할수록 레코드 정렬과 같이 키 값 비교 처리가 많은 경우 쿼리 비용이 높아진다.
- 각 단위 작업 비용으로 실행 계획에 표시되는 비용을 직접 계산하는 건 쉽지 않다. 추가적으로 필요한 값들이 모두 사용자에게 표시되지 않기 때문이다.
- 가장 중요한 건 각 단위 작업에 설정되는 비용 값의 변동에 따라 실행 계획의 비용이 달라지는 것이다.
	- `key_compare_cost` 비용이 높아지면, 옵티마이저가 가능하면 정렬을 수행하지 않는 방향의 실행 계획을 선택할 가능성이 높아진다.
	- `row_evaluate_cost` 비용이 높아지면, 풀 스캔을 실행하는 쿼리 비용이 높아지고 옵티마이저는 가능하면 인덱스 레인지 스캔을 사용하는 실행 계획을 선택할 가능성이 높아진다.
	- `disk_temptable_create_cost`와 `disk_temptable_row_cost` 비용을 높이면 옵티마이저는 디스크에 임시 테이블을 만들지 않는 방향의 실행 계획을 선택할 가능성이 높아진다.
	- `memory_temptable_create_cost`와 `memory_temptable_row_cost` 비용을 높이면 옵티마이저는 메모리 임시 테이블을 만들지 않는 방향의 실행 계획을 선택할 가능성이 높아진다.
	- `io_block_read_cost` 비용이 높아지면 옵티마이저는 가능하면 InnoDB 버퍼 풀에 데이터 페이지가 많이 적재돼 있는 인덱스를 사용하는 실행 계획을 선택할 가능성이 높아진다.
	- `memory_block_read_cost` 비용이 높아지면 서버는 InnoDB 버퍼 풀에 적재된 데이터 페이지가 상대적으로 적다고 하더라도 그 인덱스를 사용할 가능성이 높아진다.
- 그러나 각 단위 작업 비용을 사용자가 변경할 수 있더라도, 꼭 변경할 필요는 없다. 서버 내부적인 처리 방식에 대한 깊은 이해가 없다면 함부로 바꾸지 마라.

# 10.2 실행 계획 확인
- DESC 또는 EXPLAIN 명령으로 확인 가능

## 10.2.1 실행 계획 출력 포맷
- EXPLAIN에 FORMAT 옵션으로 JSON이나 TREE, 단순 테이블 형태로 확인할 수 있다.

## 10.2.2 쿼리의 실행 시간 확인
- EXPLAIN ANALYZE
- SHOW PROFILE 도 비슷한 명령인데, 실행 계획의 단계별로 소요된 시간 정보를 보여주지 않는다.
- EXPLAIN ANALYZE는 항상 TREE 포맷으로 결과를 보여준다.
- 들여쓰기가 가장 안쪽인 라인이 먼저 실행된다.
- 들여쓰기 레벨이 같다면 가장 상단에 위치한 라인부터 먼저 실행된다.
- EXPLAIN ANALYZE는 EXPLAIN과 달리 실행 계획만 추출하는 것이 아니라 실제 쿼리를 실행하고, 사용한 실행 계획과 소요 시간을 보여준다.
	- 쿼리 실행 시간이 아주 많이 걸린다면 EXPLAIN을 먼저 실행하여 확인 후 튜닝을 한 뒤 EXPLAIN ANALYZE를 실행하자.
