# 5장 - 트랜잭션과 잠금

트랜잭션 - 작업의 완전성을 보장. 모두 완벽하게 처리하거나, 모두 처리하지 않거나.. 작업의 일부만 적용되지 않도록 한다.

락 - 동시성을 제어
트랜잭션 - 데이터의 정합성을 보장
격리수준 - 하나의 트랜잭션 내부 또는 여러 트랜잭션 간의 작업 내용을 어떻게 공유하고 차단할 지 결정하는 레벨

# 5.1 트랜잭션
## 5.1.1 MySQL에서의 트랜잭션
MyISAM 테이블과 InnoDB에 데이터를 삽입하는 과정을 생각해보자.

```
CREATE TABLE tab_myisam( fdpk INT NOT NULL, PRIMARY KEY (fdpk)) ENGINE=MyISAM;
INSERT INTO tab_myisam(fdpk) VALUES (3);

CREATE TABLE tab_innodb( fdpk INT NOT NULL, PRIMARY KEY (fdpk)) ENGINE=INNODB;
INSERT INTO tab_innodb(fdpk) VALUES (3);

SET autocommit=ON;

INSERT INTO tab_myisam(fdpk) VALUES (1), (2), (3);
INSERT INTO tab_innodb(fdpk) VALUES (1), (2), (3);
```

두 테이블 모두 '3'을 삽입할 때 키 중복 오류가 발생한다.
그런데 삽입 결과를 보면, MyISAM 테이블은 1, 2, 3이 들어있는 반면 InnoDB 테이블은 최초 삽입했던 3만 들어있다.
MyISAM 테이블은 부분 업데이트가 발생하여, 데이터 정합성 확보가 어려워진 반면 InnoDB 테이블은 오류가 발생하기 전 상태 그대로 복구하였다.

## 5.1.2 주의사항
프로그램 코드에서 트랜잭션의 범위를 최소화해야 한다.
예를 들어,
1. 로그인 여부 확인, 내용 검증 로직, 파일 확인 등 커넥션과 관련이 적은 코드들
2. DB에서 조회
3. FTP 파일 전송 작업 또는 네트워크를 통한 원격 서버 작업 등
과 같은 부분은 트랜잭션에서 제거하는 것이 좋다.
DB 커넥션의 개수는 제한적이므로, 각 단위 프로그램이 점유하는 시간이 길어질수록 사용 가능한 여유 커넥션의 수는 줄어든다. 이게 반복되면 커넥션 점유를 위해 대기하는 경우도 발생할 수 있다.

# 5.2 MySQL 엔진의 잠금
스토리지 엔진 레벨의 잠금은 각 스토리지 엔진에 영향을 끼치지 않지만, MySQL 엔진 레벨의 잠금은 모든 스토리지 엔진에 영향을 끼친다.
## 5.2.1 글로벌 락
```
FLUSH TABLES WITH READ LOCK
```
- MySQL에서 제공하는 잠금 중 제일 넓은 범위의 잠금
- 한 세션에서 글로벌 락을 획득하면 다른 세션에서 SELECT를 제외한 대부분의 DDL, DML을 실행하는 경우 글로벌 락이 해제될 때까지 대기 상태로 남는다.
- MySQL 서버 전체에 영향을 미치며, 작업 대상 테이블 또는 데이터베이스가 다르더라도 동일하게 영향을 미친다.
- 여러 DB에 존재하는 MyISAM이나 MEMORY 테이블에 대해 mysqldump로 일관된 백업이 필요하다면 글로벌 락을 사용해야 한다.
---
### 주의할 점
- `FLUSH TABLES WITH READ LOCK` 명령이 실행되기 전 쓰기 잠금이 걸려있다면 이전에 실행되고 있던 쿼리가 완료되어야 하므로, 대기가 발생할 수 있다.
- `mysqldump`와 같은 백업 프로그램 실행 시 `FLUSH TABLES WITH READ LOCK`을 내부적으로 실행할 수도 있으므로, 사용하는 옵션에 따라 어떤 잠금을 거는 지 확인해보아야 한다.
---
- 다만 InnoDB는 트랜잭션을 지원하므로 일관된 데이터 상태를 위해 모든 데이터 변경 작업을 멈출 필요는 없다.
- MySQL 8.0부터는 Xtrabackup, Enterprise Backup 같은 백업 툴의 안정적 실행을 위해 백업락이 도입됐다.
```
LOCK INSTANCE FOR BACKUP;
UNLOCK INSTANCE;
```

- 특정 세션에서 백업 락을 획득하면 모든 세션에서 다음 내용들을 변경할 수 없다.
	- DB 및 테이블 . 등모든 객체 생성 및 변경, 삭제
	- REPAIR TABLE과 OPTIMIZE TABLE 명령
	- 사용자 관리 및 비밀번호 변경
- 그러나 백업 락은 일반적인 테이블 데이터 변경은 허용된다.
	- MySQL 서버는 소스 서버와 레플리카 서버로 구성된다.
	- 주로 백업은 레플리카에서 실행된다.
	- `FLUSH TABLES WITH READ LOCK` 명령으로 글로벌 락을 획득하면 복제는 백업 시간만큼 지연된다. 백업 중에 소스 서버에 문제가 생기면 레플리카 서버 데이터가 최신이 될 때까지 서비스를 정지해야 할 수도 있다.
	- XtraBackup이나 Enterprise Backup 툴들은 모두 복제 중에 일관된 백업을 만들 수 있지만, 도중에 스키마가 변경되면 백업은 실패한다.
	- 이것을 방지하기 위해 백업 락이 도입되었으며, 복제 실행 중 DDL 실행 시 복제를 일시 중지하는 역할을 한다.

## 5.2.2 테이블 락
- 개별 테이블 단위로 설정되는 잠금
- MyISAM, InnoDB 사용하는 테이블은 모두 가능
- 명시적, 묵시적으로 특정 테이블의 락을 획득한다.

### 명시적 획득
- `LOCK TABLES table_name [ READ | WRITE ]`
- `UNLOCK TABLES` 명령으로 잠금 반납
- 특별한 상황이 아니면 애플리케이션에서 사용할 일이 거의 없다. 글로벌 락처럼 온라인 작업에 상당한 영향을 미친다.
### 묵시적 획득
- MyISAM이나 MEMORY 테이블에 데이터를 변경하는 쿼리를 실행하면 발생
	- 쿼리가 실행되는 동안 자동으로 획득했다가 쿼리 완료 후 자동 해제된다.
	- InnoDB 테이블은 스토리지 엔진 자체에서 레코드 기반 잠금을 제공하기에 단순 데이터 변경 쿼리로 묵시적 테이블 락이 설정되지 않는다. 정확히는 대부분의 DML에선 무시되고 DDL에선 영향이 있다.

## 5.2.3 네임드 락
- `GET_LOCK()` 함수로 임의의 문자열에 대해 잠금을 설정한다.
- 잠금의 대상은 테이블, 레코드 같은 DB 객체가 아니라 사용자가 지정한 문자열이다.
- 자주 사용되지는 않는다.
```
-- 'mylock' 문자열에 잠금을 획득한다. 이미 잠금 중이면 2초만 대기한다.(2초 이후 자동 잠금 해제)
SELECT GET_LOCK('mylock', 2);

-- 잠금이 설정되어 있는지 확인한다.
SELECT IS_FREE_LOCK('mylock');

-- 획득했던 잠금을 반납한다.
SELECT RELEASE_LOCK('mylock');

-- 모두 정상적으로 락을 획득하거나 해제하면 1, 아니면 NULL이나 0을 반환한다.
```
- 많은 레코드를 복잡한 조건으로 변경하는 트랜잭션에 유용하게 쓸 수 있다.(e.g. 데드락 발생하기 쉬운 배치 프로그램 등)
- 네임드 락을 중첩해서 사용할 수도 있다. 또한 현 세션에서 획득한 네임드 락을 한 번에 모두 해제할 수도 있다. `SELECT RELEASE_ALL_LOCKS();`

## 5.2.4 메타데이터 락
- 데이터베이스 객체(테이블, 뷰 등)의 이름이나 구조를 변경할 때 획득
- 명시적으로 획득, 해제할 수 없으며 `RENAME TABLE tab_a TO tab_b`같이 변경하는 경우 자동으로 획득한다.
- `RENAME TABLE`은 원본 이름과 변경될 이름에 모두 한꺼번에 잠금을 설정한다.
- 테이블 구조를 변경해야 할 때, 새 테이블을 만들고 테이블 쓰기 락을 설정한 뒤 데이터를 복사한다. 이후 `RENAME` 명령으로 테이블명을 바꿔 구조를 변경하는 방식으로 사용할 수도 있다.

# 5.3 InnoDB 스토리지 엔진 잠금
- InnoDB는 MySQL에서 제공하는 잠금과 별개로 엔진 내부에서 레코드 기반 잠금 방식을 탑재하고 있다.
- 이는 MyISAM보다 훨씬 뛰어난 동시성 처리를 제공할 수 있지만, 이원화된 잠금 처리 때문에 MySQL 명령을 이용해 접근하기 어렵다.
- 예전 버전에는 InnoDB의 잠금 정보를 보기 위해 `lock_monitor`와 `SHOW ENGINE INNODB STATUS`를 사용하는게 전부였으며 그 결과도 이해하기 어려웠다.
- 최근에는 트랜잭션과 잠금, 잠금 대기 중인 트랜잭션 목록을 조회할 수 있게 되었다.
- MySQL 서버의 `information_schema` 데이터베이스의 `INNODB_TRX, INNODB_LOCKS, INNODB_LOCK_WAITS` 테이블을 조인하여 조회하면 현재 트랜잭션들의 상태를 확인할 수 있다.
- 또한 `Performance Schema`를 이용해 InnoDB 내부의 세마포어(내부 잠금) 모니터링 방법도 추가되었다.
## 5.3.1 InnoDB 스토리지 엔진의 잠금
- 레코드 기반 잠금 제공, 잠금 정보는 상당히 작은 공간으로 제공되어 락이 레벨업되는 경우(락 에스컬레이션)는 없다.
- 레코드 사이 간격을 잠그는 갭(GAP)락을 지원
### 5.3.1.1 레코드 락
- 레코드 자체만을 잠그는 락
- InnoDB 스토리지 엔진의 레코드 락은 레코드 자체가 아니라 인덱스의 레코드를 잠근다.
- 인덱스가 하나도 없어도 내부적으로 자동 생성된 클러스터 인덱스를 이용해 잠금을 설정한다.
- 보조 인덱스를 이용한 변경 작업은 넥스트 키 락이나 갭 락을 사용하지만, PK 또는 유니크 인덱스에 의한 변경 작업에서는 레코드 자체에만 락을 건다.

### 5.3.1.2 갭 락
- 레코드 자체가 아닌 레코드와 바로 인접한 레코드 사이 간격을 잠그는 락
- 레코드 사이 간격에 새로운 레코드가 생성(INSERT)되는 것을 제어한다.
- 넥스트 키 락의 일부로 자주 사용된다.

### 5.3.1.3 넥스트 키 락
- 레코드 락과 갭 락을 합쳐 놓은 형태
- STATEMENT 포맷의 바이너리 로그를 사용하는 MySQL 서버는 REPEATABLE READ 격리 수준을 이용해야 한다.
- `innodb_locks_unsafe_for_binlog` 시스템 변수가 비활성되면(0으로 설정) 변경을 위해 검색하는 레코드에는 넥스트 키 락 방식으로 잠금이 걸린다.
- InnoDB의 갭 락이나 넥스트 키 락은 바이너리 로그에 기록되는 쿼리가 레플리카 서버에서 실행될 때 소스 서버에서 만들어낸 결과와 동일하게 만들어내도록 보장하는 것이 주 목적이다.
- 그런데 넥스트 키 락과 갭 락으로 인해 데드락이나 트랜잭션의 대기가 자주 발생하므로, 가능하다면 바이너리 로그 포맷을 ROW 형태로 바꿔 넥스트 키 락이나 갭 락을 줄이는 게 좋다.
- 8.0 버전부터는 ROW 포맷의 바이너리 로그가 기본 설정이다.

### 5.3.1.4 자동 증가 락
- AUTO_INCREMENT 칼럼이 사용된 테이블에 동시에 여러 레코드가 INSERT될 때, 내부적으로 테이블 수준의 잠금을 사용한다.
- INSERT와 REPLACE처럼 새 레코드를 저장하는 쿼리에서만 필요하다.
- InnoDB의 다른 락과 달리 트랜잭션과 관계없이 AUTO_INCREMENT 값을 가져오는 순간만 락을 걸었다가 해제한다.
- AUTO_INCREMENT 락은 테이블에 단 하나만 존재하기에 여러 INSERT 쿼리가 동시에 실행될 경우 대기가 필요하다.
- AUTO_INCREMENT 칼럼에 명시적으로 값을 주어도 자동 증가 락을 사용한다.
- 명시적으로 획득, 해제하는 법은 없다. 또한 사용 시간이 짧아서 대부분은 문제되지 않는다.
- 5.1 버전 이후부터는 `innodb_autoinc_lock_mode`라는 시스템 변수로 작동 방식을 변경할 수 있다.
	- 시스템 변수 = 0
		- 5.0과 동일한 방식으로 모든 INSERT가 자동 증가 락을 쓴다.
	- 시스템 변수 = 1
		- 한 건 또는 여러 건의 레코드를 INSERT하는 쿼리 중 MySQL 서버가 정확한 레코드의 건수를 예측할 수 있을 때 자동 증가락을 사용하지 않고 래치(뮤텍스)를 이용한다.
		- 자동 증가 락보다 더 빠른 시간 동안 잠금을 걸고, 필요한 값을 가져오면 해제된다.
		- 그러나 INSERT ... SELECT 처럼 MySQL 서버가 쿼리 실행 전에 건수를 예측하기 어려울 땐 변수 값 = 0과 같이 자동 증가 락을 쓴다.
		- INSERT 문장이 완료될 때까지 락을 점유한다.
		- 대량 INSERT 실행 시 여러 자동 증가 값을 한 번에 할당받아와 값의 누락을 방지한다. 그러나 한 번 할당된 값 중 사용하지 않은 값이 있다면 이후 INSERT에서 값의 누락이 발생할 수 있다.
		- 이 설정으로 최소 1개의 INSERT 문장으로 INSERT되는 레코드는 연속된 자동 증가 값을 가지게 되며, 연속 모드라고도 한다.
	- 시스템 변수 = 2
		- InnoDB 스토리지 엔진은 절대 자동 증가 락을 안 걸고 경량화된 래치(뮤텍스)를 사용한다.
		- 그러나 이 설정에서는 하나의 INSERT 문장으로 INSERT되는 레코드라고 해도 연속된 자동 증가 값을 보장하지 않는다.
		- 인터리빙 모드라고도 하며, 대량 INSERT문의 실행 중에도 다른 커넥션에서 INSERT를 사용할 수 있어 동시 처리 성능이 높다.
		- 그러나 이 설정에서의 자동 증가 기능은 유니크 값이 생성되는 것만 보장한다.
		- STATEMENT 포맷 바이너리 로그를 쓰는 복제에서는 소스와 레플리카의 자동 증가 값이 달라질 수도 있기에 주의해야 한다.
	- 추가적인 내용은 공식문서 확인
	- 5.7까지는 시스템 변수 기본값이 1이었지만 8.0부터는 2다. STATEMENT에서 ROW 포맷으로 바이너리 로그 포맷이 변경되었기 때문. STATEMENT를 쓸거면 1로 바꿔라.
- AUTO_INCREMENT 락을 최소화하기 위해, 자동 증가 값이 한 번 증가하면 쿼리가 실패했더라도 절대 줄어들지 않는다.

## 5.3.2 인덱스와 잠금
- InnoDB의 잠금은 레코드를 잠그는 것이 아니라 인덱스를 잠그는 방식
- 변경해야 할 레코드를 찾기 위해 검색한 인덱스의 레코드 모두를 락 걸어야 한다.
- 검색을 위한 적절한 인덱스가 준비되어 있지 않다면 각 클라이언트 간의 동시성이 떨어진다.
- 인덱스가 아예 없다면 처음부터 끝까지 테이블 풀 스캔이 필요

## 5.3.3 레코드 수준의 잠금 확인 및 해제

# 5.4 MySQL의 격리 수준
|                  | DIRTY READ | NON-REPEATABLE READ | PHANTOM READ   |
| ---------------- | ---------- | ------------------- | -------------- |
| READ UNCOMMITTED | 발생         | 발생                  | 발생             |
| READ COMMITTED   | 없음         | 발생                  | 발생             |
| REPEATBLE READ   | 없음         | 없음                  | 발생(InnoDB는 없음) |
| SERIALIZABLE     | 없음         | 없음                  | 없음             |
- READ UNCOMMITTED는 일반적인 DB에서 거의 사용되지 않는다.(READ COMMITTED나 REPEATABLE READ 사용(전자는 오라클에서, 후자는 MySQL에서 주로 사용))
- 격리수준이 올라갈수록 동시처리 성능은 떨어진다. 근데 SERIALIZABLE 정도가 아니라면 크게 성능 개선이나 저하는 발생하지 않는다.

## 5.4.1 READ UNCOMMITTED
- 사용자 A가 테이블에 INSERT 했을 때, 커밋하지 않았음에도 불구하고 다른 사용자가 A가 INSERT한 데이터를 조회할 수 있다.
- A가 그 데이터를 롤백해도 다른 사용자들은 그 데이터를 정상이라고 생각할 것이다.
- 즉, 어떤 트랜잭션에서 처리한 작업이 끝나지 않았음에도 다른 트랜잭션에서 볼 수 있는 현상을 Dirty Read라고 한다.
- RDBMS 표준에서 격리 수준으로 인정하지 않을 정도로 정합성에 문제가 많다.

## 5.4.2 READ COMMITTED
- 오라클 DBMS에서 기본으로 사용, 온라인 서비스에서 가장 많이 선택됨
- 다른 트랜잭션이 커밋한 데이터만 조회할 수 있기에 Dirty Read가 발생하지 않음
- 어떤 트랜잭션이 UPDATE를 진행하고 커밋하지 않았을 때, UPDATE하기 이전 값은 언두 로그로 복사된다. 그리고 다른 트랜잭션이 그 데이터를 조회하려고 하면 언두 로그에 기록된 값을 반환한다.
- Non-Repeatable Read : 한 트랜잭션 내부에서 같은 데이터를 반복적으로 조회할 때 동일한 결과를 보여줘야 하지만, 다른 트랜잭션의 작업으로 인해 동일한 결과를 보여주지 못하는 것.

## 5.4.3 REPEATABLE READ
- InnoDB에서 기본으로 사용
- 트랜잭션 롤백 가능성에 대비해 변경 전 레코드를 언두 로그에 백업해두고 실제 레코드값을 변경(MVCC 참고)
- 실행 중인 트랜잭션 가운데 가장 오래된 트랜잭션 번호보다 트랜잭션 번호가 앞선 언두 로그의 데이터를 삭제할 수 없음
- Phantom Read : 트랜잭션이 동일한 쿼리를 두 번 실행할 때, 중간에 다른 트랜잭션이 데이터의 삽입이나 삭제를 통해 결과 집합에 영향을 주어 두 번의 쿼리 결과가 달라지는 상황

## 5.4.4 SERIALIZABLE
- 가장 단순하면서 가장 엄격한 격리 수준
- 동시 처리 성능도 다른 격리 수준보다 떨어진다.
- InnoDB의 기본적인 SELECT 작업은 아무 레코드 잠금 없이 실행된다.(Non-Locking Consistent Read)
- 그러나 SERIALIZABLE에서는 읽기 작업도 공유 잠금(읽기 잠금)을 획득해야 하며 동시에 다른 트랜잭션은 그 레코드를 변경할 수 없다.
- InnoDB에서는 갭 락과 넥스트 키 락이 있기 때문에 REPEATABLE READ에서도 PHANTOM READ가 발생할 확률이 적기에, 굳이 SERIALIZABLE까진 필요하지 않다.
