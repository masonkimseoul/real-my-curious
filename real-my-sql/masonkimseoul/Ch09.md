# 9장 옵티마이저와 힌트
- `EXPLAIN` 명령으로 쿼리 실행 계획을 확인할 수 있다.

# 9.1 개요

- 옵티마이저는 실행계획을 수립한다.

## 9.1.1 쿼리 실행 절차

- 쿼리 실행 과정은 크게 세 단계로 나눌 수 있다.
    1. 사용자로부터 요청된 SQL 문장을 잘게 쪼개서 MySQL 서버가 이해할 수 있는 수준으로 분리(파스 트리)한다.
    2. SQL의 파싱 정보(파스 트리)를 확인하면서 어떤 테이블부터 읽고 어떤 인덱스를 이용해 테이블을 읽을지 선택한다.
    3. 두 번째 단계에서 결정된 테이블의 읽기 순서나 선택된 인덱스를 이용해 스토리지 엔진으로부터 데이터를 가져온다.
- 1단계를 `SQL 파싱` 이라고 한다. MySQL 서버의 SQL 파서 모듈로 파싱을 진행한다. 문법적으로 잘못된 문장은 이 단계에서 걸러진다. 이 단계에서 `SQL 파스 트리` 를 만든다. 파스 트리를 이용하여 쿼리를 실행한다.

- 2단계는 1단계에서 만든 SQL 파스 트리를 참조하며 다음 내용을 처리한다.
    - 불필요한 조건 제거 및 복잡한 연산의 단순화
    - 여러 테이블의 조인이 있는 경우 어떤 순서로 테이블을 읽을지 결정
    - 각 테이블에 사용된 조건과 인덱스 통계 정보를 이용해 사용할 인덱스를 결정
    - 가져온 레코드들을 임시 테이블에 넣고 다시 한 번 가공해야 하는지 결정
    - 그 외…
- 2단계는 `최적화 및 실행 계획 수립` 단계이며, 옵티마이저에서 처리한다. 이 단계가 완료되면 실행계획이 만들어진다.
- 3단계는 수립된 실행 계획대로 스토리지 엔진에 레코드를 읽어오도록 요청하며, 읽어온 레코드를 조인하거나 정렬한다.
- 1, 2단계는 거의 MySQL 엔진에서 처리하며, 3단계는 MySQL 엔진과 스토리지 엔진이 동시에 참여해 처리한다.

## 9.1.2 옵티마이저의 종류

- 옵티마이저는 DB에서 두뇌 같은 역할을 담당한다.
- 크게 규칙 기반 최적화 방법(Rule-based optimizer, RBO), 비용 기반 최적화 방법(Cost-based optimizer, CBO)으로 나눌 수 있다.

### 규칙 기반 최적화

- 레코드 건수, 선택도 등을 고려하지 않고 옵티마이저에 내장된 우선순위에 따라 실행 계획을 수립하는 방식
- 통계 정보(테이블 레코드 건수, 칼럼값 분포도)를 조사하지 않고 실행 계획이 수립한다. 그래서 같은 쿼리에 대해 거의 항상 같은 실행 방법을 만든다.
- 사용자 데이터의 분포도는 매우 다양하기에, 이 방법은 Deprecated된 방법이다. 안 쓴다.
- 옛날에 CPU가 느려 비용 산출 과정이 부담스러워서 사용하던 방법

### 비용 기반 최적화

- 쿼리를 처리하기 위한 여러 가능한 방법을 만들고, 각 단위 작업의 비용(부하) 정보와 대상 테이블의 예측된 통계 정보를 이용해 실행 계획별 비용을 산출한다.
- 실행 방법들 중 비용이 최소로 소요되는 처리 방식을 선택한다.

# 9.2 기본 데이터 처리

## 9.2.1 풀 테이블 스캔과 풀 인덱스 스캔

- 옵티마이저는 다음 조건일 때 풀 테이블 스캔을 사용한다.
    - 테이블 레코드 건수가 너무 작아 인덱스를 통해 읽는 것보다 풀 테이블 스캔을 하는 편이 더 빠른 경우
        - 일반적으로 테이블이 페이지 1개로 구성될 경우
    - WHERE 절이나 ON 절에 인덱스를 이용할만한 적절한 조건이 없는 경우
    - 인덱스 레인지 스캔을 사용할 수 있는 쿼리이지만 옵티마이저가 판단한 조건 일치 레코드 건수가 너무 많은 경우
        - 인덱스의 B-Tree를 샘플링하여 조사한 통계 정보 기준
- 대부분의 DBMS는 풀 테이블 스캔 시 한 번에 여러 페이지를 읽어올 수 있다. 그런데 MySQL에는 풀 테이블 스캔 시 한 번에 몇 개씩 페이지를 읽어올지 설정하는 시스템 변수가 없다.
- 그래서 MyISAM인 경우 한 번에 한 페이지씩 읽어오지만, InnoDB는 백그라운드 스레드에 의해 리드 어헤드 작업이 자동으로 시작된다.
    - 리드 어헤드 : 어떤 영역의 데이터가 필요할 지 예측하여 요청 오기 전에 읽어와 InnoDB 버퍼 풀에 두는 것.
- 풀 테이블 스캔 시 처음 몇 데이터 페이지는 포그라운드 스레드가 읽지만, 특정 시점 이후부턴 백그라운드 스레드가 작업한다.
    - 백그라운드 스레드는 그 시점부터 한 번에 4개 or 8개씩 읽어온다.
    - 읽어올수록 그 수가 점점 증가하여 한 번에 최대 64개 페이지를 읽어와 버퍼 풀에 저장한다.
    - 그럼 포그라운드 스레드는 읽어온 것을 가져다가 사용하면 끝
- `innodb_read_ahead_threshold` 시스템 변수로 InnoDB가 언제 리드 어헤드를 시작할 지 임계점을 정할 수 있다.
    - 일반적인 상황은 default 값도 충분하지만 데이터 웨어하우스용이라면 더 빠르게 리드 어헤드가 실행되도록 해도 좋다.
- 리드 어헤드는 풀 인덱스 스캔에서도 동일하게 사용된다.

## 9.2.2 병렬 처리

- 하나의 쿼리를 여러 스레드가 동시에 처리할 수 있다.
    - `innodb_parallel_read_threads` 시스템 변수로 최대 몇 개 스레드가 동시에 처리할 지 변경 가능
- 아직 MySQL 서버는 쿼리를 여러 개의 스레드를 이용해 병렬로 처리하게 하는 힌트나 옵션은 없다.
    - 8.0에서는 아무런 WHERE 없이 레코드 전체 건수만 가져오는 쿼리만 병렬로 처리할 수 있다.

```sql
SET SESSION innodb_parallel_read_threads=8;
SELECT COUNT(*) FROM salaries;
```

## 9.2.3 ORDER BY 처리(Using Filesort)

- 정렬을 처리하는 방법은 인덱스를 이용하는 방법, Filesort를 이용하는 방법이 있다.

|  | 장점 | 단점 |
| --- | --- | --- |
| 인덱스 이용 | INSERT, UPDATE, DELETE 쿼리가 실행될 때 이미 인덱스가 정렬되어 있어 순서대로 읽기만 하면 되므로 매우 빠르다. | INSERT, UPDATE, DELETE 작업 시 부가적인 인덱스 추가/삭제 작업이 필요하므로 느리다.
인덱스 때문에 디스크 공간이 더 많이 필요하다.
인덱스의 개수가 늘어날수록 InnoDB의 버퍼 풀을 위한 메모리가 많이 필요하다. |
| Filesort 이용 | 인덱스를 생성하지 않아도 되므로 인덱스를 이용할 때의 단점이 장점으로 바뀐다.
정렬해야 할 레코드가 많지 않다면 메모리에서 Filesort가 처리되므로 충분히 빠르다. | 정렬 작업이 쿼리 실행 시 처리되므로 레코드 대상 건수가 많아질수록 쿼리의 응답 속도가 느리다. |
- 항상 Filesort를 거쳐서 레코드를 정렬하는 건 아니지만, 다음과 같은 경우는 인덱스로 정렬하는 것이 불가하다.
    - 정렬 기준이 너무 많아 요건별로 모두 인덱스를 생성하는 것이 불가능한 경우
    - GROUP BY의 결과 또는 DISTINCT 같은 처리의 결과를 정렬해야 하는 경우
    - UNION의 결과와 같이 임시 테이블의 결과를 다시 정렬해야 하는 경우
    - 랜덤하게 결과 레코드를 가져와야 하는 경우
- 실행 계획의 Extra 칼럼에서 “Using filesort”라고 적혀있으면 인덱스를 사용하지 않고 정렬한 것이다.

### 9.2.3.1 소트 버퍼

- MySQL이 정렬을 수행하기 위해 할당받은 별도의 메모리 공간
- 정렬이 필요한 경우만 할당되며 크기는 정렬할 레코드의 크기에 따라 가변적으로 변한다.
    - 최대 사용 가능한 소트 버퍼 공간 : `sort_buffer_size` 시스템 변수
- 만약 정렬해야 할 레코드 건수가 소트 버퍼로 할당된 공간보다 크면?
    - 멀티 머지(Multi-merge) - 먼저 소트 버퍼에서 정렬을 하고 그 결과를 임시로 디스크에 기록한다. 이 작업을 반복적으로 수행 후 버퍼 크기만큼 정렬된 레코드를 다시 병합하며 정렬한다.
        - 멀티 머지가 수행된 횟수는 `Sort_merge_passes` 라는 상태 변수에 누적해서 집계된다.
    - 레코드가 많을수록 디스크 I/O 횟수가 많아진다.
    - 소트 버퍼가 커져도 의미 있는 성능 차이는 없다.
    - 보통 256KB ~ 8MB에서 최적인듯, 너무 커지면 오히려 성능이 떨어질수도…
- 소트 버퍼는 여러 클라이언트가 공유하여 사용할 수 없다.
    - 그래서 커넥션이 많으면 많을수록, 정렬 작업이 많으면 많을수록 소트 버퍼로 소비되는 메모리 공간은 커진다.
    - 소트 버퍼 크기가 커지면 커넥션마다 소트 버퍼가 생기니 OOM 에러가 발생할 수 있고, OOM-Killer가 MySQL 서버를 죽일 것이다.

### 9.2.3.2 정렬 알고리즘

- 정렬 시 레코드 전체를 소트 버퍼에 담을 지, 정렬 기준 칼럼만 소트 버퍼에 담을지에 따라 싱글 패스, 투 패스로 나눌 수 있다.(공식 명칭은 아님)
    - 옵티마이저 트레이스 기능으로 확인할 수 있다.

```sql
SET OPTIMIZER_TRACE="enabled=on", END_MARKERS_IN_JSON=on;
SET OPTIMIZER_TRACE_MAX_MEM_SIZE=100000;
```
