# Chapter 04 아키텍처
# 4.1 MySQL 엔진 아키텍처
## 4.1.1 MySQL의 전체 구조
일반 상용 RDBMS와 같이 대부분의 프로그래밍 언어로부터 접근 방법을 모두 지원한다.

MySQL 서버는 크게 사람의 머리 역할인 MySQL 엔진과 손발 역할을 하는 스토리지 엔진으로 구분할 수 있다.
스토리지 엔진은 핸들러 API를 만족하도록 구현하면 얼마든지 추가할 수 있다.

### 4.1.1.1 MySQL 엔진
커넥션 핸들러 - 클라이언트로부터의 접속, 쿼리 요청을 처리
SQL파서 및 전처리기
옵티마이저 - 쿼리의 최적화된 실행

표준 SQL문법을 지원하기에 타 DBMS와 호환되어 사용 가능하다.

### 4.1.1.2 스토리지 엔진
디스크 스토리지에 실 데이터를  I/O하는 부분을 전담한다.
MySQL 엔진은 MySQL 서버에 1개 뿐이지만 스토리지 엔진은 여러 개를 동시에 사용할 수 있다.
테이블이 사용할 스토리지 엔진을 지정하면 그 테이블의 모든 I/O 작업은 그 스토리지 엔진이 처리한다.
```
CREATE TABLE test_table (fd1 INT, fd2 INT) ENGINE=INNODB;
```
각 스토리지 엔진은 성능 항상을 위해 키 캐시(MyISAM 스토리지 엔진)나 InnoDB 버퍼 풀(InnoDB 스토리지 엔진)과 같은 기능을 내장하고 있다.

### 4.1.1.3 핸들러 API
핸들러 요청 - MySQL 엔진의 쿼리 실행기에서 스토리지 엔진에 데이터 I/O 작업을 요청하는 것을 의미한다.
핸들러 API는 이 요청에 사용하는 API이다.
```
SHOW GLOBAL STATUS LIKE 'Handler%';
```
위 명령으로 핸들러 API를 통해 얼마나 많은 데이터 작업이 있었는지 확인할 수 있다.

## 4.1.2 MySQL 스레딩 구조

MySQL 서버는 프로세스 기반이 아닌 스레드 기반으로 작동하며, 크게 포그라운드(Foreground) 스레드와 백그라운드(Background) 스레드로 구분할 수 있다. 백그라운드 스레드의 개수는 MySQL서버 설정 내용에 따라 가변적일 수 있으며, 동일한 이름의 스레드가 2개 이상씩 보이는 것은 MySQL 서버의 설정에 의해 여러 스레드가 동일 작업을 병렬로 처리하는 경우이다.

### 4.1.2.1 포그라운드 스레드(클라이언트 스레드)
- 최소 MySQL 서버에 접속된 클라이언트 수만큼 존재하며, 주로 각 클라이언트 사용자가 요청하는 쿼리 문장을 처리한다.

- 이 스레드는 클라이언트 사용자가 작업을 마치고 커넥션을 종료할 때 스레드 캐시(Thread Cache)로 돌아간다.
- 스레드 캐시는 일정 개수 이상의 대기 중인 스레드가 있으면, 돌아오는 스레드를 캐시에 넣지 않고 종료시켜 일정 개수의 스레드만 캐시에 존재하도록 한다. 유지 가능한 최대 스레드 개수는 thread_cache_size 시스템 변수로 설정한다.

- 이 스레드는 데이터를 MySQL의 데이터 버퍼나 캐시로부터 가져온다.
- 버퍼나 캐시에 존재하지 않으면 직접 디스크의 데이터나 인덱스 파일에서 데이터를 읽어온다.
- MyISAM 테이블은 디스크 쓰기 작업까지 포그라운드 스레드가 처리하지만, InnoDB의 경우 데이터 버퍼나 캐시까지만 포그라운드 스레드가 처리하고, 나머지 버퍼로부터 디스크까지의 기록은 백그라운드 스레드가 처리한다.

### 4.1.2.2 백그라운드 스레드
- InnoDB는 다음 작업을 백그라운드로 처리한다.
	- 인서트 버퍼(Insert Buffer)를 병합하는 스레드
	- 로그를 디스크로 기록하는 스레드
	- InnoDB 버퍼 풀의 데이터를 디스크에 기록하는 스레드
	- 데이터를 버퍼로 읽어 오는 스레드
	- 잠금이나 데드락을 모니터링하는 스레드

- 이 중 로그 스레드(Log thread)와 쓰기 스레드(Write thread, 버퍼 데이터를 디스크로 내려쓴다)가 제일 중요하다고 할 수 있다.
- MySQL 5.5부터 데이터 쓰기 스레드와 읽기 스레드를 2개 이상 지정할 수 있으며, `innodb_write_io_threads`와 `innodb_read_id_threads` 시스템 변수로 스레드 개수를 설정할 수 있다.
- InnoDB에서 데이터 읽기 작업은 주로 클라이언트 스레드에서 처리되기 때문에 읽기 스레드는 많이 설정할 필요가 없다.
- 다만 쓰기 스레드는 많은 작업을 백그라운드 스레드로 처리하기에, 적절히 설정하는게 중요하다.(일반 내장 디스크 사용 시 2~4, DAS, SAN 같은 스토리지 사용 시 디스크를 최적으로 사용할 만큼 충분히)
- 사용자 요청 처리 중 쓰기는 지연되어 처리할 수 있지만 읽기는 절대 지연될 수 없다.
- 그러므로 일반 DBMS는 대부분 쓰기를 버퍼링하여 일괄 처리하는 기능이 있다. InnoDB 또한 그렇다.
- MyISAM은 그렇지 않고 클라이언트 스레드가 쓰기 작업까지 함께 처리한다. 그러므로 쓰기 버퍼링 기능을 사용할 수 없다.

## 4.1.3 메모리 할당 및 사용 구조
- 글로벌 메모리 영역
	- InnoDB 버퍼 풀
	- MyISAM 키 캐시
	- 바이너리 로그 버퍼
	- 리두 로그 버퍼
	- 테이블 캐시
- 세션(커넥션) 메모리 영역
	- 조인 버퍼
	- 정렬(Sort) 버퍼
	- 네트워크 버퍼
	- 리드 버퍼

- 크게 글로벌 메모리 영역, 로컬 메모리 영역으로 구분할 수 있다.

### 4.1.3.1 글로벌 메모리 영역
- 클라이언트 스레드 수와 무관하게 하나의 메모리 공간만 할당된다. 필요에 따라 2개 이상을 할당받을 수도 있다.
- 생성된 글로벌 메모리 영역이 N개여도 모든 스레드에 의해 공유된다.
- 모든 메모리 공간은 MySQL 서버가 시작되며 OS로부터 할당된다. 정확히 그 양을 측정하기 어렵지만, 단순히 MySQL의 시스템 변수로 설정된 만큼 할당받는다고 생각하면 된다.

### 4.1.3.2 로컬 메모리 영역
- 세션 메모리 영역이라고도 한다.
- MySQL 서버상 존재하는 클라이언트 스레드가 쿼리를 처리하는데 사용한다.
- 클라이언트가 MySQL 서버에 접속하면 클라이언트 커넥션의 요청을 처리하기 위해 스레드를 하나씩 할당한다. 그래서 클라이언트 메모리 영역이라고도 한다.
- 로컬 메모리는 각 클라이언트 스레드별로 독립적으로 할당되며, 절대 공유되지 않는다.
- 로컬 메모리 영역의 크기도 글로벌 메모리 영역처럼 주의해서 할당하는게 중요하다.
- 쿼리의 용도별로 필요할 때만 공간이 할당되고, 필요하지 않을땐 MySQL이 메모리 공간 할당조차 안할 수도 있다.
- 커넥션 버퍼나 결과 버퍼와 같이, 커넥션이 열려있는 동안 계속 할당된 상태로 남아 있는 공간도 있다.
- 소트 버퍼나 조인 버퍼와 같이, 쿼리를 실행하는 순간에만 할당했다가 해제하는 공간도 있다.

## 4.1.4 플러그인 스토리지 엔진 모델

- 핸들러 - 어떤 기능을 호출하기 위해 사용하는 운전대와 같은 역할을 하는 객체
- MySQL 서버에서 MySQL 엔진은 사람 역할, 각 스토리지 엔진은 자동차 역할이라면, MySQL 엔진이 스토리지 엔진을 조작하기 위해 핸들러를 사용한다. 즉, 스토리지 엔진이 데이터를 읽거나 쓰도록 명령하려면 핸들러를 반드시 거쳐야 한다.
- 그래서 `Handler_`로 시작하는 상태 변수는 MySQL 엔진이 각 스토리지 엔진에게 보낸 명령의 횟수를 의미하는 변수로 이해할 수 있음
- MySQL에서 MyISAM이나 InnoDB와 같이 다른 스토리지 엔진을 사용하는 테이블에 대해 쿼리를 실행해도 MySQL의 처리내용은 대부분 동일하며, 단순히 데이터 읽기/쓰기 영역의 처리만 차이가 있다.
- 여러 스토리지 엔진 중 뭘 써도 별 차이 없다고 생각할 수 있지만, `데이터 읽기/쓰기` 작업 처리 방식이 얼마나 달라질 수 있는지에 달려있다.
- 즉, 각 단위 작업이 MySQL 엔진의 영역인지, 스토리지 엔진의 영역인지 구분할 수 있겠다.

```
SHOW ENGINES;
```
```
 -- 결과
 Engine / Support / Comment / Transactions / XA / Savepoints
```

- Support 칼럼에 표시될 수 있는 값
	- YES : MySQL 서버에 해당 스토리지 엔진이 포함되어 있으며 사용 가능으로 활성화된 상태
	- DEFAULT : `YES`와 동일한 상태이지만 필수 스토리지 엔진임을 의미한다. 만약 없으면 MySQL은 시작하지 못할 수도 있다.
	- NO : 현재 MySQL 서버에 포함되지 않았음을 의미한다.
	- DISABLED : 현재 MySQL 서버에는 포함되었지만 파라미터에 의해 비활성화된 상태이다.

- MySQL 서버에 포함되지 않은 스토리지 엔진을 사용하려면 MySQL 서버를 다시 빌드해야 하지만, 플러그인 형태로 빌드된 스토리지 엔진 라이브러리를 사용하면 쉽게 교체할 수 있다.
- `SHOW PLUGINS;` 명령으로 설치된 플러그인을 확인할 수 있다.
- 스토리지 엔진뿐만 아니라 다양한 기능을 플러그인으로 제공한다.

## 4.1.5 컴포넌트
- MySQL 8.0부터는 기존 플러그인 아키텍처를 대체하기 위해 컴포넌트 아키텍처가 지원된다.
- 컴포넌트는 다음 단점을 보완한다.
	- 플러그인은 오직 MySQL 서버와 인터페이스할 수 있고, 플러그인끼리는 통신 불가
	- 플러그인은 MySQL 서버의 변수나 함수를 직접 호출하기 때문에 안전하지 않음(캡슐화 안됨)
	- 플러그인은 상호 의존 관계를 설정할 수 없어서 초기화가 어려움

## 4.1.6 쿼리 실행 구조
1. 사용자의 SQL 요청 -> MySQL 서버
2. -> MySQL 엔진 - 쿼리 파서 - 전처리기 - 옵티마이저 - 쿼리 실행기
3. -> 스토리지 엔진(InnoDB, MyISAM, Memory)
4. -> SQL 결과

### 4.1.6.1 쿼리 파서
- 사용자 요청으로 들어온 쿼리 문장을 토큰으로 분리해 트리 형태의 구조로 만드는 작업
- 기본 문법 오류를 발견하고 오류 메세지를 전달한다.
- 토큰 : MySQL이 인식할 수 있는 최소 단위의 어휘 혹은 기호

### 4.1.6.2 전처리기
- 만들어진 파서 트리를 기반으로 쿼리 문장에 구조적 문제점이 있는지 확인
- 각 토큰을 테이블 이름, 칼럼 이름, 내장 함수와 같은 객체를 매핑하여, 해당 객체의 존재 여부와 접근 권한 등을 확인하는 과정을 수행

### 4.1.6.3 옵티마이저
- 사용자 요청으로 들어온 쿼리 문장을 저렴한 비용으로 가장 빠르게 처리할 지 결정하는 역할(두뇌 역할)
- 매우 중요한 역할이며 넓은 영향 범위를 가짐

### 4.1.6.4 실행 엔진
- 옵티마이저와 핸들러 사이의 역할을 하며, 핸들러에게 요청하여 받은 결과를 또 다른 핸들러 요청의 입력으로 연결하는 역할을 수행

### 4.1.6.5 핸들러(스토리지 엔진)
- MySQL 서버의 최하단에서 실행 엔진의 요청에 따라 데이터를 디스크로 저장하고 읽어오는 역할을 담당

## 4.1.7 복제
- MySQL 서버의 복제(Replication)는 매우 중요한 역할을 담당하며, 다른 장에서 상세히 설명한다.

## 4.1.8 쿼리 캐시
- 빠른 응답을 필요로 하는 웹 어플리케이션에서 매우 중요한 역할을 담당
- SQL 실행 결과를 메모리에 캐시하여, 동일 쿼리 실행 시 즉시 결과를 반환해 빠른 성능을 보여줬다.
- 그러나 테이블의 데이터가 변경되면 변경된 테이블과 관련된 것은 모두 삭제해야 해서, 동시 처리 성능 저하를 유발했다. 그리고 MySQL 서버의 발전에 따라 많은 버그의 원인이 되기도 했다.
- MySQL 8.0부터 쿼리 캐시는 제거되었다.

## 4.1.9 스레드 풀
- MySQL 서버 엔터프라이즈 에디션은 내장하여 지원
- Percona Server는 플러그인 형태로 작동하도록 구현
- 내부적으로 사용자 요청을 처리하는 스레드 개수를 줄여, 동시 처리되는 요청이 많아도 MySQL 서버의 CPU가 제한된 개수의 스레드 처리에만 집중할 수 있게 하여 서버의 자원 소모를 줄이는 것이 목적
- 그러나 스레드 풀이 실제 괄목적인 성능 향상을 만드는 경우는 드물었다. 오히려 CPU 스케줄링 과정에서 성능이 구려지는 경우도 발생했다.
- 스레드 그룹은 CPU 코어 개수와 맞추는 것이 CPU 프로세서 친화도를 높이는데 좋다.
- MySQL 서버가 처리해야 할 요청이 발생 시 스레드 풀로 처리 이관
	- 스레드 풀이 처리 중인 작업이 있으면, `thread_pool_oversubscribe` 시스템 변수에 설정된 개수만큼 추가로 더 받아들여서 처리한다. 이 값이 너무 크면 스케줄링할 스레드가 많아져서 스레드 풀이 비효율적으로 작동할 수 있다.
	- 스레드 그룹의 모든 스레드가 처리중인 경우 : 스레드 풀은 해당 스레드 그룹에 새 작업 스레드를 추가할 지, 기존 작업 스레드를 기다릴 지 여부를 판단한다.
- 타이머 스레드 : 주기적으로 스레드 그룹의 상태를 체크하여, `thread_pool_stall_limit` 시스템 변수에 정의된 밀리초만큼 작업 스레드가 작업을 끝내지 못하면 새 스레드를 만들어 스레드 그룹에 추가한다.
	- 전체 스레드 풀에 있는 스레드 개수는 `thread_pool_max_threads` 설정 개수를 넘을 수 없다.
- 응답 시간에 민감한 서비스는 `thread_pool_stall_limit`을 적당히 낮춰서 설정해야 한다.
	- 모든 스레드 그룹의 스레드가 각자 작업을 처리하고 있다면 `thread_pool_stall_limit` 시간을 기다려야 새 요청을 처리할 수 있기 때문
	- 그러나 0에 가까운 값으로 설정하는건, 스레드 풀을 사용하지 않느니만 못하다.
- Percona Server의 스레드 풀은 선순위 큐 / 후순위 큐로 특정 트랜잭션이나 쿼리를 우선적으로 처리할 수 있는 기능을 제공

## 4.1. 10 트랜잭션 지원 메타데이터
- 메타데이터(데이터 딕셔너리) : 테이블 구조 정보와 스토어드 프로그램 등의 정보
- MySQL 5.7까지는 FRM 파일로 메타데이터를 저장했는데, MySQL 서버가 비정상적으로 종료되면 이 파일이 일관되지 못하게 남아있었다.
- MySQL 8.0부터 메타데이터를 InnoDB의 테이블에 저장하도록 개선했다.
	- 시스템 테이블 : MySQL 서버가 작동하는 데 기본적으로 필요한 테이블들
	- 시스템 테이블 + 메타데이터를 `mysql.ibd` 테이블스페이스에 저장
- 스키마 작업 중간에 비정상적으로 MySQL 서버가 종료되면, 완전한 성공 또는 완전한 실패로 정리하도록 하여 문제를 유발하지 않게 개선했다.
- InnoDB 스토리지 엔진 외에 스토리지 엔진을 사용하는 테이블 : SDI(Serialized Dictionary Information) 파일 사용 `*.sdi`
    - InnoDB 테이블 구조도 SDI 파일로 변환 가능 (`ibd2sdi` 유틸리티)

# 4.2 InnoDB 스토리지 엔진 아키텍처
- MySQL 스토리지 엔진 중 가장 많이 사용되며, MySQL에서 사용할 수 있는 스토리지 엔진 중 거의 유일하게 레코드 기반 잠금을 제공한다.
- 높은 동시성 처리, 안정적, 뛰어난 성능

## 4.2.1 프라이머리 키에 의한 클러스터링
- InnoDB의 모든 테이블은 기본적으로 PK를 기준으로 클러스터링되어 저장된다. 즉 PK 순으로 디스크에 저장된다.
- 모든 세컨더리 인덱스는 레코드 주소 대신 PK 값을 논리적인 주소로 사용한다.
- PK를 이용한 레인지 스캔은 상당히 빨리 처리될 수 있다.
- 그러나 MyISAM에서는 클러스터링 키를 지원하지 않는다. 그래서 MyISAM은 PK와 세컨더리 인덱스는 구조적으로 차이가 없다.
	- MyISAM에게 PK는 유니크 제약을 가진 세컨더리 인덱스에 불과
	- PK를 포함한 모든 인덱스는 물리적인 레코드 주소 값(ROWID)를 가진다.

## 4.2.2 외래 키 지원
- InnoDB 스토리지 엔진 레벨에서 지원하는 기능으로, MyISAM, MEMORY 테이블에서는 사용불가
- FK는 DB 서비스용 서버 운영 불편함으로 인해 생성하지 않는 경우도 있지만, 개발 환경에선 좋을 수 있다.
	- InnoDB의 FK는 부모 테이블과 자식 테이블 모두 해당 칼럼에 인덱스 생성이 필요하고, 변경 시 반드시 부모 테이블이나 자식 테이블에 데이터가 있는지 체크하는 작업이 필요
	- 잠금이 여러 테이블로 전파되고, 데드락이 발생할 때가 많아 개발할 때 FK 존재에 주의하는게 좋다.
- 수동으로 데이터를 적재하는 등 FK 체크를 무시해야 하는 상황이 발생한다면, `foreign_key_checks` 시스템 변수를 `OFF`로 설정하여 FK 체크 작업을 일시적으로 멈출 수 있다.
- 이 시스템 변수는 적용 범위를 GLOBAL, SESSION으로 모두 설정 가능하다.
```
SET foreign_key_checks=OFF;
```
- `SESSION`을 언급하지 않으면, 위 명령어는 기본적으로 `SESSION`에 대해 설정한다.
- 끄면 `ON DELETE CASCADE`, `ON UPDATE CASCADE` 작업도 무시한다.
- 작업이 끝나면 다시 활성화해야 한다.

## 4.2.3 MVCC(Multi Version Concurrency Control)
- 레코드 레벨의 트랜잭션을 지원하는 DBMS가 제공하는 기능, 가장 큰 목적은 잠금을 사용하지 않는 일관된 읽기를 제공
- InnoDB는 언두 로그(Undo Log)를 이용해 구현한다.
- Multi Version은 하나의 레코드에 대해 여러 버전이 동시에 관리되는 걸 말한다.
자세한 구현 내용은 책 101 page 참고..

- INSERT 문 실행 시
	- InnoDB 버퍼 풀과 데이터 파일(디스크)는 동일하게 정보가 기록
- 이후 UPDATE 문 실행 시
	- 커밋 실행 여부와 관계 없이 InnoDB 버퍼 풀은 업데이트가 진행됨
	- 언두로그에는 변경된 칼럼의 변경 전 값만 복사
	- 디스크의 데이터 파일은 체크포인트나 InnoDB의 쓰기 스레드에 의해 업데이트가 진행될수도, 아닐수도 있음. 다만 InnoDB가 ACID를 보장하기 때문에 일반적으로 InnoDB 버퍼 풀과 데이터 파일은 동일한 상태로 가정해도 무방하다.
- 여기서 COMMIT 혹은 ROLLBACK 되기 전 상황에서 조회를 한다면?
	- `transaction_isolation`시스템 변수에 설정된 격리 수준에 따라 다르다.
	- READ_UNCOMMITTED의 경우, 버퍼 풀에 기록된 현재의 변경된 데이터를 반환
	- 그 이상의 격리 수준의 경우, 변경되기 전의 값을 가진 언두 로그의 데이터를 반환
- 이것이 MVCC이다.
- 1개의 레코드에 대해 2개의 버전을 유지하며, 필요에 따라 어느 데이터가 보여지는지 상황에 따라 달라짐
- 관리해야 하는 이전 버전 데이터가 무한히 많아질 수 있다.
- 트랜잭션이 길어지면 예전 데이터가 삭제되지 못하고 오래 관리해야 하며, 언두 로그가 저장되는 시스템 테이블스페이스의 공간이 많이 늘어나는 상황이 발생할 수도 있다.
- 위 상태에서 COMMIT을 실행하면 InnoDB는 더 이상 변경 작업 없이 영구적인 데이터로 기록하지만, ROLLBACK을 실행하면 언두 로그 영역의 데이터를 InnoDB 버퍼 풀로 복구하고 그 내용을 삭제한다.
- 커밋한다고 항상 바로 삭제하는 건 아니고, 그 언두 로그 영역을 필요로 하는 트랜잭션이 없을 때 삭제한다.

## 4.2.4 잠금 없는 일관된 읽기(Non-Locking Consistent Read)
- InnoDB는 MVCC를 이용해 잠금 없이 읽기를 수행한다.
- 그래서 다른 트랜잭션이 가지고 있는 잠금을 기다리지 않고 읽을 수 있다.
- 격리 수준이 SERIALIZABLE이 아니라면, INSERT와 연결되지 않은 순수한 읽기 작업은 다른 트랜잭션 변경 작업과 관련 없이 항상 잠금을 대기하지 않고 바로 실행된다.
- READ_UNCOMMITTED는 바로 읽을테고, READ_COMMITTED와 REPEATABLE_READ는 언두 로그를 사용해서 읽는다.
- 오랫동안 활성 상태인 트랜잭션이 있어 MySQL 서버에 문제가 발생할 수도 있다. 언두 로그가 삭제되지 않고 계속 유지해야 하기 때문에, 가능한 한 빨리 트랜잭션을 완료하는게 좋다.

## 4.2.5 자동 데드락 감지
- InnoDB는 내부적으로 잠금이 교착 상태에 빠지지 않았는지 체크하기 위해 잠금 대기 목록을 그래프(Wait-for List) 형태로 관리한다.
- 데드락 감지 스레드가 주기적으로 잠금 대기 그래프를 검사하여, 교착 상태에 빠진 트랜잭션을 찾아 하나를 강제 종료한다.
	- 트랜잭션의 언두 로그의 양을 기준으로 강제 종료할 트랜잭션을 선정한다.
	- 언두 로그 레코드가 더 적은 트랜잭션이 일반적으로 롤백의 대상이 된다. 그런 트랜잭션은 롤백을 해도 언두 처리를 할 내용이 적어 부하가 적기 때문이다.
	- InnoDB는 `innodb_table_locks`로 엔진 내부 레코드 잠금, 테이블 레벨 잠금을 감지 가능
- 동시 처리 스레드가 많아지거나, 각 트랜잭션이 가지는 잠금의 개수가 많아지면 데드락 감지 스레드가 느려진다.
	- `innodb_deadlock_detect` : OFF로 설정 시 데드락 감지 스레드는 작동하지 않는다.
    - 데드락 상황 무한정 대기
	    - `innodb_lock_wait_timeout` : 데드락 상황에서 일정 시간이 지나면 자동으로 요청이 실패하고, 에러 메세지를 반환한다.
	        - 초 단위 설정 가능
	        - 50초보다 낮은 시간으로 설정하는 것을 권장한다.

## 4.2.6 자동화된 장애 복구
- InnoDB에는 손실이나 장애로부터 데이터를 보호하기 위해 여러 메커니즘을 탑재
	- 서버 시작 시 완료하지 못한 트랜잭션이나 디스크에 일부만 기록된 데이터 페이지 등에 대한 일련의 복구를 자동으로 진행한다.
- InnoDB 데이터 파일은 기본적으로 MySQL서버가 시작될 때 항상 자동 복구를 수행한다.
	- 이 때 복구할 수 없는 손상이 있다면 자동 복구를 멈추고 MySQL 서버는 종료된다.
	- `innodb_force_recovery` 시스템 변수를 설정하여 MySQL 서버를 시작해야 한다.
		- 로그 파일 손상 시, 6으로 설정하고 기동한다.
		- 테이블의 데이터 파일이 손상됐다면, 1로 설정하고 기동한다.
		- 어디가 문제인지 모르면 1부터 6까지 변경하면서 기동해본다.
		- 그 값이 커질수록 심각한 상황이라 데이터 손실 가능성은 커지고 복구 가능성은 낮아진다.
- MySQL 서버가 기동되고 InnoDB 테이블이 인식되면 mysqldump를 이용하여 데이터를 가능한 만큼 백업하고 그 데이터로 MySQL 서버의 DB와 테이블을 다시 생성하는 것이 좋다.
- innodb_force_recovery가 0이 아닌 복구 모두에서는 SELECT 이외의 쿼리는 수행할 수 없다.

#### innodb_force_recovery 설정 값

- `1(SRV_FORCE_IGNORE_CORRUPT)`
    - 테이블스페이스의 데이터나 인덱스 페이지에서 손상된 부분이 발견돼도 무시하고 MySQL 서버 시작한다.
    - 에러 로그 파일에 `Database page corrupt on disk or a failed`
    - mysqldump 프로그램이나 `SELECT INTO OUTFILE...` 명령 이용해 덤프해서 데이터베이스 다시 구축한다.
- `2(SRV_FORCE_NO_BACKGROUND)`
    - InnoDB의 메인 스레드가 언두 데이터를 삭제하는 과정에서 장애 발생 시
    - 백그라운드 스레드 가운데 메인 스레드를 시작하지 않고 MySQL 서버 시작한다.
- `3(SRV_FORCE_NO_TRX_UNDO)`
    - 커밋되지 않은 트랜잭션의 작업을 롤백하지 않고 그대로 놔둔다.
    - 데이터 백업 후 데이터베이스를 새로 구축해야 한다.
- `4(SRV_FORCE_NO_IBUF_MERGE)`
    - INSERT, UPDATE, DELETE 데이터 변경으로 인한 인덱스 변경 작업 -> 즉시 처리하거나 인서트 버퍼에 저장 후처리 -> 언제 데이터 파일에 병합될지 알 수 없다.
    - 인서트 버퍼의 내용을 무시하고 강제로 MySQL 시작한다.
- `5(SRV_FORCE_NO_UNDO_LOG_SCAN)`
    - 언두 로그를 모두 무시하고 MySQL을 시작한다.
    - MySQL 서버가 종료되던 시점에 커밋되지 않았던 작업도 모두 커밋된 것처럼 처리 -> 잘못된 데이터가 데이터베이스에 남는다.
    - 데이터 백업 후 데이터베이스를 새로 구축해야 한다.
- `6(SRV_FORCE_NO_LOG_REDO)`
    - 리두 로그를 모두 무시한 채로 MySQL 서버 시작한다.
    - 커밋됐다 하더라도 리두 로그에만 기록되고 데이터 파일에 기록되지 않은 데이터는 모두 무시된다.
    - 마지막 체크포인트 시점의 데이터만 남게 된다.
    - MySQL 서버가 시작하면서 리두 로그가 없으면 새로 생성한다.
    - 데이터 백업 후 데이터베이스를 새로 구축해야 한다.

## 4.2.7 InnoDB 버퍼 풀
- 데이터 파일이나 인덱스 정보를 메모리에 캐시해두는 공간
- InnoDB 스토리지 엔진에서 가장 핵심적인 부분
- 데이터를 변경하는 쿼리는 데이터 파일의 랜덤한 위치에 있는 레코드를 변경하기에, 디스크 작업 또한 랜덤하게 발생된다. 버퍼 풀은 이런 변경 데이터를 모아 처리하여 랜덤한 디스크 작업 횟수를 줄일 수 있다.

### 4.2.7.1 버퍼 풀의 크기 설정
- OS와 각 클라이언트 스레드가 사용할 메모리도 충분히 고려해서 설정해야 한다.
- 레코드 버퍼 - 각 클라이언트 세션에서 테이블의 레코드를 읽고 쓸 때 버퍼로 사용하는 공간, 커넥션이 많거나 사용하는 테이블도 많다면 공간이 많이 필요할 수도 있다.
- MySQL이 사용하는 레코드 버퍼는 별도로 설정할 수 없으며 전체 커넥션 개수와 각 커넥션에서 읽고 쓰는 테이블 개수에 따라 결정된다.
- 동적으로 해제되기도 해서 정확히 얼마나 필요한진 모른다.
- MySQL 5.0부터는 InnoDB 버퍼 풀의 크기를 동적으로 조절할 수 있어서, 가능하면 적절히 작은 값부터 시작해 조금씩 증가시키는게 최적이다.
- 전체 메모리가 8GB 미만이면 50%만 InnoDB 버퍼 풀로 설정하는게 좋다.
- 그 이상이면 50%부터 시작해서 조금씩 올리며 최적점을 찾는다.
- 전체 메모리 공간이 50GB 이상이면, 15GB에서 30GB 정도를 제외하고 나머지를 InnoDB 버퍼 풀로 할당한다.
- InnoDB 버퍼 풀은 `innodb_buffer_pool_size` 시스템 변수로 크기를 설정할 수 있다.
	- 버퍼 풀을 더 크게 변경하는건 영향이 적지만, 작게 변경하는건 영향이 크다.
	- 내부적으로 128MB 청크 단위로 쪼개서 관리된다.
	- 가능한 MySQL 서버가 한가한 시점을 골라서 진행하는 것이 좋다.
- 버퍼 풀 전체를 관리하는 잠금(세마포어)으로 인해 내부 잠금 race를 많이 유발했는데, 이를 줄이기 위해 버퍼 풀을 여러 개로 쪼개어 관리할 수 있게 개선됐다.
	- `innodb_buffer_pool_instances` 시스템 변수로 버퍼 풀을 여러 개로 분리해서 관리할 수 있다.
	- 분리한 각 버퍼 풀은 버퍼 풀 인스턴스라고 표현한다.
	- 기본적으로 8개로 초기화된다.
	- 버퍼 풀 전체 메모리 크기가 1GB 미만이면 인스턴스는 1개만 생성된다.
	- 40GB 이하면 기본값인 8을 유지하며, 더 크면 인스턴스 당 5GB가 되도록 개수를 설정하는게 좋다.

### 4.2.7.2 버퍼 풀의 구조
- 버퍼 풀을 페이지 크기(`innodb_page_size` 시스템 변수로 설정)의 조각으로 쪼개어 엔진이 데이터를 필요로 할 때 해당 데이터 페이지를 읽어 각 조각에 저장한다.
- LRU(Least Recently Used) 리스트, 플러시(Flush) 리스트, 프리(Free) 리스트로 3개의 자료 구조를 관리한다.

#### Free 리스트
- InnoDB 버퍼 풀에서 실제 사용자 데이터로 채워지지 않은 빈 페이지들의 목록
- 사용자 쿼리가 새롭게 데이터 페이지를 읽어와야 하는 경우 사용

#### LRU 리스트
- 엄밀히는 MRU(Most Recently Used) 리스트가 결합된 형태
- Old 서브리스트는 LRU, New 서브리스트는 MRU 느낌
- 디스크로부터 한 번 읽어온 페이지를 최대한 오랫동안 버퍼 풀의 메모리에 유지하여 디스크 읽기 최소화
    - 처음 한 번 읽힌 데이터 페이지가 자주 사용되면 MRU 영역에서 계속 살아남는다
    - 거의 사용되지 않으면 LRU 끝으로 밀려나고, 버퍼 풀에서 제거

#### 플러시 리스트 
- 디스크로 동기화되지 않은 데이터를 가진 데이터 페이지(Dirty Page라고도 함)의 변경 시점 기준의 페이지 목록을 관리한다.
    - 한 번 데이터 변경이 가해진 데이터 페이지는 플러시 리스트에 관리하며, 특정 시점이 되면 디스크에 기록한다.
