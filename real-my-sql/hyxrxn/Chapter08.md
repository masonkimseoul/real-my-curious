# 8.1

### HDD(하드 디스크 드라이브)와 SSD(솔리스 스테이트 드라이브)
- HDD
  - 기계식 장치
- SSD
  - 전자식 저장 매체
  - SATA나 SAS를 지원하므로 내장 디스크나 DAS, SAN에 그대로 사용 가능
  - 데이터 저장용 플래터(원판) 대신 플레시 메모리 장착
  - 전원이 공급되지 않아도 데이터 삭제되지 않음
  - D-Ram보다는 느리지만 HDD보다는 훨씬 빠름
  - 순차 I/O에서는 HDD보다 조금 빠르거나 거의 비슷할 수 있지만, 랜덤 I/O에서는 훨씬 빠름

### 랜덤 I/O와 순차 I/O
- HDD에서의 랜덤 I/O는 여러 번 쓰기 또는 읽기를 요청해 디스크 헤드가 많이 움직이고, 작업 부하가 훨씬 큼
- SSD 또한 여전히 랜덤 I/O는 순차 I/O보다 Throughput이 떨어짐
- 쿼리를 튜닝하는 것은 대부분 랜덤 I/O를 순차 I/O로 바꾸는 것이 아니라 랜덤 I/O 자체를 줄이는 것

# 8.2

### 인덱스란
- 인덱스는 정렬이 되어있기 때문에 SELECT 성능이 높음
- 하지만 정렬을 해야하기 때문에 INSERT나 UPDATE 성능이 떨어짐
- 앞으로 키와 인덱스는 같은 의미로 사용할 것!
- 역할별로 구분
  - 프리아미러 키(Primary key)
  - 보조 키(Secondary key)
- 알고리즘별로 구분
  - B-Tree 인덱스
  - Hash 인덱스
  - Fractal-Tree 인덱스
  - Merge-Tree 인덱스
- 중복 허용 여부로 구분
  - 유니크 인덱스(Unique)
  - 유니크하지 않은 인덱스(Non-Unique)

# 8.3

## 구조 및 특성
- 구조
  - 트리 구조의 최상위에 하나의 루트 노드(Root node)
  - 그 하위에 자식 노드
  - 가장 하위의 노드가 리프 노드(Leaf node), 항상 실제 데이터 레코드를 찾아가기 위한 주소값을 가지고 있음
  - 루트도 아니고 리프도 아닌 노드가 브랜치 노드(Branch node)
- 특성
  - MyISAM은 세컨더리 인덱스가 물리적인 주소를 가지는 반면 InnoDB는 프라이머리 키를 주소처럼 사용하기 때문에 논리적인 주소 가짐
  - InnoDB 테이블에서 인덱스를 통해 레코드를 읽을 때는 인덱스에 저장되어 있는 프라이머리 키 값으로 프라이머리 키 인덱스를 한 번 더 검색해야 함
  - InnoDB 테이블이 성능이 떨어질 것 같지만 장단점 존재 -> 8.8에서 자세히 확인

## B-Tree 인덱스 키 추가 및 삭제

### 인덱스 키 추가
- 저장될 키 값을 이용해 적절한 위치 검색
- 위치 결정되면 키와 대상 레코드의 주소 정보를 리프 노드에 저장
- 리프 노드가 꽉 찼으면 Split
- Split 시에는 상위 브랜치 노드까지 처리해야 하기 때문에 새로운 키 추가 작업에 비용이 많이 듬
- 추가 시기
  - MyISAM / MEMORY 는 즉시 새로운 키 값 추가
  - InnoDB는 지연시켜 나중에 처리 가능
  - 프라이머리 키 / 유니크 인덱스는 중복 체크가 필요해 즉시 추가 / 삭제

### 인덱스 키 삭제
- 해당 키 값이 저장된 리프 노드를 찾아 삭제 마크
- 삭제 마킹된 공간은 방치하거나 재활용
- InnoDB에서는 이 또한 지연 처리 가능

### 인덱스 키 변경
- 키 값을 삭제한 후 다시 새로운 키 값을 추가하는 형태로 처리
- 마찬가지로 InnoDB에서는 지연 처리 가능

### 인덱스 키 검색
- 가능한 경우
  - 100% 일치
  - 앞부분(Left-most part)만 일치
  - 부등호 비교 조건
- 불가능한 경우
  - 뒷부분만 일치
  - 키 값에 변형이 가해진 후 비교하는 경우 (함수나 연산을 수행한 결과로 정렬하거나 검색하는 작업)
- InnoDB에서는 불필요한 잠금을 피하기 위해서라도 인덱스 설계 잘 해야 함

## B-Tree 인덱스 사용에 영향을 미치는 요소

### 인덱스 키 값의 크기
- InnoDB는 디스크에 데이터를 페이지(Page) / 블록(Block) 단위로 저장
- 인덱스도 페이지 단위로 관리
- 저장 예시
  - 페이지 크기가 16KB, 인덱스 키가 16B, 자식 노드 주소 영역이 12B라고 가정
  - 하나의 페이지에 16*1024/(16+12) = 585개 저장
  - 만약 키 값이 32B라면 16*1024/(32+12) = 372개 저장
- 키 값이 커지면 디스크로부터 읽어야 하는 횟수 증가
- 인덱스의 크기가 커지면 캐시해둘 수 있는 레코드 수 감소 -> 메모리 효율 떨어짐

### B-Tree 깊이
- 위의 예시에서, Depth가 3이고 키가 16B인 경우 585*585*585 = 대략 2억개 저장 가능
- 키가 32B로 늘어난 경우 372*372*372 = 대략 5천만개 저장 가능
- 인덱스 키 값이 커지면 같은 개수를 저장할 때 Depth가 깊어져 디스크 읽기가 더 많이 필요
- 실제로는 5단계 이상까지 깊어지는 경우는 흔치 않음

### 선택도(Selectivity)/기수성(Cardinality)
- 모든 인덱스 키 값 가운데 유니크한 값의 수
- 중복된 값이 많아지면 많아질수록 기수성이 낮아지고 선택도가 떨어짐
- 선택도가 높을수록 검색 대상이 줄어들어 빠르게 처리

### 읽어야 하는 레코드의 건수
- 일반적으로 인덱스를 통해 레코드 1건을 읽는 것이 직접 레코드 1건을 읽는 것보다 4~5배 정도 비용이 더 많이 드는 것으로 예측
- 인덱스를 통해 읽어야 할 레코드의 건수가 전체 테이블의 20~25%를 넘어가면 전체를 읽는 것이 효율적

## B-Tree 인덱스를 통한 데이터 읽기

### 인덱스 레인지 스캔
- 가장 대표적인 접근 방식
- 검색해야 할 인덱스의 범위가 결정됐을 때 사용
- 시작해야 할 위치를 찾으면 그때부터 리프 노드의 레코드만 순서대로 읽음(스캔)
- 스캔 중 리프노드의 끝까지 읽으면 리프 노드 간의 링크로 다음 리프노드르 찾아 다시 스캔
- 스캔을 멈춰야 할 위치에 다다르면 지금까지 읽은 레코드를 반환하고 쿼리 종료
- 검색 조건에 일치하는 건들은 데이터 파일에서 레코드를 읽어오는 과정도 필요! (커버링 인덱스로 처리하면 불필요)
- 레코드 한 건 단위로 랜덤 I/O 발생
- 정리
  1. 조건을 만족하는 값이 저장된 위치를 찾는 인덱스 탐색(Index seek)
  2. 그 위치부터 필요한 만큼 인덱스를 차례대로 읽는 인덱스 스캔(Index scan)
  3. 그 인덱스 키와 레코드 주소를 이용해 저장돈 페이지 가져오고 최종 레코드 읽음

### 인덱스 풀 스캔
- 인덱스의 처음부터 끝까지 모두 읽는 방식
- 대표적으로 쿼리의 조건절에 사용된 칼럼이 인덱스의 첫 번째 칼럼이 아닌 경우 사용
- 쿼리가 인덱스에 명시된 칼럼만으로 조건을 처리할 수 있는 경우 사용
- 인덱스뿐만 아니라 데이터 레코드까지 읽어야 하는 경우 이 방식으로 처리 불가
- 이것은 일반적으로 인덱스를 생성하는 목적이 아니고, 인덱스를 효율적으로 사용하지 못하는 것임...

### 루스(Loose) 인덱스 스캔
- 오라클의 인덱스 스킵 스캔과 작동 방식 비슷
- 느슨하게, 듬성듬성하게 인덱스를 읽는 것을 의미
- 인덱스 레인지 스캔과 비슷하게 작동하지만 중간에 필요치 않은 인덱스 키 값은 무시(Skip)
- 일반적으로 `GROUP BY` 또는 `MAX()`, `MIN()` 함수에 대해 최적화를 하는 경우에 사용

### 인덱스 스킵 스캔(Index skip scan)
- 인덱스는 정렬되어있기 때문에 인덱스를 구성하는 칼럼의 순서가 매우 중요
- 8.0부터는 칼럼을 건너뛰고 검색이 가능하게 해주는 인덱스 스킵 스캔 최적화 기능 도입
- `WHERE` 조건절의 검색을 위해 사용 가능하도록 용도가 넓어진 것
- 단점
  - 조건이 없는 인덱스의 선행 칼럼의 유니크한 값의 개수가 적어야 함
  - 쿼리가 인덱스에 존재하는 칼럼만으로 처리 가능해야 함(커버링 인덱스)

## 다중 칼럼(Multi-column) 인덱스
- 두 개 이상의 칼럼으로 구성된 인덱스
- 실제 서비스에서는 이 인덱스가 더 많이 사용
- 인덱스의 두 번째 칼럼은 첫 번째 칼럼에 의존해 정렬
- 그래서 각 칼럼의 순서가 매우 중요

## B-Tree 인덱스의 정렬 및 스캔 방향

### 인덱스의 정렬
- 인덱스를 생성하는 시점에 각 칼럼의 정렬을 오름차순 또는 내림차순으로 설정
- 8.0부터 정렬 순서를 혼합한 인덱스 생성 가능

### 인덱스 스캔 방향
- 쿼리가 인덱스를 사용하는 시점에 인덱스를 읽는 방향에 따라 오름차순 또는 내림차순 효과 낼 수 있음
- `ORDER BY` 처리나 `MIN()`, `MAX()` 등의 최적화가 필요한 경우 인덱스의 읽기 방향을 전환해 사용

### 내림차순 인덱스
- 용어 정리
  - 오름차순 인덱스(Ascending index): 작은 값의 인덱스 키가 B-Tree의 왼쪽으로 정렬된 인덱스
  - 내림차순 인덱스(Descending index): 큰 값의 인덱스 키가 B-Tree의 왼쪽으로 정렬된 인덱스
  - 인덱스 정순 스캔(Forward index scan): 인덱스 리프 노드의 왼쪽 페이지부터 오른쪽으로 스캔
  - 인덱스 역순 스캔(Backward index scan): 인덱스 리프 노드의 오른쪽 페이지부터 왼쪽으로 스캔
- 내부적으로는 InnoDB에서 역순 스캔이 정순 스캔에 비해 느릴 수밖에 없음
  - 페이지 잠금이 정순 스캔에 적합하기 때문
  - 페이지 내에서 인덱스 레코드가 단방향으로만 연결되었기 때문

## B-Tree 인덱스의 가용성과 효율성

### 비교 조건의 종류와 효율성
- 칼럼의 순서와 사용된 조건이 동등비교인지 범위 조건인지에 따라 칼럼의 활용 형태와 효율이 달라짐
- 인덱스를 통해 읽은 레코드가 나머지 조건에 맞는지 비교하면서 취사선택하는 작업이 필터링
- 작업의 범위를 결정하는 조건이 작업 범위 결정 조건
- 작업의 범위를 줄이지 못하고 단순히 거름종이 역할만 하는 것이 필터링 조건 / 체크 조건
- 작업 범위 결정 조건이 많을수록 쿼리의 성능을 높임
- 예시
  - `SELECT * FROM dept_emp WHERE dept_no='d002' AND emp_no >= 10114 ;` 실행
  - `INDEX (dept_no, emp_no)` 인 경우
    - 두 조건 모두 작업 범위 결정 조건
  - `INDEX (emp_no, dept_no)` 인 경우
    - emp_no 칼럼만 작업 범위 결정 조건

### 인덱스의 가용성
- 하나의 칼럼으로 검색해도 값의 왼쪽 부분이 없으면 인덱스 레인지 스캔 방식 불가능
  - 예시
    - `INDEX (first_name)` 에서 `SELECT * FROM employees WHERE first_name LIKE '%mer' ;` 실행
- 다중 칼럼 인덱스에서 왼쪽 칼럼의 값을 모르면 인덱스 레인지 스캔 방식 불가능
  - 예시
    - `INDEX (dept_no, emp_no)` 에서 `SELECT * FROM dept_emp WHERE emp_no >= 10133 ;` 실행

### 가용성과 효율성 판단
- 작업 범위 결정 조건으로 사용할 수 없는 조건들
  - NOT-EQUAL로 비교된 경우 (<>, NOT IN, NOT BETWEEN, IS NOT NULL)
  - 뒷부분 일치 형태로 문자열 패턴이 비교된 경우 (LIKE '%??')
  - 스토어트 함수나 다른 연산자로 인덱스 칼럼이 변형된 후 비교된 경우
  - NOT-DETERMINISTIC 속성의 스토어트 함수가 비교 조건에 사용된 경우
  - 인덱스 칼럼의 타입을 변환해야 비교가 가능한 경우 (데이터 타입이 서로 다른 비교)
  - 문자열 데이터 타입의 콜레이션(15.1.4 참조)이 다른 경우
- 다중 칼럼인 경우
  - 첫번째 칼럼에 대한 조건이 없거나 위의 인덱스 사용 불가 조건인 경우 작업 범위 결정 조건으로 사용 불가
  - i-1번째 칼럼까지 동등 비교 형태이고 i번째 칼럼이 동등 비교 / 크다 작다 형태 / LIKE로 좌측 일치 패턴인 경우 i번째 칼럼까지는 작업 범위 결정 조건으로 사용 가능

# 8.5

## 전문 검색(Full Text search)
- 문서의 내용 전체를 인덱스화해서 특정 키워드가 포함된 문서 검색
- 전문 검색을 위한 인덱싱 알고리즘이 전문 검색 인덱스

## 인덱스 알고리즘
- 문서의 키워드를 인덱싱하는 기법에 따라 구분

### 어근 분석 알고리즘
- 검색어로 선정된 단어의 뿌리인 원형을 찾는 작업이 어근 분석(Stemming)
- MeCap을 이용해 한글 분석 가능
- 하지만 단어 사전과 문장 해체해 각 단어의 품사를 식별할 수 있는 문장의 구조 인식 필요!

### n-gram 알고리즘
- MeCab을 위한 형태소 분석은 많은 시간과 노력이 필요하기 때문에 범용적으로 적용하기는 쉽지 않아 보완하기 위해 도입된 방법
- 형태소 분석이 아닌 단순히 키워드를 검색해내기 위한 인덱싱 알고리즘
- 본문을 무조건 몇 글자씩 잘라서 인덱싱하는 방법
- 형태소 분석보다는 단순하고 준비 작업이 필요 없지만, 만들어진 인덱스의 크기가 상당히 큼
- n은 인덱싱할 키워드의 최소 글자 수
- 일반적으로는 2글자 단위로 키워드를 쪼개서 인덱싱하는 방식 사용
- 예시 (2-gram으로 `That is the question` 토큰 분리)
  1. 띄어쓰기와 마침표를 기준으로 단어 구분 후 2글자씩 중첩해서 토큰으로 분리
    - That -> Th, ha, at
    - is -> is
    - the -> th, he
    - question -> qu, ue, es, st, ti, io, on
  2. 불용어와 동일하거나 불용어를 포함하는 경우 버림
    - at, ha, io, is, ti 버림
