# 5.1

## MySQL에서의 트랜잭션

### MyISAM과 InnoDB 처리 방식 차이
- MyISAM에서는 중간에 쿼리가 실패해도 이전의 쿼리가 실행된 상태로 종료 (부분 업데이트, Partial Update)
- InnoDB에서는 중간에 쿼리가 실패하면 이전의 쿼리도 실행되기 이전의 상태로 종료

### 주의사향
- 데이터베이스 커넥션을 가지고 있는 범위 최소화
- 트랜잭션이 활성화돼 있는 프로그램의 범위 최소화
- 네트워크 작업이 있는 경우 반드시 트랜잭션에서 배제

# 5.2

## MySQL에서의 잠금

### 글로벌 락(Global Lock)
- `FLUSH TABLES WITH READ LOCK` 명령으로 획득
- 가장 범위가 큰 잠금
- 한 세션에서 글로벌 락 획득 시 다른 세션에서 SELECT를 제외한 대부분의 DDL, DML 문장이 대기 상태가 됨
- 서버 전체에 영향
- 작업 대상 테이블이나 데이터베이스가 다르더라도 동일하게 영향
- InnoDB는 트랜잭션을 지원하기 때문에 모든 데이터 변경 작업 정지는 불필

### 백업 락
- 8.0부터 Xtrabackup / Enterprise Backup 등의 백업 툴의 안정적인 실행을 위해 도입
- 특성 세션에서 백업 락 획득 시 모든 세션에서 테이블의 스키마나 인증 관련 정보를 변경할 수 없음

### 테이블 락(Table Lock)
- 개별 테이블 단위로 설정
- 명시적
  - `LOCK TABLES table_name [ READ | WRITE ]` 명령으로 획득
  - `UNLOCK TABLES` 명령으로 반납
  - 온라인 작업에 상당한 영향을 미쳐 특별한 상황이 아니면 사용 불필요
- 묵시적
  - MyISAM이나 MEMORY 테이블에 데이터 변경 쿼리 실행시 발생, 쿼리가 완료되면 자동 해제
  - InnoDB의 경우 레코드 기반의 잠금을 제공해 단순 데이터 변경 쿼리(DML)로 테이블 락이 설정되지는 않음
  - 스키마를 변경하는 쿼리(DDL)인 경우에만 영향

### 네임드 락(Named Lock)
- `GET_LOCK()` 함수로 임의의 문자열에 대해 잠금 설정
- 여러 클라이언트가 상호 동기화를 처리해야 할 때 이용
- 많은 레코드에 대해 복잡한 요건으로 레코드를 변경하는 트랜잭션에 유용
- 동일 데이터를 변경 / 참조하는 프로그램끼리 분류해 네임드 락을 걸고 쿼리 실행하는 방식으로 이용
- 8.0부터는 중첩 사용, 현재 세션의 락 한번에 해제 가능

### 메타데이터 락(Metadata Lock)
- 데이터베이스 객체(테이블, 뷰 등)의 이름이나 구조를 변경하는 경우 자동으로 획득
- `RENAME TABLE` 명령의 경우 원본 이름과 변경될 이름 모두 잠금 설정

# 5.3

## InnoDB에서의 잠금

### 레코드 락(Record lock, Record only lock)
- 다른 상용 DBMS의 레코드 락과 동일한 역할
- 레코드 자체가 아니라 인덱스의 레코드를 잠금
- 인덱스가 없더라도 자동 생성된 클러스터 인덱스 이용

### 갭 락(Gap lock)
- 레코드와 바로 인접한 레코드 사이의 간격만을 잠그는 것
- 레코드와 레코드 사이의 간격에 새로운 레코드가 INSERT 되는 것을 제어
- 주로 넥스트 키 락의 일부로 사용

### 넥스트 키 락(Next key lock)
- 레코드 락과 갭 락을 합쳐 놓은 형태
- `innodb_locks_unsafe_for_binlog`가 0으로 설정되면 변경을 위해 검색하는 레코드에 걸림
- 바이너리 로그에 기록되는 쿼리가 레플리카 서버에서 실행될 때 소스 서버에서 만들어 낸 결과와 동일한 결과를 만들어내도록 보장하는 것이 주목적
- 바이너리 로그 포맷을 ROW 형태로 변경해 넥스트 키 락이나 갭 락을 줄이는 것이 좋음

### 자동 증가 락(Auto increment lock)
- `AUTO_INCREMENT` 칼럼이 사용된 테이블에 새로운 레코드가 저장될 때 내부적으로 사용
- 테이블 수준의 잠금
- 각 레코드가 중복되지 않고 저장된 순서대로 증가하는 일련번호 값을 가지게 함
- 트랜잭션과 관계없이 INSERT나 REPLACE 문장에서 AUTO_INCREMENT 값을 가져오는 순간에만 락
- 테이블에 단 하나만 존재
- 5.1부터의 작동 방식
  - `innodb_autoinc_lock_mode = 0` : 모든 경우에 자동 증가 락 사용
  - `innodb_autoinc_lock_mode = 1` : 서버가 INSERT 레코드 건수를 정확히 예측 가능하면 래치(뮤텍스) 사용
  - `innodb_autoinc_lock_mode = 2` : 모든 경우에 래치(뮤텍스) 사용

### 인덱스와 잠금
- InnoDB는 레코드가 아닌 인덱스를 잠금
- 변경해야 할 레코드를 찾기 위해 검색한 인덱스의 레코드에 모두 락을 걸어야 함
- 인덱스가 없느 상태에서 검색한다면 테이블을 풀 스캔하며 모든 레코드 잠금 -> 인덱스 설계 중요

### 레코드 수준의 잠금 확인 및 해제
- 8.0부터의 확인 및 해제 방법
  - `SHOW PROCESSLIST`로 프로세스 목록 조회
  - `performance_schema`의 `data_locks` 테이블과 `data_lock_waits` 테이블 조인해 잠금 대기 순서 확인
  - `performance_schema`의 `data_locks` 테이블의 칼럼으로 어떤 잠금을 가지고 있는지 확인
  - `KILL thread_number`로 스레드 강제 종료하며 락 해제

# 5.4

## 격리 수준

### READ UNCOMMITTED
- 각 트랜잭션의 변경 내용이 COMMIT이나 ROLLBACK 여부에 상관없이 다른 트랜잭션에서 보임
- 어떤 트랜잭션에서 처리한 작업이 완료되지 않았지만 다른 트랜잭션에서 볼 수 있는 DIRTY READ 발생
- 데이터가 나타났다가 사라지는 현상 초래
- 일반적인 DB에서는 거의 사용하지 않음

### READ COMMITTED
- COMMIT이 완료된 데이터만 다른 트랜잭션에서 조회 가능
- COMMIT 전까지 이전 값은 언두 영역에 따로 저장, 조회 시 언두 영역의 백업된 레코드가 보임
- 하나의 트랜잭션 내에서 같은 SELECT 쿼리를 진행했지만 다른 결과가 나오는 문제 발생
- 오라클 DBMS에서 기본적으로 사용
- 온라인 서비스에서 가장 많이 선택

### REPEATABLE READ
- MVCC를 이용해 동일 트랜잭션 내에서는 동일한 결과를 보여줌
- 다른 트랜잭션에서의 변경 작업에 의해 레코드가 보였다 안보였다 하는 PHANTOM READ(PHANTOM ROW) 발생
- SELECT ... FOR UPDATE가 언두 레코드에 쓰기 잠금을 걸 수 없어서 발생
- InnoDB의 스토리지 엔진에서 기본으로 사용
- 바이너리 로그를 가진 MySQL 서버에서는 최소 REPEATABLE READ 이상을 사용해야 함
- InnoDB에서는 갭 락과 넥스트 키 락으로 REPEATABLE READ에서도 PHANTOM READ 거의 미발생

### SERIALIZABLE
- 읽기 작업도 공유 잠금을 획득해야 하고, 다른 트랜잭션은 그 레코드 변경 불가
- 한 트랜잭션에서 읽고 쓰는 레코드를 다른 트랜잭션에서 절대 접근 불가
