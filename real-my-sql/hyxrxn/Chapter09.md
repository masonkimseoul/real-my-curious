# 9.1

### 쿼리 실행 절차
1. SQL Parsing
   - SQL 파서 모듈로 처리
   - 요청된 SQL 문장을 쪼개 서버가 이해할 수 있는 수준으로 분리(파스 트리)
   - 문법적으로 잘못되었다면 여기서 걸러짐
2. 최적화 및 실행 계획 수립
   - 옵티마이저에서 처리
   - 파싱 정보를 확인하며 어떤 테이블로부터 어떤 인덱스를 이용해 읽을지 선택
   - 불필요한 조건 제거
   - 연산 단순화
   - 조인이 있는 경우 순서 결정
   - 조건과 인덱스 통계 정보로 인덱스 결정
   - 레코드를 임시 테이블에 넣고 다시 한번 가공해야 하는지 결정
3. 결정된 테이블의 읽기 순서나 선택된 인덱스로 데이터 가져옴
   - 실행 계획대로 스토리지 엔진에 레코드 요청
   - MySQL 엔진에서 레코드를 조인하거나 정렬

### 옵티마이저 종류
- 규칙 기반 최적화(Rule-based optimizer, RBO)
   - 대상 테이블의 레코드 건수나 선택도 등을 고려하지 않음
   - 내장된 우선순위에 따라 실행 계획 수립
   - 같은 퀴리에 대해서 거의 항상 같은 실행 방법 생성
   - 오래 전부터 거의 사용되지 않음
- 비용 기반 최적화(Cost-based optimizer, CBO)
   - 여러 방법을 만들고 각 단위 작업의 비용 정보와 대상 테이블의 예측된 통계 정보로 실행 계획별 비용 산출
   - 비용이 최소로 소요되는 방식 선택

# 9.2

### 풀 테이블 스캔과 풀 인덱스 스캔
- 풀 테이블 스캔
  - 사용하는 경우
    - 레코드 건수가 너무 작아서 인덱스를 통한 것보다 풀 테이블 스캔이 더 빠른 경우
    - WHERE / ON 절에 인덱스를 이용할 적절한 조건이 없는 경우
    - 옵티마이저가 판단한 조건 일치 레코드 건수가 너무 많은 경우
  - InnoDB
    - 특정 테이블의 연속된 데이터 페이지가 읽히면 백그라운드 스레드에 의해 Read ahead 작업 시작
    - 즉 처음 몇 개의 페이지는 포그라운드 스레드가 실행하지만 특정 시점부터는 백그라운드 스레드로 넘김
    - 백그라운드가 넘겨받는 시점부터는 한 번에 4개 혹은 8개씩 읽으며 계속 수 증가시킴 (최대 64개)
    - `innodb_read_ahead_threshold` 변수로 언제 Read ahead 시작할지 설정
- 풀 인덱스 스캔
  - 예시
    - `SELECT COUNT(*) FROM employees;` 레코드 건수만 필요로 하므로 인덱스를 선택하는 것이 디스크 읽기 횟수 줄임

### 병렬 처리
- 여기서의 병렬 처리는 하나의 쿼리를 여러 스레드가 나눠서 처리하는 것을 의미!
- `innodb_parallel_read_threads` 변수로 하나의 쿼리를 최대 몇 개의 스레드로 처리할지 설정
- 아무론 WHERE 조건 없이 테이블의 전체 건수를 가져오는 쿼리만 병렬 처리 가능

### ORDER BY 처리 (Using filesort)
- 대부분의 SELECT 쿼리에서 정렬 필수적으로 사용
- 정렬 방법
  - 인덱스 이용
    - INSERT, UPDATE, DELETE에서 이미 인덱스가 정렬되어있어 매우 빠름
    - 부가적인 인덱스 추가/삭제 작업이 필요함
    - 디스크 공간 추가적으로 필요
  - Filesort 이용
    - 레코드가 많지 않으면 메모리에서 처리되므로 빠름
    - 대상 건수가 많아질수록 응답 속도가 느림
- 소트 버퍼(Sort buffer)
  - 정렬을 수행하기 위해 할당받은 별도의 메모리 공간
  - 세션 메모리 영역 (여러 클라이언트가 공유할 수 없음)
  - 정렬이 필요한 경우에만 할당
  - `sort_buffer_size` 변수로 최대 버퍼 크기 설정
  - 쿼리의 실행이 완료되면 즉시 반납
  - 레코드의 건수가 많아 소트 버퍼의 공간보다 크다면 레코드를 여러 조각으로 나누어 처리
  - 이때 임시 저장을 위해 디스크 이용
  - 각 버퍼 크기만큼 정렬된 레코드를 다시 병합하며 정렬 수행하는 Multi-merge 진행
  - 수행된 Multi-merge 횟수는 `Sort_merge_passes` 변수에 누적되어 집계
- 정렬 알고리즘
  - Single-pass
    - 특징
      - 정렬에 필요하지 않은 칼럼까지 전부 읽음
      - 정렬이 완료되면 정렬 버퍼의 내용을 그대로 클라이언트로 넘김
      - 더 많은 소트 버퍼 공간 필요
      - 최신 버전에서는 일반적으로 이 방식 사용
      - 정렬 대상 레코드의 크기나 건수가 작은 경우 빠름
    - 종류
      - <sort_key, additional_fields>
        - 정렬 키와 레코드 전체를 가져와 정렬
        - 레코드의 칼럼들은 고정 사이즈로 메모리 저장
      - <sort_key, packed_additional_fields>
        - 정렬 키와 레코드 전체를 가져와 정렬 
        - 레코드의 칼럼들은 가변 사이즈로 메모리 저장
        - 5.7부터 도입
  - Two-pass
    - 특징
      - 대상과 프라이머리 키만 담아서 정렬
      - 이후 다시 프라이머리 키로 테이블을 읽어 칼럼을 가져옴
      - 그래서 테이블을 두 번 읽어야 함
      - 정렬 대상 레코드의 크기나 건수가 많은 경우 빠름
    - 종류
      - <sort_key, rowid>
        - 정렬 키와 레코드의 로우 아이디만 가져와 정렬
- 정렬 처리 방법
  - 인덱스 이용 (Extra 컬럼에 별도 표기 없음)
    - ORDER BY에 명시된 칼럼이 제일 먼저 읽는 테이블에 속하고, ORDER BY의 순서대로 생성된 인덱스가 있어야 함
    - WHERE 절에 첫 번째로 읽는 테이블의 칼럼에 대한 조건이 있다면 그 조건과 ORDER BY는 같은 인덱스를 사용할 수 있어야 함
    - B-Tree 계열의 인덱스가 아닌 해시 인덱스나 전문 검색 인덱스 등에서는 사용할 수 없음
    - 여러 테이블이 조인되는 경우에는 Nested-loop 방식의 조인에서만 사용 가능
  - 조인의 드라이빙 테이블만 정렬 (Extra 컬럼에 Using filesort 표기)
    - 첫 번째 테이블의 레코드만 먼저 정렬한 다음 조인 실행하는 것
    - 조인에서 첫 번째로 읽히는 테이블(드라이빙 테이블)의 칼럼만으로 ORDER BY 절 작성해야 함
  - 임시 테이블을 이용한 정렬 (Extra 컬럼에 Using temporary; Using filesort 표기)
    - 위의 상황이 아닌 패턴의 쿼리에서 사용
    - 정렬해야 할 레코드 건수가 가장 많기 때문에 가장 느림
