# 4.1

## MySQL 서버
- 구성
  - MySQL 엔진
  - 스토리지 엔진
- 스레드 기반 작동
  - 포그라운드(Foreground) or 백그라운드(Background)

### MySQL 엔진
- 요청된 SQL 문장 분석 및 최적화 등
- 서버에 하나
- 구성
  - 커넥션 핸들러
  - SQL 파서
  - 전처리기
  - 옵티마이저

### 스토리지 엔진
- 실제 데이터를 디스크 스토리지에 저장하고, 읽어오는 부분
- 여러 개 동시에 사용 가능
- 지정 방법
  ```sql
    CREATE TABLE test_table (fd1 INT, fd2 INT) ENGINE=INNODB;
    ```

### 핸들러 API
- 핸들러(handler): 스토리지 엔진에 하는 쓰기 또는 읽기 요청
- 핸들러 API: 핸들러에 사용되는 API

### 포그라운드 스레드(클라이언트 스레드)
- MySQL 서버에 접속한 클라이언트의 수 이상 존재
- 주로 각 클라이언트 사용자가 요청하는 쿼리 문장 처리
- 사용자가 커넥션을 종료하면 해당 스레드는 스레드 캐시로 돌아감
- 이 때 스레드 캐시에 일정 개수 이상의 대기 스레드가 있으면 종료시킴
- 캐시의 최대 스레드 개수는 `thread_cache_size` 시스템 변수로 설정

### 백그라운드 스레드
- InnoDB의 경우
  - 인서트 버퍼 병합
  - 로그를 디스크로 기록
  - InnoDB 버퍼 풀의 데이터를 디스크에 기록 (`innodb_write_io_threads`)
  - 데이터를 버퍼로 읽어 옴 (`innodb_read_io_threads`)
  - 잠금이나 데드락 모니터링
  - 쓰기 작업을 버퍼링해서 일괄 처리
  - 데이터가 변경되는 경우 디스크의 데이터 파이로 완전히 저장될 때까지 기다리지 않아도 됨
- MyISAM의 경우
  - 사용자 스레드가 쓰기 작업까지 함께 처리
  - 일반적인 쿼리는 쓰기 버퍼링 기능 사용 불가

## 메모리 할당 및 사용 구조
- 구성
  - 글로벌 메모리 영역
  - 로컬 메모리 영역

### 글로벌 메모리 영역
- MySQL 서버가 시작되며 운영체제로부터 할당
- 일반적으로 클라이언트 스레드 수와 무관하게 하나의 메모리 공간만 할당
- 필요에 따라 2개 이상일 수 있으나 클라이언트 스레드 수와는 무관
- 영역이 N개여도 모든 스레드에 의해 공유
- 대표적인 영역
  - 테이블 캐시
  - InnoDB 버퍼 풀
  - InnoDB 어댑티브 해시 인덱스
  - InnoDB 리두 로드 버퍼

### 로컬 메모리 영역(세션 메모리 영역, 클라이언트 메모리 영역)
- 클라이언트 스레드가 쿼리를 처리하는 데 사용
- 각 클라이언트 스레드별로 독립적으로 할당
- 대표적인 영역
  - 커넥션 버퍼
  - 정렬(소트) 버퍼
  - 조인 버퍼
  - 바이너리 로그 캐시
  - 네트워크 버퍼
- 필요할 때만 공간 할당
  - 커넥션이 열려 있는 동안 계속 할당(커넥션, 결과 버퍼) 
  - 쿼리 실행 시에만 할당(소트, 조인 버퍼)

## 플러그인 스토리지 엔진 모델

## 컴포넌트
- 플러그인의 단점
  - 플러그인끼리 통신 불가
  - 서버의 변수, 함수를 직접 호출하기 때문에 캡슐화 불가
  - 상호 의존 관계 설정 불가로 초기화 어려움
- MySQL 8.0부터는 플러그인 아키텍처를 대체하기 위해 컴포너트 아키텍처 지원

## 쿼리 실행 구조
- 쿼리 파서
  - 토큰으로 분리해 트리 형태의 구조로 만드는 작업 진행
  - 기본 문법 오류 발견 및 오류 메시지 전달
- 전처리기
  - 파서 트리를 기반으로 구조적인 문제점 확인
  - 토큰을 테이블 이름, 칼럼 이름, 내장 함수 등으로 매핑
  - 존재 여부, 접근 권한 확인
- 옵티마이저
  - DBMS의 두뇌 역할
  - 쿼리 문장을 저렴하고 빠르게 처리하는 방법 설정
- 실행 엔진
  - 만들어진 계획대로 핸들러에게 요청
  - 받은 결과를 또 다른 핸들러의 요청으로 연결
- 핸들러(스토리지 엔진)
  - 데이터를 디스크로 저장, 디스크에서부터 읽어옴
  - MyISAM 테이블 조작 시 MyISAM 스토리지 엔진이 되고, InnoDB 테이블 조작 시 InnoDB 스토리지 엔진이 됨
- 쿼리 캐시(Query Cache)
  - 8.0에서부터 제거
- 스레드 풀(Tread Pool)
  - 엔터프라이즈 에디션에서는 지원, 커뮤니티 에디션은 미지원
  - Percona Server에서 지원하는 스레드 풀
    - 플러그인 형태로 작동
    - 스레드 개수를 줄여서 CPU가 제한된 개수의 스레드 처리에만 집중할 수 있게 해 서버의 자원 소모 줄이는 목적
    - 스케줄링 과정에서 CPU 시간ㄴ을 제대로 확보하지 못하면 처리가 더 늦어질 수도 있

## 트랜잭션 지원 메타데이터
- 5.7까지는 파일 기반의 메타데이터 사용
- 테이블의 생성 또는 변경 도중에 서버가 종료되면 일관되지 않은 상태로 남음
- 8.0부터는 테이블의 구조 정보, 스토어드 프로그램의 코드 정보를 InnoDB의 테이블에 저장하도록 개선
- 시스템 테이블과 데이터 딕셔너리 정보를 모두 MySQL DB(mysql.ibd)에 저장
- MyISAM, CSV 등의 스토리지 엔진의 메타 정보는 SDI(Serialized Dictionary Information) 파일 사용

# 4.2

## 프라이머리 키에 의한 클러스터링
- InnoDB
  - 모든 테이블은 PK 값의 순서대로 디스크에 저장 -> PK를 이용한 레인지 스캔은 굉장히 빠름
  - 모든 세컨더리 인덱스는 레코드 주소 대신 PK 값을 논리적인 주소로 사용
- MyISAM
  - 클러스터링 키 미지원
  - PK와 세컨더리 인덱스는 구조적으로 차이 없음

## 외래 키 지원
- InnoDB 스토리지 엔진 레벨에서 지원
- MyISAM, MEMORY 테이블에서는 사용 불가
- `foreign_key_checks` 시스템 변수를 off로 설정하면 외래 키 체크 작업 일시적으로 중지

## MVCC(Multi Version Concurrency Control)
- 멀티 버전: 하나의 레코드에 대해 여러 개의 버전이 동시에 관리됨
- 일반적으로 레코드 레벨의 트랜잭션을 지원하는 DBMS가 지원하는 기능
- 잠금을 사용하지 않는 일관된 읽기를 제공하는 것이 가장 큰 목적
- InnoDB는 언두 로그(Undo log)를 이용해 지원

### 예시
1. UPDATE 실행 -> InnoDB 버퍼 풀 업데이트
2. COMMIT 혹은 ROLLBACK 이전에 SELECT
3. 반환
   - READ_UNCOMMITTED: 버퍼 풀이 가지고 있는 데이터
   - 그 이상의 격리 수준: 변경되기 이전의 언두 영역 데이터
4. 이후
   - COMMIT 실행: 지금의 상태를 영구적인 데이터로
   - ROLLBACK 실행: 언두 영역의 백업 데이터를 InnoDB 버퍼 풀로 복구

### 잠금 없는 일관된 읽기(Non-Locking Consistent Read)
- SERIALIZABLE이 아니면 SELECT 작업은 항상 바로 실행되는 것
- 트랜잭션이 오랜 시간 활성 상태가 되는 경우 언두 로그를 유지해야 하기 때문에 서버가 느려질 수 있음

## 자동 데드락 감지
- InnoDB는 잠금 대기 목록을 그래프 형태로 관리(Wait-for-List)
- 데드락 감지 스레드가 주기적으로 잠금 대기 그래프 검사
- 교착 상태라면 그 중 언두 로그 가장 적게 가진 트랜잭션 강제 종료
- `innodb_deadlock_detect`를 off로 설정하면 데드락 감지 스레드 미작동
- `innodb_lock_wait_timeout`으로 데드락 상황에서 일정 시간이 지나면 요청 실패 및 에러 메시지 반환하게 설정

## 자동 장애 복구
- 설정 파일의 `innodb_force_recovery` 변수로 서버가 시작될 때 스토리지 엔진이 데이터 파일이나 로그 파일의 손상 여부 검사를 선별적으로 진행하게 설정
  - 로그 파일 손상 -> 6으로 설정
  - 데이터 파일 손상 -> 1로 설정
  - 모르겠음 -> 1~6으로 변경해보며 재시작

## InnoDB 버퍼 풀
- 디스크의 데이터 파일이나 인덱스 정보 캐시해두는 공간
- 쓰기 작업 지연으로 일괄 처리할 수 있게 해주는 버퍼 역할도 함
- 내부적으로 128MB 청크 단위로 관리
- `innodb_buffer_pool_instances`로 버퍼 풀 분리해서 관리 가능
  - 각 버퍼 풀은 버퍼 풀 인스턴스라고 표현
  - 기본적으로 버퍼 풀 인스턴스는 8개로 초기화
- 버퍼 풀을 페이지 크기로 쪼개어 해당 페이지를 읽어서 저장

### 크기
- 5.7부터 버퍼 풀 크기 `innodb_buffer_pool_size`로 동적 조절 가능
- 적절히 작은 값으로 설정해 조금씩 증가시키는 방법이 최적
- OS의 전체 메모리 공간별 초기 설정 시 권장 방법
  - 8GB 미만: 50% 정도를 버퍼 풀로 설정
  - 8GB 이상: 50%에서 시작, 서서히 올려서 최적점 확인
  - 50GB 이상: 15~30GB 정도를 남기고 나머지 할당
- 크기를 줄이는 작업은 서비스 영향도가 큼
- 크기별 버퍼 풀 인스턴스 개수
  - 1GB 미만: 1개
  - 40GB 이하: 기본값
  - 40GB 초과: 버퍼 풀 인스턴스당 5GB 정도로 설정

### 구조
- 프리(Free) 리스트
  - 실제 사용자 데이터로 채워지지 않은 비어 있는 페이지 목록
  - 쿼리가 새롭게 디스크의 데이터 페이지를 읽어와야 하는 경우 사용
- LRU(Least Recently Used) 리스트
  - 한 번 읽어온 페이지를 최대한 오랫동안 버퍼 풀에 유지해 디스크 읽기를 최소화하는 것이 목적
- 플러시(Flush) 리스트
  - 디스크로 동기화 되지 않은 데이터를 가진 페이지(더티 페이지)의 변경 시점 기준의 페이지 목록 관리

### 데이터 찾는 과정
1. 필요한 페이지가 버퍼 풀에 있는지 검사
   1. 어댑티브 해시 인덱스 이용해 페이지 검색
   2. 테이블의 인덱스를 이용해 페이지 검색
   3. 버퍼 풀에 페이지 있다면 해당 페이지 포인터를 MRU(Most Recently Used) 방향으로 승급
2. 디스크에서 필요한 페이지를 버퍼 풀에 적재, 그 페이지의 포인터를 LRU 헤더 부분에 추가
3. LRU 헤더 부분의 페이지가 실제로 읽히면 MRU 헤더 부분으로 이동
4. 버퍼 풀의 페이지는 나이 부여, 오래 사용되지 않아 나이가 많아지면 버퍼 풀에서 제거
5. 필요 데이터가 자주 접근되면 해당 페이지 인덱스 키를 어댑티브 해시 인덱스에 추가
