8.1 디스크 읽기 방식

HDD(Hard Disk Drive) vs SSD(Solid State Drive)

기계식 vs 전자식

기존 하드의 플래터(원판)을 제거하고 플래시 메모리를 대신 장착 -> 기계식 회전이 필요없어 훨씬 빠름

순차 I/O -> ssd가 조금 빠르거나 비슷함
랜덤 I/O -> 훨씬 빠름

순차 I/O는 디스크에 기록할 위치를 찾기 위해서 디스크 헤더를 한 번 움직임
랜덤 I/O는 데이터가 많을 수록 더 잦은 헤더 움직임이 발생

ssd에서도 throughput 이 랜덤이 순차에 비해 좀 떨어짐

8.2 인덱스란

'색인'
칼럼의 값을 키로, 레코드가 저장된 주소를 값으로 key-value 쌍
중요한것은 정렬 칼럼의 값을 미리 정렬해서 보관
항상 정렬된 상태를 유지

장단점: 저장될 때 마다 정렬을 유지해야 해 insert, update, delete 등이 느려지지만 select가 매우 빠름

저장 성능과 읽기 속도의 조절, where 절에 들어간다고 모두 인덱스화 시키면 인덱스 크기가 비대해져 역효과


8.3 B-TREE 인덱스

https://www.cs.usfca.edu/~galles/visualization/BTree.html

balanced-tree

* 구조 및 특성

루트 노드와 리프 노드, 그 사이의 브랜치 노드로 이루어짐
인덱스의 리프 노드는 항상 실제 데이터 레코드를 찾아가기 위한 주소값

인덱스의 키값은 모두 정렬되어 있지만, 데이터 파일의 레코드는 정렬되어 있지 안ㅇ흠

대부분 RDBMS 의 데이터 파일에서 레코드는 임의 순서로 저장, InnoDB 테이블에서 레코드는 클러스터되어 저장되므로 프라이머리 키 순서로 정렬되어 저장

MyISAM -> 리프 노드(페이지) -> 데이터 파일 주소
InnoDB -> 리프 노드(페이지) -> (루트 노드 -> 브랜치 노드 -> 리프 노드)

* 인덱스 키 추가 및 삭제

인덱스 키 추가

새로운 키 값이 B-Tree 에 저장될 때 적절한 위치를 찾아야 함 -> 위치 결정 시 레코드의 키 값과 주소 정보를 리프 노드에 저장, 리프 노드가 꽉 찬 경우 리프 노드 분리 작업 필요, 상위 브랜치 노드까지 처리해야 함 -> 쓰기 작업 비용 높음

InnoDB 엔진의 경우 다른 것과 다르게 insert 문 실행 시 즉시 새로운 키 값을 b-tree 인덱스에 넣지 않을 수 있음(지연), 프라이머리 키 혹은 유니크 인덱스의 경우 중복 체크 필요해 즉시 추가 혹은 삭제

인덱스 키 삭제 -> 키 값이 저장된 리프 노드 찾아 삭제 마크(디스크 I/O 필요), MySQL 5.5 이상부터 버퍼링되어 지연 삭제 가능

인덱스 키 변경 -> 변경된 값의 위치를 찾아야 하므로 키 값 삭제 - 이후 다시 추가

인덱스 키 검색 -> 트리 탐색, b-tree 인덱스를 이용하면 완전 일치 혹은 left-most part 일치 로 검색 가능, 인덱스의 키 값에 변형이 가한 형태로는 빠르게 찾기 불가능
특히 InnoDB에서 레코드 잠금, 넥스트 키 락이 검색을 수행한 인덱스를 잠근 후 테이블의 레코드를 잠그기 때문에 인덱스를 잘못 걸면 락이 잘못 걸릴 수 있음

* 인덱스 사용에 영향을 미치는 요소

인덱스를 구성하는 칼럼의 크기, 레코드의 건수, 유니크한 인덱스 키 값의 개수 등

인덱스 키 값의 크기 -> 페이지 혹은 블록 단위로 디스크에 데이터를 저장한다. 즉, 디스크 읽기 쓰기의 최소 작업 단위이면서 InnoDB 스토리지 엔진의 버퍼 풀에서 데이터를 버퍼링하는 기본 단위 -> 루트, 브랜치, 리프 노드 구분 또한 페이지 단위

MySQL에서 B-Tree 의 자식 노드 수는 인덱스 페이지 크기와 키 값의 크기에 따라 결정 MySQL 5.7 부터 `innodb_page_size`를 통해 4~64KB 로 설정가능, 기본 16KB 
인덱스 키 값 증가 -> 페이지에 담을 수 있는 인덱스 키가 줄어듬 -> 더 많은 페이지 필요
b-tree 깊이 -> 디스크로 랜덤 I/O 를 몇 번 수행해야 하는가 -> 적을 수록 좋음 <- 인덱스 크기가 커지면 한 깊이에 담을 개수도 줄어듬
선택도(Selectivity) or 기수성(Cardinality) -> 유니크한 인덱스 키 값의 수 -> 중복된 값이 많을 수록 검색 대상이 늘어남(단, 정렬이나 그루핑 등의 작업을 위해 선택도가 좋지 않아도 인덱스를 만드는 것이 나을 수 있음, 상황에 따라 고려)
읽어야 하는 레코드의 건수 -> 일반적으로 인덱스를 통해 레코드 1건을 읽는 것이 테이블에서 직접 읽는 것 보다 4~5배 비용이 더 든다고 예측함. 즉, 인덱스를 통해 읽어야 하는 건수가 전체의 20~25%가 넘는다면 테이블을 직접 읽어 필터링하는 것이 효율적일 수 있음

* 인덱스를 통한 데이터 읽기
인덱스 레인지 스캔(탐색(index seek) -> 스캔(index scan) -> 레코드가 저장된 페이지 불러와 레코드 읽고 반환) -> 검색해야 할 인덱스의 범위가 결정되었을 때 사용, 루트 -> 브랜치 -> 리브까지 비교하면서 들어가, 레코드의 시작점을 찾아 스캔, 리프 노드의 끝까지 읽었다면 다음 리프 노드로 넘어감
어떤 방식으로 스캔하든, 해당 인덱스를 구성하는 칼럼의 정순 혹은 역순으로 정렬된 상태로 레코드를 가져옴
리프 노드 스캔 시 검색 조건에 일치하는 건들은 데이터 파일로부터 레코드를 읽어오는 과정 추가로 필요(한 건 단위로 랜덤 I/O) 

인덱스 풀 스캔(인덱스의 처음부터 끝까지 모두 읽는 방식) 대표적으로 조건절에 사용된 칼럼이 인덱스의 첫 번째 칼럼이 아닌경우
테이블을 처음부터 읽는 것 보다 인덱스만 읽는 것이 효율적(리프 노드의 시작 혹은 끝에서부터 스캔)

루스 인덱스 스캔(loose, 앞의 두 방법은 tight index scan)
인덱스 레인지 스캔과 비슷하지만, 중간에 필요치 않은 인덱스 키 값은 skip 하고 넘어감, 일반적으로 group by 혹은 max, min 함수에 대해 최적화를 하는 경우 사용

인덱스 스킵 스캔(루스 인덱스 스캔과 같은 방식으로 읽고, 인덱스에 존재하는 모든 값을 먼저 추출한 뒤 그 결과로 인덱스 스킵 스캔 시행)
MySQL 8.0 부터 도입되어 where 조건절에 조건이 없는 인덱스의 선행 칼럼의 유니크 값의 개수가 적어야 하고 쿼리가 인덱스에 존재하는 칼럼만으로 처리 가능해야 함

* 다중 칼럼 인덱스
인덱스의 두 번째 칼럼은 첫 번째 칼럼에 의존해 정렬되어 있음, 칼럼 순서에 따라 정렬이 달라짐

* 정렬 및 스캔 방향
인덱스를 어떤 방향으로 읽을 지는 옵티마이저가 실시간으로 만들어내는 실행 계획에 따라 결정됨

인덱스를 생성하는 시점에 정렬됨, MySQL 5.7 까진 칼럼 단위로 정렬 순서 혼합 불가능, MySQL 8.0 부터 가능
`CREATE INDEX ix_teamname_userscore ON employees (team_name ASC, user_score DESC);`
인덱스 스캔 방향은 정렬 순서에 따라 옵티마이저가 알아서 선택
페이지 잠금이 인덱스 정순 스캔에 적합한 구조, 페이지 내에서 인덱스 레코드가 단방향으로 연결된 구조 -> 역순 스캔이 정순 스캔보다 느림

* 가용성, 효율성
비교 조건에서: 작업 범위 결정 조건 vs 필터링 조건 -> 작업 범위 결정 조건이 많을 수록 쿼리 처리 성능 올라감
가용성: b-tree 인덱스는 left-most 에서부터 오른쪽 값이 정렬됨
=> not-equal, like '%???', 다른 연산자로 인덱스 칼럼이 변형된 후 비교, 데이터 타입이 서로 다른 비교, 문자열 데이터 타입의 콜레이션이 다른 경우 등에서 b-tree 인덱스 사용할 수 없음
다중 칼럼으로 만들어진 인덱스에서(INDEX ix_test (col1, col2, ..., coln)):
   col1 칼럼에 대한 조건이 없는 경우, col1 칼럼의 비교 조건이 인덱스 사용 불가 조건인 경우에 작업 범위 결정 조건으로 인덱스를 사용하지 못함
   col1~col(i-1) 칼럼까지 동등 비교 형태, coli가 (동등 비교, 크다 혹은 작다, like 좌측 일치 패턴)인 경우 col1~coli  까지 작업 범위결정 조건으로 사용, col(i+1)부터 체크 조건으로 사용
