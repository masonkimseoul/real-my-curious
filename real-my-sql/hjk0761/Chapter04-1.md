## `MySQL 서버 구조`

- MySQL 엔진: 요청된 SQL 을 분석하고 최적화
    - 커넥션 핸들러
    - SQL 파서 및 전처리기
    - 옵티마이저
    - 서버 당 하나만 존재

- 스토리지 엔진: 실제 데이터를 디스크 스토리지에 저장 및 읽어오는 부분
    - InnoDB, MyISAM 및 커스텀 등 여러 개 존재
    - 테이블 별로 처리할 엔진 선택 가능
    - 핸들러 API: MySQL 엔진의 쿼리 실행기에서 데이터 읽기/쓰기가 필요할 떄에 각 스토리지 엔진에 핸들러 API 를 통해 요청한다.

## 4.1 MySQl 엔진 아키텍처

### 스레드 기반
- 포그라운드(클라이언트 스레드)
    - 최소 MySQL 에 접속된 클라이언트 수만큼 존재
    - 각 클라이언트가 요청하는 쿼리문 처리
    - 스레드 캐시 시스템 사용
    - InnoDB 테이블의 경우 데이터 버퍼와 캐시만 처리, MyISAM 테이블은 디스크 쓰기까지 모두 처리
- 백그라운드 스레드
    - InnoDB의 경우 버퍼 병합 스레드, 로그 및 버퍼 풀에서의 디스크 쓰기 스레드, 버퍼 읽기 스레드, 락 모니터링 스레드 등
    -InnoDB 의 경우 쓰기 지연 작업이 가능 -> 읽기는 다른 작업을 기다릴 필요가 없음

### 메모리 구조
- 글로벌 메모리 영역
    - 클라이언트 스레드 수와 무관하게 하나의 공간만 할당, 모든 스레드에 공유
    - 테이블 캐시
    - InnoDB 버퍼 풀
    - InnoDB 어댑티브 해시 인덱스
    - InnoDB REDO 로그 버퍼
- 로컬 메모리 영역(세션 메모리 영역)
    - 클라이언트 스레드가 쿼리를 처리하는 데 사용하는 영역
    - 클라이언트 스레드 별로 독립적으로 할당 및 공유하지 않음
    - 정렬 버퍼, 조인 버퍼, 로그 캐시, 네트워크 버퍼 등
    - 커넥션이 열려있는 동안 계속 할당되기도, 필요할 떄 할당 및 해제하기도 한다.

### 플러그인 및 컴포넌트
- 플러그인
    - 스토리지 엔진, 파서, 인증 등 다양한 기능
- 컴포넌트
    - 플러그인의 단점(플러그인끼리 소통 불가, 캡슐화 불가, 초기화 힘듦)을 극복하고자 나온 기능

### 쿼리 실행 구조
1. 사용자 요청
2. 쿼리 파서에서 파싱 - 트리 구조로 변환(문법 오류 감지)
3. 전처리기 - 토큰 매핑, 권환 확인 등(구조적 오류 감지)
4. 옵티마이저 - 가장 저렴한 비용으로 처리할지 결정
5. 실행 엔진 - 옵티마이저의 선택대로 핸들러를 호출
6. 핸들러 - 스토리지 엔진으로 요청을 전달하여 실제 쿼리 수행

차후 확인

데이터 변경 시 캐시를 다 바꿔주어야 해서 삭제된 기능

### 스레드 풀
유휴 스레드의 하한과 상한을 정해 자원 소모 아끼는 것이 목적

## InnoDB 스토리지 엔진 아키텍쳐

### 프라이머리 키 클러스터링
프라이머리 키를 키값 순서로 디스크에 저장, 세컨더리 인덱스는 프라이머리 키의 값을 논리주소로 사용 -> 범위 검색 빠름

따라서 쿼리 실행 계획에서 프라이머리 키가 선택될 확률이 높음

MyISAM 스토리지 엔진은 클러스터링 제공 X

### 외래 키 지원
InnoDB 스토리지 엔진에서 제공하는 기능

외래 키 관게 체크 작업을 껐다 킬 수 있음(`foreing_key_ckecks`)

### MVCC(Multi Version Concurrency Controll)
잠금을 사용하지 않는 일관된 읽기를 제공하기 위함

InnoDB 는 UNDO 로그를 통해 이를 구현

Update, Delete 등이 일어나면 이전 결과는 UNDO 로그에 쌓이고, 버퍼 풀에서 변화가 일어남

커밋 혹은 롤백 이전까진 두 상태가 존재하기 때문에 multi version 이라고 명함

### 잠금 없는 일관된 읽기
격리 수준이 Serializable 이 아닌경우, 읽기는 대기 없이 바로 실행됨

Read_uncommitted 인 경우는 버퍼 풀에서, 그 외는 언두 로그에서 읽기를 수행함

### 자동 데드락 감지
wait-for list 로 잠금 대기 목록을 관리함

InnoDB 스토리지 엔진은 데드락 감지 스레드가 쥑적으로 그래프를 검사해 교착 상태에 빠진 트랜잭션 중 언두 로그가 적은 트랜잭션을 롤백함

데드락 감지 여부를 정하는 시스템 변수(`innodb_deadlock-detect`) 를 끈다면 잠금 획득 시간 제한(`innodb_lock_wait_timeout`) 을 짧게 설정하기를 추천

### 장애 복구
기본적으로 MySQL 서버 시작 시 자동 복구 실행, 실패했다면 서버 종료

이떄 MySQL 의 `innodb_force_recovery` 변수를 1 부터 6 까지 바꿔가면서 복구를 시도함

숫자가 높아질수록 더 큰 범주의 복구를 시도함

### InnoDB 버퍼 풀
디스크에 데이터 파일이나 인덱스 정보 등을 메모리에 캐시하는 공간

이상적으론 작은 값부터 늘려 나가면서 설정하는 것이 좋음

일반적으로 8GB 이하의 운영체제라면 50% 정도만 버퍼 풀로 설정하고, 그 이상이라면 50% 부터 시작해 올려나간다.

동적 할당은 `innodb_buffer_pool_size`를 통해 설정 가능

128MB 의 청크 단위로 크기를 줄이거나 늘림

버퍼 풀은 `innodb_page_size`개로 나누어 필요할 때 마다 각 페이지를 사용함

- LRU list: LRU(Least Recently Used) 와 (Most Recently Used) 가 결합된 형태, 페이지를 읽을 수록 New sublist 의 head 쪽으로, 사용되지 않을수록 Old sublist 의 tail 쪽으로 밀려나 삭제됨
- Flush list: 디스크와 동기화 되지 않은 데이터를 가진 페이지(더티 페이지)를 관리함
- Free list: 빈 페이지 목록
