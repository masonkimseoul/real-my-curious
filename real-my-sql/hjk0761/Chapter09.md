9 옵티마이저와 힌트

개요
MySQL 서버로 요청된 쿼리는 결과는 동일하지만 내부적으로 쿼리를 최적으로 실행하기 위해 통계 정보를 참조하고, 기본 데이터를 비교해 최적의 실행 계획을 수립하는 작업이 필요하다. 이를 옵티마이저가 담당한다.
MySQL 에서는 `EXPLAIN`이라는 명령으로 실행 계획 확인 가능

9.1 개요
## 쿼리 실행 절차
1. SQL 파싱 - 사용자로부터 요청된 SQL 쿼리를 파싱해 MySQL 서버가 이해할 수 있는 형태로 변환(파싱 트리), SQL 파서 모듈이 처리, SQL 파스 트리 반환
2. 최적화 및 실행 계획 수립 - 파싱 정보를 확인하면서 어떤 테이블로부터 읽고 어떤 인덱스를 사용해 읽을지 선택, 불필요한 조건 제거 및 복잡한 연산 단순화, 조인이 있는 경우 읽을 테이블 순서 결정, 각 테이블에 사용된 조건과 인덱스 통계 정보를 사용해 사용할 인덱스 결정, 가져온 레코드들을 임시 테이블에 넣도 다시 가공해야 하는지 결정, 옵티마이저에서 처리
3. 테이블의 읽기 순서와 인덱스를 이용해 스토리지 엔진으로부터 데이터를 가져옴, 1, 2단계와 달리(MySQL 엔진에서 처리) MySQL 엔진과 스토리지 엔진 동시 참여해 처리

## 옵티마이저의 종류

비용 기반 최적화(Cost-based Optimizer, CBO) vs 규칙 기반 최적화(Rule-based Optimizer, RBO)
RBO: 대상 테이블의 레코드 건수나 선택도 등을 고려하지 않고 옵티마이저에 내장된 우선순위에 따라 실행 계획을 수립, 통계 정보를 조사하지 않기 때문에 같은 쿼리에서 거의 같은 실행 방법 산출
CBO: 쿼리를 처리하는 여러 방법을 만들고, 각 단위 작업의 비용 정보와 대상 테이블의 예측된 통계 정보를 이용해 비용을 산출
함, 이를 기반으로 최소로 소요되는 처리 방식을 선택

9.2 기본 데이터 처리

## 풀 테이블 스캔 / 풀 인덱스 스캔

풀 테이블 스캔은 인덱스를 사용하지 않고 테이블의 데이터를 처음부터 끝까지 읽어서 요청된 작업을 처리하는 작업
- 테이블의 레코드 건수가 너무 작아서 인덱스를 통해 읽는 것보다 풀 테이블 스캔이 따른 경우(일반적으로 테이블이 페이지 1개로 구성된 경우)
- WHERE 이나 ON 절에 인덱스를 이용할 수 있는 적절한 조건이 없는 경우
- 인덱스 레인지 스캔을 사용할 수 있는 쿼리라고 하더라도 옵티마이저가 판단한 조건 일치 레코드 건수가 너무 많은 경우

대부분의 DBMS 에선 풀 테이블 스캔을 실행할 때에 여러 개의 블록이나 페이지를 읽어오는 기능 내장, 하지만 MySQL의 MyISAM 스토리지 엔진에선 한 페이지씩 가져와서 많은 디스크 읽기를 수행하게 됨. InnoDB 스토리지 엔진에선 특정 테이블의 연속된 데이터 페이지가 읽히면 백그라운드 스레드에 의해 Read-ahead 작업이 자동으로 시작, InnoDB 버퍼 풀에 미리 가져다 두게 됨. Read-ahead 를 실행하는 임계값을 `innodb_read_ahead_threshold` 시스템 변수를 통해 조정(포그라운드 스레드에서 해당 변수만큼의 연속된 페이지가 읽힌 경우 Read-ahead 실행). 이는 풀 인덱스 스캔에서도 동일하게 사용

## 병렬 처리
MySQL 8.0 버전부터, 한정된 용도에서 쿼리 병렬 처리가 가능
`innodb_parallel_read_threads` 시스템 변수를 통해 하나의 쿼리를 최대 몇 개의 스레드를 이용할 지 정할 수 있음.
아직 이에 대한 힌트나 옵션이 없어, WHERE 절 없이 단순히 테이블의 전체 건수를 가져오는 쿼리만 병렬 처리가 가능함.

## ORDER BY 처리
대부분의 SELECT 쿼리에서 정렬은 필수적으로 사용됨.
대량의 데이터 조회가 아닌 경우 조회 쿼리에 레코드 정렬 요건이 포함되어 있을 것임.
### 정렬을 처리하는 방법
인덱스 이용: INSERT, UPDATE, DELETE 쿼리 실행 시 이미 인덱스가 정렬되어 있어 순서대로 읽기만 수행하면 되어 빠름, 하지만 해당 작업 시 부가적인 인덱스 추가/삭제 작업이 필요해 느려질 수 있고, 인덱스를 위한 디스크 공간 필요, 인덱스 개수가 늘어날수록 InnoDB 버퍼 풀을 위한 메모리 필요
Filesort 이용: 인덱스 생성이 필요없어 인덱스 사용시 단점이 장점이 되고, 정렬할 레코드가 많지 않다면 메모리에서 Filesort 가 처리되므로 충분한 속도, 정렬 작업이 쿼리 실행 시 수행되므로 레코드 대상 건수가 많이질수록 응답 느려짐

Filesort 를 이용해 정렬했는지는 실행 계획의 `Extra` 칼럼에 "Using filesort" 메시지로 표시됨.

### 소트 버퍼
정렬 수행을 위한 별도의 메모리 공간을 의미함.
정렬이 필요한 경우에만 할당되고, 쿼리 실행이 완료되면 즉시 시스템으로 반납됨.
최대 `sort_buffer_size` 의 크기에서 가변적으로 레코드 크기에 따라 증가함.

문제점
정렬해야할 레코드 건수가 소트 버퍼로 할당된 공간보다 크다면 레코드를 조각으로 나눠서 처리하고, 임시 저장을 위해 메모리 사용. 정렬 수행, 이전 결과와 병합 및 임시 저장을 반복(Multi-merge)하여 정렬을 수행함(`Sort_merge_passes` 에 의해 multi-merge 횟수가 집계됨).

저자의 경험상 일반적인 트랜잭션 처리용 소트 버퍼 크기는 56KB ~ 1MB 로 구성. 이들은 세션 메모리 영역이기 때문에 클라이언트마다 할당되기 때문에 무작정 커질 수 없음.

### 정렬 알고리즘
정렬 시 레코드 전체를 소트 버퍼에 담을지(싱글 패스), 정렬 기준 칼럼(투 패스)만 담을지로 나뉨.
```
mysql> SELECT * FROM INFORMATION_SCHEMA.OPTIMIZER_TRACE \G
...

    "filesort_summary": {
        ...
        "sort_mode": //여기서 확인 가능
    }
```
sort_mode:
- <sort_key, rowid> : 정렬 키와 레코드의 row id 만 가져와서 정렬(투 패스)
- <sort_key, additional_fields> : 정렬 키와 레코드 전체를 가져와서 정렬, 레코드의 칼럼들은 고정 사이즈로 메모리 저장(싱글 패스)
- <sort_key, packed_additional_fields> : 위와 동일하지만, 레코드의 칼럼들은 가변 사이즈로 메모리 저장(싱글 패스)

싱글 패스는 테이블을 한 번만 읽어도 되지만, 정렬에 필요없는 칼럼도 가지고 와야해 더 많은 소트 버퍼가 필요.
투 패스는 정렬 대상 칼럼과 프라이머리 키 값만 먼저 읽고 정렬한 다음, 정렬 순으로 다시 테이블을 읽어야 하지만 소트 버퍼 공간이 덜 필요.
일반적으로 싱글 패스를 사용하나, 레코드의 크기가 `max_length_for_sort_data` 보다 클 때, BLOB 나 TEXT 타입의 칼럼이 SELECT 대상에 포함될 때 투 패스를 사용.

### 정렬 처리 방법
ORDER BY 사용되면 아래 3가지 중 하나로 정렬이 처리됨. 아래로 갈 수록 처리 속도 떨어짐.
- 인덱스를 사용한 정렬: 실행 계획의 Extra 칼럼에 표기 없음.
    반드시 ORDER BY 에 명시된 칼럼이 제일 먼저 읽는 테이블(조인이 사용된 경우 드라이빙 테이블)에 속하고, ORDER BY 의 순서대로 생성된 인덱스가 존재해야 함.
    WHERE 절에 첫 번째로 읽는 테이블의 칼럼에 대한 조건이 있따면 그 조건과 ORDER BY 는 같은 인덱스를 사용할 수 있어야 함.
    B-Tree 계열의 인덱스가 아닌 경우 인덱스를 사용한 정렬이 불가능(R-Tree 는 가능).
    여러 테이블이 조인된 경우 nested-roop 방식의 조인에서만 적용 가능
    실제 인덱스의 값이 정렬되어 있기 때문에 인덱스 순서대로 읽기만 하면 됨.
    단, 조인을 사용한 경우에 조인 버퍼가 사용되면 순서가 달라질 수 있음
- 조인에서 드라이빙 테이블만 정렬: 실행 계획의 Extra 칼럼에 "Using filesort".
    조인에서 첫 번째로 읽히는 테이블(드라이빙 테이블)의 칼럼만으로 ORDER BY 절을 작성해야 함.
- 조인에서 조인 결과를 임시 테이블로 저장 후 정렬: 실행 계획의 Extra 칼럼에 "Using temporary; Using filesort".
    조인의 드라이빙 테이블만 정렬하는 경우가 아니면 임시 테이블 사용 필요

#### 쿼리가 처리되는 방식
- 스트리밍 방식: 서버 쪽에서 처리할 데이터가 얼마인지에 관계없이 조건에 일치하는 레코드가 검색될 때마다 바로 클라이언트로 전송
    이렇게 처리되는 경우 첫 레코드를 전달받기 까지 응답 시간이 짧아지고, LIMIT 같이 결과 건수를 제한하는 조건이 전체 쿼리 실행 시간을 줄여줌.
- 버퍼링 방식: ORDER BY 혹은 GROUP BY 는 모든 해당하는 레코드를 가져온 이후에 처리해야 하기 때문에 스트리밍 방식 사용 불가능.
    서버에서 처리가 다 될 때까지 클라이언트는 응답 대기(버퍼링).
인덱스를 사용한 정렬만 스트리밍의 형태, 나머지 정렬 처리 방식은 버퍼링 방식이다.
따라서 LIMIT 과 같은 쿼리는 인덱스를 사용한 정렬이 가능할 때에만 처리 속도를 올려줄 수 있음.

### 정렬 관련 상태 변수
MySQL 서버에서 주요 작업에 대한 실행 횟수를 저장.
```
mysql> FLUSH STATUS;
mysql> SHOW STATUS LIKE 'Sort%';
```
`Sort_merge_passes`: multi-merge 처리 횟수
`Sort_range`: 인덱스 레인지 스캔을 통해 검색된 결과에 대한 정렬 작업 횟수
`Sort-scan`: 풀 테이블 스캔을 통해 검색된 결과에 정렬 작업 횟수.
`Sort-rows`: 지금까지 정렬한 전체 레코드 건수

## GROUP BY 처리
앞서 본 것 처럼, GROUP BY 는 ORDER BY와 같이 스트리밍 처리를 불가능하게 하는 작업.
GROUP BY 의 결과에 대한 필터링으로 HAVING 절 사용 가능.
GROUP BY 에 사용된 조건은 인덱스를 사용하여 처리할 수 없으므로 HAVING 절을 튜닝하려고 인덱스 생성할 필요 없음.

### 처리 방법
- 인덱스 스캔을 이용하는 GROUP BY(타이트 인덱스 스캔):
    드라이빙 테이블에 속한 칼럼만 이용하여 그루핑하는 경우 GROUP BY 칼럼으로 이미 인덱스가 있다면 이를 차례로 읽으면서 그루핑 작업을 수행하고 조인 처리.
    실행 계획의 Extra 칼럼에 별다른 표시 없음.
- 루스 인덱스 스캔을 이용하는 GROUP BY:
    인덱스의 레코드를 건너뛰면서 필요한 부분만 읽어서 가져오는 방식.
    실행 계획의 Extra 칼럼에 "Using index for group-by" 표기.
    단일 테이블에 대해 수행되는 GROUP BY 처리에서만 사용 가능, Prefix-index 는 사용 불가능.
    유니크한 값이 적을 수록 성능 향상.
    임시 테이블 필요 없음.
- 임시 테이블을 사용하는 GROUP BY:
    기준 칼럼이 드라이빙 테이블이든 아니든 인덱스를 사용하지 못하는 경우.
    실행 계획의 Extra 칼럼에 "Using temporary" 표기("Using fildsort" 가 없는 이유는 MySQL 8.0 부터 묵시적 정렬이 없어졌기 때문).
    내부적으로 GROUP BY 절의 칼럼들로 구성된 유니크 인덱스를 가지는 임시 테이블을 만들어 중복 제거 및 집합 함수 연산을 수행하고 이후 조인 결과를 한 건씩 가져와 임시 테이블에 중복 체크하면서 INSERT 혹은 DELETE 수행.

## DISTINCT 처리

### 처리 방법
- 집합 함수(MIN(), MAX(), COUNT() 등) 없이 단독 사용:
    GROUP BY 와 동일한 방식으로 처리.
    DISTINCT 키워드는 조회되는 모든 칼럼에 영향을 미침. 단, 집합 함수와 함께 사용되면 다름.
- 집합 함수와 함께 사용:
    집합 함수의 인자로 전달된 칼럼값이 유니크한 것들만 가져옴.

## 내부 임시 테이블 활용
지금까지의 임시 테이블("CREATE TEMPORARY TABLE" 을 사용한, 이전의 모든 임시 테이블 예제들)과는 달리, MySQL 엔진이 스토리지 엔진으로부터 받아온 레코드를 정렬하거나, 그루핑할 때 사용.
처음에 메모리에 생성되었다가 테이블 크기가 커지면 디스크로 옮겨짐. 특정 케이스는 바로 디스크에 생성.
MySQL 8.0 이전의 경우 MEMORY 스토리지 엔진을 통해서만 임시 테이블이 메모리를 사용할 수 있었고, 디스크에 저장되는 경우 MyISAM 만을 사용하게 됨.
이는 메모리에 생성되는 경우 TempTable 이라는 스토리지 엔진으로, 디스크에 생성되는 경우 InnoDB 스토리지 엔진을 사용하도록 개선됨.
MEMORY 스토리지 엔진 -> 가변 길이 타입 지원 안됨, MyISAM 스토리지 엔진 -> 트랜젝션 지원 안됨.
`internal_tmp_mem_storage_engine` 을 통해 MEMORY 와 TempTable 을 고를 수 있고, 기본값은 TempTable.
`temptable_max_ram` 을 통해 TempTable 이 최대로 사용가능한 메모리 공간을 제어(기본 1GB)
이 최대값을 넘은 경우 디스크로 저장, `temptable_use_mmap`(기본값 ON) 을 통해 해당 TempTable 이 MMAP 파일로 저장될지, InnoDB 테이블로 기록될지를 정함.
이때 디스크에 생성되는 임시 테이블은 `tmpdir` 에 정의된 디렉터리에 저장됨.
디스크에 임시 테이블이 생성되는 경우 파일 열기 작업 이후 바로 파일 삭제도 같이 실행.
앞서 메모리를 거쳐 디스크 임시 테이블이 되는 경우와 달리, 처음부터 디스트 임시 테이블로 가는 경우는 `internal_tmp_disk_storage_engine`(기본값 InnoDB)을 통해 저장.

임시 테이블이 필요한 쿼리
- ORDER BY 와 GROUP BY 에 명시된 칼럼이 다른 쿼리
- ORDER BY 나 GROUP BY 에 명시된 칼럼이 조인의 순서상 첫 번째 테이블이 아닌 경우
- DISTINCT 와 ORDER BY 가 동시에 쿼리에 존재하는 경우 또는 DISTINCT 가 인덱스로 처리되지 못하는 경우
- UNION 이나 UNION DISTINCT 가 사용된 쿼리
- 쿼리 실행 계획에서 select_type 이 DERIVED 인 쿼리

어느 쿼리가 실행 계획에서 임시 테이블을 사용하는지 확인 -> Extra 칼럼에 "Using temporary" 문구 여부로 확인 가능(위 예시 중 뒤 3개는 표시되지 않아도 사용).

임시 테이블이 디스크에 생성되는 경우
- UNION 이나 UNION ALL 에서 SELECT 되는 칼럼 중 길이가 512 바이트 이상인 크기의 칼럼이 있는 경우
- GROUP BY 나 DISTINCT 칼럼에서 512 바이트 이상인 칼럼이 있는 경우
- 메모리 임시 테이블의 크기가 MEMORY 스토리지 엔진의 경우 `tmp_table_size` 혹은 `max_heap_table_size` 보다 크거나, TempTable 스토리지 엔진에서 `temptable_max_ram` 크기보다 큰 경우

임시 테이블 상태 변수
`Created_tmp_tables`: 쿼리의 처리를 위해 만들어진 내부 임시 테이블의 개수 누적, 메모리든 디스크든 모두 누적함.
`Created_tmp_dist_tables`: 디스크에 내부 임시 테이블이 만들어진 개수만 누적.
