# 5장 트랜잭션과 잠금

날짜: 2024-09-04

범위: 5장 전체(p155~183)

## 5.1 트랜잭션

하나의 논리적인 작업 셋이 전부 적용되거나, 아무것도 적용되지 않음을 통해 데이터의 정합성을 보장하기 위한 기능

MySQL 내 엔진 중 InnoDB 스토리지 엔진은 트랜잭션을 지원하고, MyISAM 과 MEMORY 스토리지 엔진은 트랜잭션을 지원하지 않음

부분 업데이트(Partial Update) 는 데이터의 정합성을 맞추는 데에 큰 문제를 만들어 냄

### 주의사항

트랜잭션은 필요한 최소한의 코드에만 적용하는 것이 좋음

특히, 네트워크 작업이 있는 경우 트랜잭션에서 배제

## 5.2 MySQL 엔진의 잠금

스토리지 엔진에서의 잠금은 각 스토리지 엔진에만 영향을 주지만, MySQL 엔진 레벨에서의 잠금은 모든 스토리지 엔진에 영향을 줌

### 글로벌 락
```
// 글로벌 락 획득
FLUSH TABLES WITH READ LOCK
// 글로벌 락 해제
UNLOCK TABLES;
```
가장 큰 범위의 잠금으로, 한 세션에서 글로벌 락을 획득하면 다른 모든 세션에서 SELECT 를 제외한 대부분의 DDL 혹은 DML 문장이 글로벌 락이 해제될 떄 까지 대기 상태가 됨

적용 범위: MySQL 서버 전체, 테이블이나 데이터베이스가 달라도 동일한 영향

`mysqldump`와 같은 백업 명령에 일관된 백업을 위해 해당 락을 사용

InnoDB 스토리지 엔진이 기본 스토리지 엔진이 되면서, 좀 더 가벼운 글로벌 락의 필요성이 생김 => 백업 락 도입

```
mysql> LOCK INSTANCE FOR BACKUP;
-- // 백업 실행
mysql> UNLOCK INSTANCE;
```

특정 세션이 백업 락을 획득했을 시 다음과 같은 항목이 제한됨
- 데이터베이스 및 테이블 등 모든 객체 생성 및 변경, 삭제
- REPAIR TABLE 과 OPTIMIZE TABLE 명령
- 사용자 관리 및 비밀번호 변경

단, 일반 테이블의 데이터 변경 허용

### 테이블 락

```
// 테이블 락 명시적 획득
LOCK TABLES table_name [ READ | WRITE]
// 명시적으로 획득한 테이블 락 해제
UNLOCK TABLES;
```

테이블 단위로 설정되는 잠금으로, 명시적 혹은 묵시적으로 획득 및 해제가 가능

MyISAM 혹은 MEMORY 테이블에 데이터를 변경하는 쿼리 실행 시 해당 테이블에 MySQL 서버가 묵시적 테이블 락을 설정하고, 데이터 변경 즉시 잠금을 해제

InnoDB 테이블의 경우 스토리지 엔진 차원에서 레코드 기반 잠금을 제공하기 때문에 단순 데이터 변경으로는 테이블 락을 획득하지 않음(DML 에서는 무시, DDL 에서는 획득)

### 네임드 락

```
-- // "mylock" 이라는 문자열에 대해 잠금을 획득, 이미 잠금을 사용중이라면 2초 동안만 대기 이후 해제
mysql> SELECT GET_LOCK('mylock', 2);
-- // "mylock" 이라는 문자열에 대해 잠금이 설정되었는지 확인
mysql> SELECT IS_FREE_LOCK('mylock');
-- // "mylock" 이라는 문자열에 대해 획득했던 잠금을 해제
mysql> SELECT RELEASE_LOCK('mylock');
-- // 모든 네임드 락을 해제
mysql> SELECT RELEASE_ALL_LOCKS();
```

잠금의 대상이 데이터베이스 객체가 아닌 문자열로, 여러 클라이언트가 상호 동기화를 처리할 때에 요긴하게 사용

MySQL 8.0 버전부터 네임드 락 중첩 사용 및 한번에 해제 가능

### 메타데이터 락

```
mysql> RENAME TABLE tab_b TO tab_a, tab_c TO tab_b; 
```

데이터베이스 객체의 메타데이터(이름 혹은 구조 등)을 변경할 때에 묵시적으로 획득

이름 변경의 경우 원본 이름과 변경될 이름 모두 한꺼번에 잠금 설정

상단의 쿼리문을 나눠서 실행하면 두 쿼리문 사이에 실행된 `tab_b` 테이블을 찾지 못해 오류 발생

## 5.3 InnoDB 스토리지 엔진 잠금

### InnoDB 스토리지 엔진의 잠금

레코드 기반의 잠금을 제공, 잠금 정보가 작은 공간에서 관리되기 때문에 락 에스컬레이션은 없음

- 레코드 락: 레코드 자체만을 잠그는 락, InnoDB 스토리지 엔진에서는 인덱스의 레코드를 잠금 / primary key 혹은 unique index 에 의한 변경 작업에서 레코드 락을 사용
- 갭 락: 레코드와 바로 인접한 레코드 사이의 간격을 잠그는 락, 레코드 사이의 간격에 새로운 레코드가 생성(INSERT) 되는 것을 제어. shared lock의 형태를 띔. 레코드가 없는 경우에 갭 락은 primary key 의 시작 가능 지점부터 끝 지점까지 모두 걸리기 때문에 갭 락으로 인한 성능 저하도 고려해야 함
- 넥스트 키 락: 레코드 락 + 갭 락[참고1](https://medium.com/daangn/mysql-gap-lock-%EB%8B%A4%EC%8B%9C%EB%B3%B4%EA%B8%B0-7f47ea3f68bc)
    - 바이너리 로그 형식에 따른 저장 방식
        - STATEMENT: 데이터 변경에 사용된 쿼리를 실행 순으로 기록
        - ROW: 변경 작업으로 변경된 모든 row 를 기록
        - [참고2](https://hyunki1019.tistory.com/105)
    - 이에 따라 STATEMENT 일때 복제 source 서버와 replica 서버에서의 결과가 다를 수 있음
    - 복제 source 와 replica 사이의 데이터 부정합을 막기 위해 갭 락 사용
    - 갭 락 혹은 넥스트 키 락을 사용할 때에 데드락이 발생할 상황이 생김
    - MySQL 8.0 버전부터 ROW 포멧의 바이너리 로그가 기본 설정이 되어 갭 락과 넥스트 키 락을 사용하는 일이 줄어듬
- 자동 증가 락: 중복되지 않고 순서대로 증가하는 값을 위해 사용하는 테이블 수준의 잠금, `innodb_autoinc_lock_mode` 시스템 변수에 따라 다르게 행동. 아주 짧은 시간에 획득했다 해제되기 때문에 명시적으로 해제할 수 없음, 또한 테이블 당 하나만 존재하기에 한 쿼리가 해당 락을 획득하면 다른 쿼리는 기다리게 됨
    - 0: 모든 INSERT, REPLACE 쿼리문에서 AUTO_INCREMENT 값을 가져오는 순간에 락이 걸렸다 즉시 해제
    - 1: INSERT 되는 레코드의 개수를 정확히 예측할 수 있을 때엔 개선된 래치를 사용하고, 그렇지 않은 경우 자동 증가 락을 사용. 연속된 INSERT 시에 자동 증가 값을 한 번에 할당받아 레코드에 사용하므로 하나의 INSERT 문에 의한 레코드는 연속된 자동 증가 값을 가짐(Consecutive mdoe)
    - 2: 항상 경량화된 래치를 사용, 하나의 쿼리문에서도 연속된 자동 증가 값을 보장할 수 없음(Interleaved mode), 다만 동시 처리 시에도 유니크한 값이 생성됨만을 보장

### 인덱스와 잠금

원하는 값을 변경할 때에 인덱스를 잠그는 방식 -> 변경할 레코드를 찾기 위해 검색한 인덱스의 레코드를 모두 락을 걸게 됨, 인덱스가 없는 경우 모든 레코드에 락을 걸게 됨 => 적절한 인덱스 설계가 필요

### 레코드 수준의 잠금 확인 및 해제

잠금을 가지고 있는 프로세스를 kill 하여 강제로 잠금을 해제할 수 있음

레코드 잠금과 잠금 대기에 대한 조회:

- MySQL 5.1 버전 이상: `information_schema` DB의 `INNODB_TRX`, `INNODB_LOCKS`, `INNODB_LOCK_WAITS` 테이블
- MySQL 8.0 버전 이상: `performance_schema` DB의 `data_locks`, `data_lock_waits` 테이블

## 5.4 MySQL의 격리 수준

여러 트랜잭션이 동시에 처리될 때에 특정 트랜잭션이 다른 트랜잭션에서 변경하거나 조회하는 데이터를 보는 것에 대한 허용 여부를 정하는 것

- 부정합 문제

||DIRTY READ|NON-REPEATABLE READ|PHANTOM READ|
|---|---|---|---|
|READ UNCOMMITTED|발생|발생|발생|
|READ COMMITTED|없음|발생|발생|
|REPEATABLE READ|없음|없음|발생(InnoDB 없음)|
|SERIALIZABLE|없음|없음|없음|

### READ UNCOMMITTED

각 트랜잭션의 변경 내용이 COMMIT 혹은 ROLLBACK 여부에 상관없이 다른 트랜잭션에서 볼 수 있음

Dirty Read: 어떤 트랜잭션에서 처리한 작업이 완료되지 않았는데 다른 트랙잰션에서 볼 수 있는 현상

## READ COMMITTED

오라클 DBMS 에서 가본으로 사용하는 격리 수준

어떤 트랜잭션에서 데이터를 변경했더라고 COMMIT 이 완료된 데이터만 다른 트랜잭션에서 조회 가능

Non-Repeatable Read: 한 트랜잭션 내에서의 반복적인 읽기 작업이 다른 결과를 가져올 수 있음

## REPEATABLE READ

MySQL InnoDB 스토리지 엔진에서 기본으로 사용하는 격리 수준

READ COMMITTED 와 차이점: UNDO 영역의 데이터 중 특정 트랜잭션 구간 내에서 백업된 UNDO 데이터를 보존(실행 중인 트랜잭션 가운데 가장 오래된 트랜잭션 번호보다 트랜잭션 번호가 앞선 언두 영역의 데이터를 삭제할 수 없음)

Phantom Read: 다른 트랜잭션에서 수행한 변경 작업에 의해 레코드가 보였다 안보이는 현상

## SERIALIZABLE

읽기 작업도 읽기 잠금을 획득해야한 하고, 해당 잠금이 있는 사이에 다른 트랜잭션은 해당 레코드를 변경하지 못함
