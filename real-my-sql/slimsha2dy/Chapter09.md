> 옵티마이저: MySQL에서 쿼리를 최적으로 실행하기 위해 각 테이블 데이터의 분포와 통계 정보를 참조해 최적의 실행 계획을 수립하는 작업을 담당

`EXPLAIN` 으로 확인할 수 있는 실행 계획을 제대로 이해하려면 옵티마이저의 최적화를 어느 정도 알면 좋다! (즐겁다)

## 개요

### 쿼리 실행 절차

1. **SQL 파싱**: 사용자가 요청한 SQL 문장을 MySQL 서버가 이해할 수 있도록 분리 → **SQL 파스 트리**
    1. SQL 파서가 처리
2. **최적화 및 실행 계획 수립**: 파싱 정보(파스 트리)를 확인하며 어떤 테이블부터, 그리고 어떤 인덱스를 이용해 읽을지 선택 → **실행 계획**
    1. 옵티마이저가 처리
3. 결정된 읽기 순서와 인덱스를 이용해 스토리지 엔진으로부터 데이터를 가져옴
    1. MySQL 엔진과 스토리지 엔진이 처리
    2. 스토리지 엔진이 레코드를 읽어오고, MySQL 엔진이 레코드를 조인하거나 정렬

2번 과정에선 대표적으로 다음과 같이 처리

- 불필요한 조건 제거 및 복잡한 연산 **단순화**
- 여러 조인이 있을 경우 **어떤 순서로 테이블을 읽을지** 결정
- 각 테이블에 사용된 조건과 인덱스 통계 정보를 이용해 **사용할 인덱스** 결정
- 가져온 레코드를 **임시 테이블**에 넣고 **다시 가공해야 하는지** 결정

### 옵티마이저의 종류

- **비용 기반 최적화**(Cost-based optimizer, CBO)
    - 현재 대부분의 DBMS가 사용
    - 쿼리를 처리하기 위한 여러 가능한 방법을 만들고, 비용 정보와 통계 정보를 이용해 계획 별 비용을 산출
    → 비용이 최소인 방식을 선택해 쿼리를 실행
- **규칙 기반 최적화**(Rule-based optimizer, RBO)
    - 예전 초기 오라클 DBMS에서 많이 사용
    - 대상 테이블의 레코드 건수나 선택도를 고려하지 않고 옵티마이저에 내장된 우선순위에 따라 실행 계획을 수립
    - 통계 정보를 조사하지 않음 → **같은 쿼리에 대해 항상 같은 실행 방법**을 만듦

## 기본 데이터 처리

### 풀 테이블 스캔과 풀 인덱스 스캔

아래의 조건일 때 풀 테이블 스캔을 선택함

- 테이블의 레코드 건수가 **너무 작을 때**(일반적으로 테이블이 페이지 1개로 구성된 경우)
- WHERE 절이나 ON 절에 인덱스를 이용할 수 있는 **적절한 조건이 없을 때**
- 인덱스 레인지 스캔을 사용할 수 있어도 **조건 일치 레코드 건수가 너무 많다**고 판단될 때(B-Tree를 샘플링해서 조사한 통계 정보 기준)

대부분 DBMS는 풀 테이블 스캔할 때 여러 블록이나 페이지를 한꺼번에 읽어오는 기능이 있지만 MySQL에는 해당 시스템 변수가 없기 때문에 하나씩 읽어온다고 생각함 ㅋㅋ(바보)

→ MyISAM에선 맞지만 InnoDB에선 틀림!

InnoDB에선 특정 테이블의 연속된 페이지가 읽히면 백그라운드 스레드가 **리드 어헤드** 작업을 시작함

**리드 어헤드**: 어떤 영역의 데이터가 필요할 것 같아서 **미리 버퍼 풀로 읽어오는 것**
→ 즉, 풀 테이블 스캔이 실행되면 특정 시점부터 백그라운드 스레드가 점점 많이씩 읽어옴

시스템 변수를 이용해 리드 어헤드를 언제 시작할지 임계값을 설정할 수 있다!

또한, 리드 어헤드는 풀 인덱스 스캔에서도 동일하게 사용됨!!!!

### 병렬 처리

하나의 쿼리를 여러 스레드가 작업을 나누어 동시에 처리한다는 의미(무슨의미?ㅋㅋ)

시스템 변수를 이용해 하나의 쿼리를 최대 몇 개의 스레드가 병렬로 처리할지 변경할 수 있음!

but, 병렬로 처리하게 하는 힌트나 옵션은 없다!!
(WHERE 절 없이 단순히 테이블의 전체 건수를 갖고 오는 쿼리만 병렬 처리 가능)

### ORDER BY 처리(Using filesort)

정렬 처리 방법은 인덱스를 활용하는 방법과 “Filesort”라는 별도 처리 방법이 있다

| 책 거 갖고옴 ㅋ | 장점 | 단점 |
| --- | --- | --- |
| 인덱스 이용 | INSERT, UPDATE, DELETE(이거 SELECT 말하는거 맞제?) 쿼리 실행 시 이미 인덱스로 정렬돼있어서 매우 빠름 | INSERT, UPDATE, DELETE 작업 시 부가적인 인덱스 작업이 필요해 느리다
디스크 공간이 더 필요하다
인덱스가 많아질수록 버퍼 풀을 위한 메모리가 많이 필요하다 |
| Filesort 이용 | 인덱스의 단점 해결
정렬할 레코드가 많지 않으면 메모리에서 Filesort가 처리되므로 빠름 | 정렬 작업이 쿼리 실행 시 처리되므로 레코드 건수가 많아질수록 느려짐 |

인덱스로 항상 처리하기 힘든 이유

- 정렬 기준이 너무 많아 요건에 맞는 인덱스 생성이 힘든 경우
- GROUP BY의 결과, DITINCT 같은 처리 결과를 정렬해야 할 이경우(우리학교 경제학과 (빡빡이)교수님, 컴과 교수님 둘 다 계심 ㅋㅋ)
- UNION의 결과와 같이 임시 테이블의 결과를 정렬해야 할 경우
- 랜덤하게 결과 레코드를 가져올 경우

인덱스를 사용했는지 아닌지는 실행 계획의 Extra 칼럼에 “Using filesort”로 확인 가능

### 소트 버퍼

> 정렬을 수행하기 위해 할당받는 별도의 메모리 공간
> 
- 정렬이 필요할 때만 할당
- 크기는 정렬해야 할 레코드 크기에 따라 가변적으로 증가
    - 근데 최대 크기는 시스템 변수로 설정
- 쿼리 실행이 완료되면 시스템으로 반납

근데 정렬해야 할 레코드 건수가 소트 버퍼보다 더 크면??

→ 정렬할 레코드를 여러 조각으로 나눠서 처리하고, 임시 저장을 위해 디스크를 사용

→ 소트 버퍼에서 정렬하고 결과를 임시로 디스크에 기록 반복

이를 **멀티 머지**(Multi-merge)라고 표현

수행된 멀티 머지 횟수는 `Sort_merge_passes` 상태 변수에 집계됨

이 작업들이 모두 디스크 I/O를 유발(하라리)하고 레코드가 많을수록 반복 작업이 많아지겠지..

그렇다고 소트 버퍼를 늘려도 실제론 큰 차이가 없다

← 너무 크면 메모리를 너무 많이 차지해서 성능이 더 떨어질 수..

심지어 얘네가 너무 커져서 프로세스를 강제 종료해야 하면 MySQL 서버가 척결대상 1순위..

그니까 결국 “**적절히 설정**”

### 정렬 알고리즘

- 싱글 패스(Single-pass): 레코드 전체를 소트 버퍼에 담음
- 투 패스(Two-pass): 정렬 기준 칼럼만 소트 버퍼에 담음

어떤 모드를 사용하는지 옵티마이저 트레이스로 확인 가능(291p)

정확힌 3가지 방법

- <sort_key, rowid>: 정렬 키와 rowid만 가져와서 정렬
- <sort_key, additional_fields> 정렬 키와 레코드 전체 가져와서 정렬, 고정 사이즈로 메모리 저장
- <sort_key, packed_addtional_fields>: 정렬 키와 레코드 전체 가져와서 정렬, 가변 사이즈로 메모리 저장

첫 번째가 투 패스, 나머지가 싱글 패스

- **싱글 패스 정렬 방식**
    - 소트 버퍼에 정렬 기준 칼럼을 포함해 SELECT 대상 칼럼 전부를 담아서 정렬
    - 정렬에 필요하지 않은 칼럼도 갖고 올 수 있음
- **투 패스 정렬 방식**
    - 정렬 대상 칼럼 + 프라이머리 키 값만 소트 버퍼에 담아서 정렬
    - 정렬된 순서대로 테이블을 읽어서 SELECT할 칼럼을 가져옴
    - 싱글 패스 도입 이전부터 사용됐지만 여전히 특정 조건에선 사용
- 투 패스는 테이블을 두 번 읽어야 하지만 싱글 패스는 더 많은 소트 버퍼 공간이 필요함
- 최신 버전에선 일반적으로 싱글 패스 정렬 방식을 주로 사용함
- 아래의 경우에 투 패스 정렬 사용
    - 레코드 크기가 `max_length_for_sort_data` 시스템 변수보다 클 때
    - BLOB이나 TEXT 타입 컬럼이 SELECT 대상에 포함될 때

### 정렬 처리 방법

정렬 쿼리가 발생하면 3가지 중 하나로 정렬이 처리됨(아래로 갈수록 처리 속도 느려짐)

옵티마이저는 먼저 인덱스를 사용할 수 있는지 검토 → 사용 불가면 레코드를 검색해 정렬 버퍼에 저장하면서 정렬을 처리함 → 정렬 대상 레코드 최소화를 위해 2 가지 방법 중 하나를 사용

- 조인의 드라이빙 테이블만 정렬하고 조인 수행
- 조인이 끝나고 일치하는 레코드를 가져온 후 정렬 수행
    - 조인이 수행되면 레코드 건수가 많아지므로 이 방법이 좀 더 비효율적

- **인덱스 사용 정렬**: Extra 칼럼에 별도 표기 X
    - ORDER BY에 병시된 칼럼이 제일 먼저 읽는 테이블에 속하고 ORDER BY 순서대로 생성된 인덱스가 있어야 함!
    - 또한 WHERE 절에 칼럼 조건ㅇ 있다면 그 조건과 ORDER BY는 같은 인덱스를 사용할 수 있어야 함
    - B-Tree 인덱스가 아니면 사용 불가
    - 추가적인 정렬 작업 X
    - 조인은 네스티드-루프 방식으로 실행되므로 순서가 흐트러지진 않지만 실행 계획에 조인 버퍼가 사용되면 흐트러질 수 있음!
- **조인에서 드라이빙 테이블만 정렬**: “Using filesort” 표시
    - 조인에서 첫 번째로 읽히는 테이블(드라이빙 테이블)의 칼럼만으로 ORDER BY 절을 작성해야 함
- **조인에서 조인 결과를 임시 테이블로 저장 후 정렬**: “Using temporary; Using filesort” 표시
    - 2개 이상의 테이블을 조인해서 그 결과를 정렬해야 할 때 필요
    - 가장 느린 정렬 방식
    - ORDER BY 절의 정렬 기준 칼럼이 드리븐 테이블에 있는 칼럼일 때

- 정렬 처리 방법의 성능 비교
    - 아무리 인덱스를 잘 활용해도 잘못된 ORDER BY나 GROUP BY 때문에 느려지는 경우가 발생
        - LIMIT로 가져오기 위해서 해당 조건으로 조회한 다음 걸러야 하기 때문에
    - 스트리밍 방식
        - 조건에 일치하는 레코드가 검색될 때마다 바로바로 클라이언트로 전송해주는 방식
        - 클라이언트는 쿼리를 요청하고 곧바로 첫 레코드를 전달받음
            - 마지막 레코드는 언제 받을지 모르긴 함
            - 클라이언트는 전달받는 동시에 데이터로 작업할 수 있게됨
        - 빠른 응답 시간을 보장
    - 버퍼링 방식
        - ORDER BY나 GROUP BY 같은 처리는 스트리밍을 불가능하게 함
        - 먼저 레코드를 가져온 후 정렬하거나 그루핑해서 보내야 하기 때문
        - 그 동안 클라이언트는 기다려야 함
        - 이 경우 LIMIT가 있어도 성능 향상에 도움되지 않음
    - 정렬 처리의 3가지 방법 중 인덱스만 스트리밍 형태, 나머진 버퍼링 형태

### 정렬 관련 상태 변수

MySQL은 주요 처리 작업의 실행 횟수를 상태 변수로 저장하는데 정렬에 관해서도 여러 정보를 저장함

몇 건의 레코드를 정렬했는지, 멀티 머지는 몇 번 했는지 등

`SHOW STATUS LIKE 'Sort%'` 

자세한 정보는 304~305p

### GROUP BY 처리

GROUP BY에 사용된 조건은 인덱스를 사용할 수 없으므로 HAVING(GROUP BY 결과 필터링 역할) 절 튜닝을 위해 고민할 필요가 없다!

- GROUP BY 작업도 인덱스를 사용하는 경우와 아닌 경우가 있다
    - 이용할 때는 또 인덱스 스캔 방법과 루스 인덱스 스캔 방법으로 나눠진다
    - 인덱스를 사용하지 못할 경우 임시 테이블 사용
- 인덱스 스캔을 이용하는 GROUP BY(타이트 인덱스 스캔)
    - 조인의 드라이빙 테이블에 속한 칼럼만 이용해 그루핑할 때 인덱스가 있다면 그 인덱스를 이용
    - 그래도 그룹 함수 등의 그룹값을 처리해야 해서 임시 테이블이 필요할 때도 있다
    - Extra 칼럼에 별도의 표시 X
- 루스 인덱스 스캔을 이용하는 ~
    - 306p의 예제 참고
    - 단일 테이블에 대해 수행되는 GROUP BY 처리에만 사용할 수 있음
    - 루스 인덱스 스캔은 인덱스 스캔과 달리 유니크한 값의 수가 적을수록 성능이 향상됨
    - Extra 칼럼에 “Using index for group-by” 코멘트 표시
- 임시 테이블을 사용하는 ~
    - 인덱스를 전혀 사용하지 못하는 경우
    - 8.0부터 묵시적 정렬을 하지 않고 처리
    - ORDER BY와 함께 사용되면 명시적 정렬 작업 실행
    - Extra 칼럼에 “Using temporary” 표시

### DISTINCT 처리

특정 칼럼의 유니크한 값만 조회할 때 SELECT와 함께 DISTINCT 사용하지요

MIN(), MAX(), COUNT() 같은 집합 함수와 함께 사용되는 경우와 아닌 경우로 구분해서 보자

집합 함수와 같이 사용될 때 DISTINCT 처리가 인덱스를 사용하지 못하면 항상 임시 테이블을 사용함
그런데 그래도 Extra 칼럼엔 “Using temporary”가 출력되지 않음 ㅜ

- **SELECT DISTINCT …**
    - GROUP BY와 동일한 방식으로 처리됨
    - 조회하는 모든 칼럼의 조합이 유니크한 레코드를 가져옴
- **집합 함수와 함께 사용된 DISTINCT**
    - 집합 함수 내에서 DISTINCT 키워드가 사용된 경우 SELECT와 다른 형태로 해석됨
    - 집함 함수의 인자로 전달된 칼럼값이 유니크한 것들을 가져옴
    - 내부적으로 임시 테이블을 사용함
    ← 근데 실행 계획에선 안알랴줌 ㅋㅋ

### **내부 임시 테이블 활용**

스토리지 엔진으로부터 받은 레코드를 정렬하거나 그루핑할 때는 내부 임시 테이블을 사용

첨엔 메모리에 생겼다가 커지면 디스크로 옮김

- **메모리 임시 테이블과 디스크 임시 테이블**
    - 8.0부터는 임시 테이블이 메모리를 사용할 때는 TempTable, 디스크에선 InnoDB 엔진을 사용하도록 개선됨
        - 기존엔 MEMORY, MyISAM
    - MEMORY는 가변 길이 타입(VARBINARY, VARCHAR)을 지원하지 못해서 최대 길이를 할당했기 때문에 메모리 낭비의 문제가 있었음
    - MyISAM은 트랜잭션을 못쓰고
    - TempTable은 가변 길이 타입을 지원함
    - 시스템 변수를 이용해 MEMORY, TempTable을 선택할 수 있음
        - 또한 TempTable이 최대 사용 가능한 메모리 공간의 크기도 시스템 변수로 제어, 기본값은 1GB
    - 이 크기를 넘어가면 디스크로 기록
        - MMAP 파일로 기록하거나 InnoDB 테이블로 기록(시스템 변수로 설정, 기본은 MMAP)
    - 근데 처음부터 디스크 테이블로 생성되는 경우도 있음!
        - 시스템 변수에 설정된 스토리지 엔진을 사용(기본값은 InnoDB)
- **임시 테이블이 필요한 쿼리**
    - 다음과 같은 패턴
        - ORDER BY, GROUP BY에 명시된 칼럼이 다른 쿼리
        - ORDER BY, GROUP BY에 명시된 칼럼이 조인의 순서상 첫 번째 테이블이 아닌 쿼리
        - DISTINCT와 ORDER BY가 동시에 쿼리에 존재하는 경우, DISTINCT가 인덱스로 처리되지 못하는 쿼리
        - UNION, UNION DISTINCT가 사용된 쿼리
        - 실행 계획에서 select_type이 DERIVED인 쿼리
    - Extra 칼럼에 “Using temporary”가 표시되는지 확인하면 알 수 있음
        - 근데 위 3 패턴은 표시되지 않지만 사용함
    - 마지막 패턴만 유니크 인덱스가 없는 내부 임시 테이블이 생성되므로 처리 성능이 느림
- **임시 테이블이 디스크에 생성되는 경우**
    - 기본적으로 메모리에 생성되지만 아래의 조건에서 메모리 임시 테이블을 사용할 수 없음
    → 디스크 기반의 임시 테이블 사용
    - UNION, UNION ALL에서 SELECT되는 칼럼 중 512 바이트 이상인 크기의 칼럼이 있는 경우
    - GROUP BY나 DISTINCT 칼럼에서 512 바이트 이상 크기의 칼럼이 있는 경우
    - 메모리 임시 테이블 크기가 시스템 변수 값보다 큰 경우
- 임시 테이블 관련 상태 변수
    - 실행 계획을 통해 임시 테이블을 사용한 사실은 알 수 있지만 메모리인지 디스크인지, 몇 개의 임시 테이블이 사용됐는지 알 수 없음
    - 이를 확인하려면 MySQL 서버의 상태 변수를 확인하면 됨
    - `SHOW SESSION STATUS LIKE 'Created_tmp%';`
    - 317~318p 참고
