MySQL 서버는 MySQL 엔진과 스토리지 엔진으로 구분할 수 있음

## MySQL 엔진 아키텍처

- **MySQL 엔진**
    - 쿼리를 작성하고 튜닝할 때 필요
    - 커넥션 핸들러: 클라이언트 접속 및 쿼리 요청 처리
    - SQL 파서, 전처리기
    - 옵티마이저
    - 표준 SQL 문법을 지원하므로 쿼리는 타 DBMS와 호환 가능
- **스토리지 엔진**
    - 실제 데이터를 디스크 스토리지에 저장하거나 읽어오는 부분
    - MySQL 엔진과 달리 여러 개를 동시에 사용할 수 있음
        - 테이블이 사용할 스토리지 엔진을 지정할 수 있음
- **핸들러 API**
    - 핸들러 요청: MySQL 엔진의 쿼리 실행기에서 각 스토리지 엔진에 쓰기 또는 읽기를 요청하는 것
    - 핸들러 요청에 사용되는 것이 핸들러 API
    - `SHOW GLOBAL STATUS LIKE 'Handler%'` 를 통해 작업 횟수를 확인할 수 있음
        - `SHOW GLOBAL STATUS` 는 서버의 상태 변수 조회, `LIKE 'Handler%'` 는 Handler로 시작하는 패턴

### **MySQL 스레딩 구조**

- MySQL 서버는 프로세스 기반이 아닌 스레드 기반으로 작동
    - 그러나 MySQL이 실행되면 두 개의 프로세스를 확인할 수 있음
    → mysqld는 실제 서비스 데몬, mysqld_safe는 MySQL이 비정상 종료되는 경우 다시 기동하는 역할
- **포그라운드**(Foreground) 스레드, **백그라운드**(Background) 스레드로 구분
- `performance_schema` 데이터베이스의 `threads` 테이블을 통해 확인 가능
- **포그라운드 스레드(클라이언트 스레드)**
    - 주로 각 클라이언트 사용자가 요청하는 쿼리 문장을 처리
    → 적어도 MySQL 서버에 접속된 클라이언트의 수만큼 존재
    - 클라이언트 사용자가 작업을 마치고 커넥션 종료 시 그 스레드는 스레드 캐시로 돌아감
        - 근데 일정 개수 이상의 스레드가 캐시에 대기 중이면 그냥 종료
        ← 시스템 변수로 설정
        - MySQL은 스레드 구조이므로 세션 생성 비용이 비교적 적음
    - 데이터를 MySQL의 버퍼나 캐시로부터 가져오거나 직접 디스크의 데이터나 인덱스 파일로부터 데이터를 읽어와서 작업을 처리
    - 쓰기 작업
        - MyISAM 테이블은 쓰기 작업도 포그라운드 스레드가 처리
        - InnoDB 테이블은 버퍼나 캐시까지만 포그라운드, 버퍼로부터 디스크는 백그라운드
        - 즉 InnoDB에서는 메모리에 대한 쓰기 작업만
- **백그라운드 스레드**
    - **Master thread**: 백그라운드 스레드에 대한 관리 및 다양한 작업들의 스케줄링 담당
        - 과거엔 하드웨어 리소스와 직접적으로 연결되는 일을 많이 했으나 버전 업에 따라 분리되는 추세
    - **Change Buffer thread:** insert buffer(change buffer)를 병합하는 스레드
        - change buffer: 보조 인덱스 I/O 성능 향상을 위한 버퍼
            - 보조 인덱스는 정렬되지 않아 최신 상태로 유지하는 데에 I/O 오버헤드가 크므로 변경 사항을 캐싱해서 성능 올림
        - 읽기 작업에 의해 페이지가 버퍼 풀에 로드될 때 버퍼링된 변경 사항을 병합
    - **Log thread:** 로그를 디스크로 기록
        - 관계형 데이터베이스에서 ACID를 위해 writer ahead log 기법을 사용하는데 이 때 사용
        - 트랜잭션 로그 작성
    - **Write thread:** 버퍼 풀의 데이터를 디스크에 기록
        - 아주 많은 작업을 백그라운드로 처리하므로 개수를 여러 개 둠(2~4 정도)
        - 지연 처리될 수 있으므로 대부분 쓰기 작업을 버퍼링해서 일괄 처리하는 기능이 있음
        → 그래서 InnoDB에서는 데이터의 변경 저장을 기다리지 않아도 됨
    - **Read thread:** 다양한 읽기 작업을 처리
        - 읽기 작업은 지연되면 안되므로 주로 클라이언트 스레드에서 처리
        - 그럼 얘는 언제 씀?
        - 아무튼 그래서 쓰기 스레드와 달리 많이 설정할 필요가 없음
    - **Page Cleaner thread:** 버퍼 풀에 있는 dirty page를 flush
        - 원래는 마스터 스레드였는데 분리됨
    - **Purge thread:** Marking 처리(rollback)된 row를 제거하는 역할
        - 이거도 마스터 스레드에서 분리

### **메모리 할당 및 사용 구조**

- 글로벌 메모리 영역과 로컬 메모리 영역으로 이루어짐
- 글로벌 영역은 서버가 시작될 때 운영체제로부터 할당됨
← 시스템 변수로 설정해 둔 만큼 생각해도 됨
- MySQL 서버 내에 존재하는 스레드들이 공유해서 사용하는 공간인지 여부에 따라 구분
- **글로벌 메모리 영역**
    - 스레드 수와 무관하게 하나(필요에 따라 늘어날 수도)의 공간만 할당됨
    - 모든 스레드에 의해 공유됨
    - 테이블 캐시, InnoDB 버퍼 풀, InnoDB 어댑티브 해시 인덱스, InnoDB 리두 로그 버퍼
- **로컬 메모리 영역(= 세션/커넥션 메모리영역)**
    - 클라이언트 스레드가 쿼리를 처리하는 데 사용하는 메모리 영역
    - 각 스레드별로 독립적으로 할당됨
    - 공유되지 않음
    - 각 쿼리의 용도별로 필요할 때만 공간이 할당됨(대표적으로 정렬, 조인 버퍼)
    - 커넥션이 열려 있는 동안 계속 할당된 상태인 공간(커넥션, 결과 버퍼)도 있고 쿼리 실행 순간에만 할당되는 공간(소트, 조인 버퍼)이 있음
    - 정렬 버퍼, 조인 버퍼, 바이너리 로그 캐시, 네트워크 버퍼

### **플러그인 스토리지 엔진 모델**

- 스토리지 엔진 외에도 전문 검색 검색어 파서, 사용자 인증 증의 작업을 플러그인으로 구현해서 제공
- 기본적으로 제공되는 스토리지 엔진 이외에 부가적인 기능을 더 제공하는 스토리지 엔진이 필요할 수 있잖아
- InnoDB 스토리지 엔진, validate_password 컴포넌트, query_rewrite 플러그인 등
- 핸들러: 프로그래밍 언어에서 어떤 기능을 호출하기 위해 사용하는 객체
    - MySQL 엔진이 각 스토리지 엔진에게 읽기/쓰기를 명령하려면 반드시 핸들러를 통해야 함
- 복잡한 쿼리 작업(SORT, JOIN)은 MySQL 엔진에서 처리되고 데이터 읽기/쓰기만 스토리지 엔진에서 처리된다
- `SHOW ENGINES` 를 통해  스토리지 엔진을 확인 가능
- `SHOW PLUGINS` 로 스토리지 엔진뿐 아니라 플러그인도 확인 가능
- 단점이 있음
    - 플러그인은 MySQL 서버와만 인터페이스할 수 있고 서로는 통신 불가
    - 플러그인은 MySQL 서버의 변수와 함수를 직접 호출하므로 안전하지 않음(캡슐화가 안됨)
    - 상호 의존 관계를 설정할 수 없어서 초기화가 어렵스
- **컴포넌트**
    - MySQL 8.0부터 기존 플러그인 아키텍처를 대체하기 위해 컴포넌트 아키텍처가 지원됨
    - 비밀번호 검증 기능을 컴포넌트로 개선
    - `INSTALL COMPONENT` 로 설치
    - `SELECT * FROM mysql.component` 로 확인

### 쿼리 실행 구조

- **쿼리 파서**
    - 사용자 요청으로 들어온 쿼리 문장을 토큰으로 분리해 트리 형태의 구조로 만드는 작업
    - 토큰: MySQL이 인식할 수 있는 최소 단위의 어휘나 기호
    - 기본 문법 오류는 여기서 발견되고 오류 메시지를 전달함
- **전처리기**
    - 파서 트리를 기반으로 문장에 구조적인 문제점이 있는지 확인
    - 각 토큰을 테이블 이름, 칼럼 이름, 내장 함수와 같은 개체에 매핑해 존재 여부 및 접근 권한 등을 확인함
    - 존재하지 않거나 권한이 안되면 여기서 걸러짐
- **옵티마이저**
    - 사용자의 요청으로 들어온 쿼리 문장을 가장 빠르게 처리할지 결정하는 역할
    - 이 책에선 대부분 옵티마이저의 선택과 이를 개선하는 방법을 설명함
- **실행 엔진**
    - 만들어진 계획대로 핸들러에게 요청하고 이 결과를 다시 다른 핸들러의 요청으로 연결하는 역할
- **핸들러(스토리지 엔진)**
    - MySQL 실행 엔진의 요청에 따라 데이터 읽기/쓰기를 담당
    - InnoDB 스토리지 엔진, MyISAM 스토리지 엔진
- **복제(Replication)**
- **쿼리 캐시**
    - SQL의 실행 결과를 메모리에 캐시하고 동일 SQL 쿼리가 실행되면 즉시 반환
    - 테이블 데이터 변경 시 변경된 테이블과 관련된 캐시를 모두 삭제해야 하므로 동시 처리 성능 저하를 유발
    - MySQL 서버가 발전하면서 많은 버그의 원인이 되기도 함
    - 결국 MySQL 8.0으로 올라오면서 완전히 제거됨

### 스레드 풀

엔터프라이즈 에디션은 제공하지만 커뮤니티 에디션은 제공하지 않음. 이 챕터에서는 **Percona Server에서 제공되는 스레드 풀 기능**을 설명

엔터프라이즈 에디션에서 MySQL 서버 프로그램에 내장된 것과 달리 Percona Server에서는 **플러그인 형태**로 작동함 → 커뮤니티 에디션에서 사용하려면 동일 버전의 Percona Server에서 플러그인을 설치해서 사용하면 됨

스레드 풀은 내부적으로 스레드 개수를 줄여서 **서버의 자원 소모를 줄이는 것**이 목적. 동시에 실행 중인 스레드들을 CPU가 최대한 잘 처리하는 수준으로 줄여서 빨리 처리하게 하는 기능
→ 따라서 실제 서비스에서 눈에 띄는 성능 향상을 보여주는 일은 드물다. 쿼리 처리가 더 느려지는 일도 생길 수도

하지만 잘 유도하면 컨텍스트 스위치를 줄여 오버헤드를 낮출 수 있음

- 기본적으로 CPU 코어의 개수만큼 스레드 그룹을 생성
← 시스템 변수를 변경해서 조정 가능, 근데 코어와 개수를 맞추는 것이 좋다
- MySQL 서버가 처리해야 할 요청이 생기면 스레드 풀로 처리를 이관함
→ 만약 이미 스레드 풀이 처리 중인 작업이 있다면 추가로 더 받아들여 처리함(이거도 시스템 변수로 조정). 이 값이 너무 크면 스케줄링할 스레드의 수가 많아져 오히려 비효율적으로 됨

모든 스레드 그룹의 스레드들이 작업 중이면 스레드 풀은 새로운 스레드를 추가할지 기다릴지 여부를 판단해야 함.
→ 타이머 스레드가 주기적으로 그룹의 상태를 체크해 일정 시간(이거도 시스템 변수) 동안 작업을 끝내지 못하면 새로 생성. 그래도 시스템 변수의 최대 개수를 넘길 순 없다

응답 시간에 민감할 경우 일정 시간 시스템 변수를 잘 조정해야 한다. 근데 0에 가까운 값을 설정할 바엔 스레드 풀을 사용하지 않는 편이 나을 수 있음

- 선순위 큐와 후순위 큐를 이용해 특정 트랜잭션/쿼리를 우선 처리할 수 있는 기능도 제공
- 잠금을 빨리 해제해서 경합을 낮출 수 있고 이를 통해 처리 성능 향상을 기대할 수 있음

### 트랜잭션 지원 메타데이터

- **메타데이터**(또는 데이터 딕셔너리): 테이블의 구조 정보와 스토어드 프로그램 등의 정보
- 원래는 파일 기반이었는데 이는 트랜잭션 지원이 안되므로 깨질 수 있음
- 8.0 버전부터 InnoDB의 테이블에 저장하도록 개선
- 시스템 테이블: MySQL 서버가 작동하는 데 기본적으로 필요한 테이블
    - 대표적으로 사용자의 인증과 권한에 관련된 테이블
    - 이를 InnoDB 스토리지 엔진을 사용하도록 개선
- 실제 mysql DB의 테이블 목록에서 볼 순 없고 뷰를 통해 조회할 수 있음
- 트랜잭션을 통해 데이터가 깨지지 않게 됨
- 근데 MyISAM이나 CSV 같은 스토리지 엔진에서는 여전함
    - 따라서 SDI 파일을 사용

## InnoDB 스토리지 엔진 아키텍처

- MySQL 스토리지 엔진 중 가장 많이 사용됨
- 거의 유일하게 레코드 기반의 잠금을 제공 → 높은 동시성 처리가 가능하고 안정적이고 성능도 굿
- **프라이머리 키에 의한 클러스터링**
    - InnoDB의 모든 테이블은 기본적으로 프라이머리 키를 기준으로 클러스터링되어 저장됨
    → 키 값의 순서대로 디스크에 저장된다는 뜻
    - 모든 세컨더리 인덱스는 레코드 주소 대신 프라이머리 키 값을 논리적인 주소로 사용함
    - 프라이머리 키가 클러스터링 인덱스이므로 레인지 스캔이 상당히 빨리 처리됨
    → 쿼리의 실행 계획에서 프라이머리 키는 다른 보조 인덱스에 비해 비중이 높게 설정됨
    - MyISAM에서는 클러스터링 키를 지원하지 않음
        - 따라서 프라이머리 키와 세컨더리 인덱스는 구조적으로 같다. 유니크 제약을 가진 세컨더리 인덱스인 것
        - 모든 인덱스는 물리적인 레코드의 주소 값을 갖고 있음
- **외래 키 지원**
    - InnoDB 스토리지 엔진 레벨에서 지원하므로 MyISAM, MEMORY 테이블에서는 사용 불가
    - 외래 키는 DB 서버 운영의 불편함 때문에 서비스용 DB에서 생성하지 않는 경우도 잦지만 개발 환경의 DB에서는 좋은 가이드 역할
    - InnoDB에서 외래 키는 부모 - 자식 테이블 모두 해당 칼럼에 인덱스 생성이 필요함
        - 변경 시 두 테이블에서 다 데이터가 있는지 확인하는 작업이 필요하므로 잠금이 전파되고 데드락 발생 확률이 올라가므로 주의하는 것이 좋다~
    - 수동 데이터 적재나 스키마 변경 등의 작업이 실패할 수도 있음
        - 관계를 파악해서 순서대로 작업해야 함
        - 복잡하면 간단하지 않다
        - 긴급 조치가 필요할 때 곤란해질 수도..ㅋ
    - foreign_key_checks 시스템 변수를 OFF로 설정하면 일시적으로 외래 키 관계 체크 작업을 멈출 수 있음
        - 근데 그래도 일관성을 맞춰줘야 하겠지?

### MVCC(Multi Version Concurrency Control)

- 잠금을 사용하지 않는 일관된 읽기를 제공하는 것이 목적
- 일반적으로 레코드 레벨의 트랜잭션을 지원하는 DBMS가 제공하는 기능
- InnoDB에서는 언두 로그(Undo Log)를 통해 구현
- 멀티 버전: 하나의 레코드에 대해 여러 버전이 동시에 관리된다는 의미
- `UPDATE member SET m_area='경기' WHERE m_id=12` 라는 쿼리를 실행하면
    - 커밋 실행 여부와 상관 없이 버퍼 풀에는 “경기”인 값이 들어감
    - 변경 전 값인 “서울”은 언두 로그에 복사
    - 데이터 파일(디스크)에는 업데이트 되었을 수도 아닐 수도
    - 이 때 다른 사용자가 작업 중인 레코드를 조회하면 어디를 참조?
    → 트랜잭션 격리 수준에 따라 다름
    - READ_UNCOMMITTED인 경우 버퍼 풀의 데이터를, READ_COMMITTED 이상의 경우 언두 영역의 데이터를 반환
    - 이러한 과정을 DBMS에서는 MVCC라고 표현함
- 하나의 레코드에 대해 2개의 버전이 유지되고 필요에 따라 어느 데이터를 보일지 상황에 따라 달라지는 구조
- 관리해야 하는 예전 버전이 무한히 많아질 수도
    - 트랜잭션이 길어질 경우 언두에서 관리하는 데이터가 오래 남게 됨
- 커밋 시 지금 상태를 영구적인 상태로 만듬, 언두 로그는 바로 삭제되지 않고 이 영역을 필요로 하는 트랜잭션이 더는 없을 때 사라짐
- 롤백 시 언두 영역의 데이터를 버퍼 풀로 복구하고 언두 영역의 데이터를 삭제
- **잠금 없는 일관된 읽기**
    - 격리 수준이 SERIALIZABLE이 아닌 경우 INSERT와 연결되지 않은 순수한 읽기 작업은 다른 트랜잭션의 변경 작업과 관계 없이 항상 잠금을 대기하지 않고 바로 실행됨
    - 특정 사용자가 레코드를 변경하고 커밋하지 않았어도 다른 사용자의 SELECT 작업을 방해하지 않는다
    - 이를 잠금 없는 일관된 읽기라고 표현
    - 트랜잭션이 길어지면 언두 로그를 계속 유지해야 하므로 MySQL의 서버가 느려지거나 문제가 발생할 수 있다
    → 트랜잭션은 가능한 빨리 완료하자

### 자동 데드락 감지

- InnoDB 스토리지 엔진은 교착 상태 확인을 위해 잠금 대기 목록을 그래프(Wait-for List) 형태로 관리함
    - 데드락 감지 스레드가 주기적으로 이 그래프를 검사해 교착 상태에 빠진 트랜잭션 중 하나를 강제 종료함
- 어떤 걸 먼저 종료할 것인지 기준은 트랜잭션의 언두 로그 양
    - 더 적은 트랜잭션이 일반적으로 대상이 됨
    - 롤백을 해도 해야 할 언두 처리의 내용이 적으니까 MySQL 서버의 부하도 덜 유발하므로
- InnoDB 스토리지 엔진은 상위 레이어인 MySQL 엔진에서 관리되는 테이블 잠금은 볼 수 없어서 데드락 감지가 불확실할 수 있음
    - `innodb_table_locks` 시스템 변수를 활성화하면 감지할 수 있게됨 → 특별한 이유 없으면 활성화하자
- 일반적으로 부담되는 작업은 아니지만 동시 처리 스레드가 매우 많아지거나 잠금의 개수가 많아지면 데드락 감지 스레드가 느려짐
    - 데드락 감지 스레드는 잠금 목록이 저장된 리스트에 새로운 잠금을 걸고 데드락 스레드를 찾음
    - 따라서 이 스레드가 느려지면 서비스 쿼리를 처리 중인 스레드의 대기가 늘어나게 됨
- `innodb_deadlock_detect` 시스템 변수를 비활성화하면 데드락 감지 스레드가 작동하지 않게 됨
    - 그럼 데드락이 발생할 수 있게 되는데..
    - `innodb_lock_wait_timeout` 시스템 변수를 활성화하면 일정 시간 후 요청을 실패하게 함
        - 설정 시간 동안 잠금을 획득하지 못하면 쿼리 실패 후 예외 반환

### 자동화된 장애 복구

InnoDB에는 손실이나 장애로부터 데이터를 보호하기 위한 메커니즘이 여럿 있는데..

서버 시작할 때 이 메커니즘을 이용해 완료되지 못한 트랜잭션이나 일부만 기록된 데이터 페이지 등에 대한 복구 작업이 진행된다

근데 디스크나 하드웨어 이슈로 자동으로 복구를 못하는 경우가 생기는데 이러면 복구하기가 아주 어렵다
← 기본적으로 서버 시작 시 자동 복구를 수행하는데 자동 복구될 수 없는 손상이 있으면 복구를 멈추고 MySQL 서버를 종료
→ 이러면 `innodb_force_recovery`  시스템 변수를 설정해 서버를 시작해야 함(InnoDB 스토리지 엔진이 손상 여부 검사를 선별적으로 진행할 수 있게 함).
1에서 6까지의 값으로 설정하면 됨. 커질수록 심각한 상황

- 0이 아닌 복구 모드에서는 SELECT 이외의 쿼리는 수행이 불가
- 각 숫자에 대한 모드 확인은 책 106~107p 확인

이를 진행했음에도 서버가 시작되지 않으면 백업을 이용하는 방법밖엔 없다..ㅜ

### InnoDB 버퍼 풀

> 디스크의 데이터 파일이나 인덱스 정보를 메모리에 캐시해 두는 공간
> 

쓰기 작업을 지연시키고 일괄 작업으로 처리할 수 있게 해주는 버퍼 역할도 같이 함
← 데이터를 변경하는 쿼리는 일반적으로 랜덤한 디스크 작업을 발생시키는데 버퍼 풀이 이를 모아서 처리하므로 랜덤한 디스크 작업 횟수를 줄일 수 있음

- **크기 설정**
    - 운영체제와 각 클라이언트 스레드가 사용할 메모리를 충분히 고려해서 설정해야 함
    - MySQL 서버 내에서 메모리를 필요로 하는 부분은 잘 없지만 특별한 경우 레코드 버퍼가 상당한 메모리를 차지하기도 함
    - 레코드 버퍼: 각 클라이언트 세션이 테이블의 레코드를 읽고 쓸 때 버퍼로 사용하는 공간
        - 커넥션이 많고 사용하는 테이블이 많은 경우 메모리 공간이 많이 필요할 수도
        - 별도로 설정할 수 없고 커넥션 개수와 테이블의 개수에 따라 결정됨
        - 동적으로 해제되기도 하므로 필요한 메모리를 계산하기 어렵다
    - 근데 MySQL 5.7부터 동적으로 조절할 수 있게 개선됨ㅋㅋ
        - 일단 적절히 작은 값으로 설정한 후 점차 증가시키는 것이 최적
    - 이미 MySQL 서버가 있다면 그 메모리 설정을 기준으로 크기를 조절하면 됨ㅋㅋ
    - 근데 처음 준비해야 하면…
        - 전체 메모리 공간이 8GB면 50% 정도만 버퍼 풀로 설정
        - 전체 메모리 공간이 그 이상이면 50%에서 시작해 점차 올리면서 최적점 찾기
        - 전체 메모리 공간이 50GB 이상이라면 15~30GB 정도를 남겨두고 나머지는 다 할당 ㄱㄱ
    - `innodb_buffer_pool_size`  시스템 변수로 크기 설정 가능
        - 근데 이 변경은 크리티컬한 변경이니까 서버 덜 바쁠 때 진행하는 것이 좋다
        - 그리고 크기를 줄이는 건 서비스 영향도가 매우 크므로 웬만하면 하지 말어라~
    - 버퍼 풀은 내부적으로 128MB의 청크 단위로 관리됨
        - 줄이거나 늘일 때고 이 단위로 처리되니까 참고하셈
    - 원래는 버퍼 풀 전체 잠금(세마포어)를 썼어서 잠금 경합이 많이 있었는데
        - 이를 줄이기 위해 버퍼 풀을 여러 개로 쪼개어 관리할 수 있도록 개선됨
        - 개별 버퍼 풀 전체를 관리하는 잠금 경합이 분산되니까
    - 각 버퍼 풀을 `버퍼 풀 인스턴스`라고 한다
        - 기본적으로 이 개수는 8개로 초기화되지만
        - 버퍼 풀에 할당된 메모리 크기가 1GB 미만이면 1개만 생성됨
        - 메모리 크기가 크면 버퍼 풀 인스턴스당 5GB 정도가 되게 인스턴스 개수를 설정하는 것이 좋음
- **버퍼 풀의 구조**
    - InnoDB 스토리지 엔진은 버퍼 풀의 메모리 공간을 페이지 크기(`innodb_page_system`)의 조각으로 쪼갬
    → 스토리지 엔진이 데이터를 필요로 하면 해당 데이터 페이지를 읽어서 각 조각에 저장함
    - 페이지 크기 조각을 관리하기 위해 LRU(Least Recently Used) 리스트와 플러시 리스트, 프리 리스트라는 3개의 자료구조를 관리함
    - **프리 리스트**: 버퍼 풀에서 실제 사용자 데이터로 채워지지 않은 비어 있는 페이지들의 목록
        - 사용자 쿼리가 새롭게 디스크 데이터 페이지를 읽어와야 하는 경우 사용됨
    - **LRU 리스트**
        - 엄밀하게는 LRU + MRU의 형태라고 보면 됨
        - Old 서브리스트가 LRU, New 서브리스트가 MRU라고 이해하면 됨 ㅋ
        - 어떻게?
            - 버퍼 풀에 있는 것을 읽을 경우 MRU 방향으로 승급
                - MRU의 헤더로 이동한다
            - 새로 가져올 경우 5/8 지점(LRU에 가깝게)에 추가
            - 언제 쿼리가 접근했는지에 따라 나이가 부여됨
            → 오래되면 버퍼 풀에서 제거
            - 자주 접근되는 경우 해당 페이지의 인덱스 키를 어댑티브 해시 인덱스에 추가
        - 어댑티브 해시 인덱스: InnoDB 스토리지 엔진에서 자주 읽히는 데이터의 키값을 이용해 Hash Index를 만들고 필요할 때마다 원하는 레코드를 즉시 찾을 수 있게 함
        - 자주 사용되는 페이지는 MRU 영역에서 계속 살아남게 되고 사용되지 않는 페이지는 LRU의 끝까지 밀려나다가 버퍼 풀에서 삭제된다
    - **플러시 리스트**: 디스크로 동기화되지 않은 데이터를 가진 데이터 페이지의 변경 시점 기준의 페이지 목록
        - 디스크로부터 읽은 상태에서 변경이 가해지면 플러시 리스트에 관리
        → 특정 시점이 되면 디스크로 기록
        - 데이터가 변경되면 변경 내용을 리두 로그에 기록하고 버퍼 풀의 데이터 페이지에도 반영함
        그래서 리두 로그의 각 엔트리는 특정 데이터 페이지와 연결됨
        - but, 리두 로그가 디스크로 기록됐어도 데이터 페이지가 항상 디스크로 기록되는건 아니다(반대의 경우도 생길 수 있음)
        - InnoDB는 체크포인트를 발생시켜 디스크의 리두 로그와 데이터 페이지의 상태를 동기화함
            - 체크포인트는 MySQL 서버가 시작될 때 InnoDB가 리두 로그의 어느 부분부터 복구해야 할지 판단하는 기준점을 만드는 역할

### 버퍼 풀과 리두 로그

버퍼 풀의 용량은 크면 클수록 좋다(모든 데이터가 버퍼 풀에 다 찬 상태가 아닌 이상)

버퍼 풀에는 크게 두 가지 기능이 있는데

1. 디스크의 **데이터 파일 캐시**
2. **쓰기 버퍼링**

메모리 공간을 늘리는 행위는 **데이터 캐시**의 성능을 향상 시키는 것. 버퍼링 기능까지 향상시키려면 리두 로그와의 관계를 이해해야 함

<aside>
💡 **리두 로그**: 데이터베이스에 생긴 변경 이력을 기록해놓은 파일들

</aside>

버퍼 풀은 밑의 두 가지를 갖고 있음

1. **클린 페이지**: 디스크에서 읽은 상태로 전혀 변경되지 않은 상태
2. **더티 페이지**: 변경된 데이터를 갖고 있음
    1. 디스크와 버퍼 풀의 상태가 다르므로 언젠가 디스크로 기록해야 함

즉, 허용 가능한 **더티 페이지의 크기**가 **쓰기 버퍼링의 성능**과 관련이 있음

![image (1)](https://github.com/user-attachments/assets/6373ca76-01fd-4e83-82ab-4555e1ee7e5b)

리두 로그는 1개 이상의 고정 크기 파일을 연결해서 순환 고리처럼 사용함
→ 데이터 변경이 계속 발생하면 리두 로그 파일에 기록됐던 로그 엔트리는 새로운 로그 엔트리로 덮어 쓰임

> 여기서 아직 반영이 안 돼서 덮어 씌우면 안되는 공간, 즉 재사용 불가능한 공간이 **활성 리두 로그** ⇒ 반영해야 되는 리두 로그임
> 

로그 파일은 기록될 때마다 로그 포지션이 증가하는데 이 값을 **`LSN**(Log Sequence Number)`이라고 함.

그리고 각 리두 로그는 더티 페이지와 1대 1로 연결되어 있음

만약 체크포인트 이벤트가 발생하게 된다면 체크포인트 `LSN`보다 작은 리두 로그 엔트리와 관련된 더티 페이지들을 전부 디스크에 동기화한다. ⇒ 이것이 곧 **쓰기 버퍼링**

가장 최근 체크포인트의 `LSN`이 활성 리두 로그 공간의 시작점이고, 마지막 리두 로그 엔트리의 `LSN` 과의 차이를 체크포인트 에이지라고 하는데, 이는 곧 활성 리두 로그 공간의 크기임. 또한 **최대 체크포인트 에이지의 크기**가 곧 **허용 가능한 더티 페이지의 크기**와 관련이 있음.
(최대 체크포인트 에이지 / 평균 리두 로그 엔트리 크기 = 가능한 더티 페이지 개수)

따라서 아무리 버퍼 풀의 크기를 키우더라도 리두 로그의 크기가 변하지 않으면 쓰기 버퍼링의 성능은 증가하지 않게 된다.

버퍼 풀의 크기가 100GB 이하의 MySQL 서버에서는 리두 로그 파일의 전체 크기를 대략 5~10GB로 선택한 후 필요할 때마다 조금씩 늘려가면서 최적값을 선택하는 것이 좋다~ ← 이거 가불기임ㅋㅋ

### 버퍼 풀 플러시

- **더티 페이지 플러시**: 더티 페이지를 디스크에 동기화하는 부분
    - 예전에는 디스크 기록이 폭증하면 MySQL 서버의 사용자 쿼리 처리 성능에 영향을 끼쳤지만, 5.7 버전을 거치고 8.0 버전에 오면서 디스크 쓰기 폭증 현상이 발생하지 않게 되었음
- 이 챕터에서는 더티 페이지 플러시와 관련된 시스템 설정을 설명하지만 특별한 성능 문제가 없다면 **굳이 조정할 필요는 없음**

InnoDB에서는 성능 상의 악영향 없이 더티 페이지 플러시를 수행하기 위해 2가지 플러시 기능을 백그라운드로 실행한다

1. 플러시 리스트 플러시
2. LRU 리스트 플러시

### 플러시 리스트 플러시

InnoDB 스토리지 엔진은 리두 로그 공간 재활용을 위해 오래된 리두 로그 엔트리가 사용하는 공간을 주기적으로 비워야 한다. 근데 이게 지워지려면 더티 페이지가 먼저 동기화돼야 하겠죠?

이 때문에 주기적으로 **플러시 리스트 플러시 함수**를 호출한다
→ 플러시 리스트에서 오래 전에 변경된 페이지 순서대로 **디스크에 동기화**하는 작업 수행

언제부터 얼마나 많은 페이지를 한 번에 동기화하느냐에 따라 성능 영향을 줄 것

**클리너 스레드**: 더티 페이지를 디스크로 동기화하는 스레드

시스템 변수로 이 스레드의 개수를 조정할 수 있지만, InnoDB에서는 버퍼 풀 인스턴스의 개수보다 많은 경우 자동으로 줄여서 개수를 맞춰준다.(한 스레드가 한 인스턴스를 처리하도록)

만약 스레드가 인스턴스 개수보다 적을 경우 한 스레드가 여러 인스턴스를 처리하게 됨.

가능하면 **두 개수를 맞춰주자**

InnoDB에서는 전체 버퍼 풀이 가진 페이지의 90%까지 더티 페이지를 가질 수 있는데 이 비율이 너무 높을 수 있음. 이 때도 시스템 변수를 통해 조정할 수 있다. 하지만 **쓰기 버퍼링 성능은 더티 페이지를 많이 갖고 있을수록 좋아지므로 기본 설정을 유지**하는 것이 좋음.

근데 버퍼 풀에 더티 페이지가 너무 많으면 **디스크 쓰기 폭발 현상** 발생 가능성이 높아진다.

시스템 변수 `innodb_io_capacity`로 설정된 값을 기준으로 더티 페이지 쓰기를 진행하는데 이보다 많은 더티 페이지가 발생하면 버퍼 풀에 더티 페이지가 점점 쌓이게 되고, 90%를 넘어가면 디스크 쓰기가 폭증하는 현상이 발생한다.

이를 완화하기 위해 시스템 변수에 설정된 값에 따라 **일정 수준 이상의 더티 페이지가 발생하면 조금씩 디스크로 동기화**하고 있음. 기본값은 10% 수준인데 더티 페이지가 별로 없을 때도 동기화 작업이 자주 일어나면 이 변수를 올려서 디스크 쓰기 횟수를 줄일 수 있다~

`innodb_io_capacity` , `innodb_io_capacity_max`  값은 백그라운드 스레드가 수행하는 디스크 작업의 크기와 관련되어 있는데 이는 대부분 더티 페이지 쓰기에 해당함. 근데 사용자 쿼리를 수행할 때도 I/O 작업이 일어나므로 io 전체 처리량만큼 저 시스템 변수를 할당하면 안된다 이거야
(물론 저거 설정한 만큼 다 쓰진 않고 최적화를 통해 결정되긴 함)

또한 이 값을 적절하게 설정하는 것은 번거로운데 이를 위해 **어댑티브 플러시**라는 기능을 제공함.
시스템 변수로 켜고 끌 수 있는데 기본값은 일단 사용.
이 기능이 활성화되면 저 **변수에 의존하지 않고 새로운 알고리즘을 사용**함. 더티 페이지 생성 속도(리두 로그 증가 속도)를 분석하고 **적절한 수준의 더티 페이지**가 **버퍼 풀에 유지**될 수 있도록 디스크 쓰기를 실행하더라.
근데 언제? 전체 리두 로그 공간 중 활성 리두 로그 공간이 10% 이상일 때

원래는 디스크 I/O 작업의 효율을 위해 이웃 페이지 동시 쓰기 기능을 시스템 변수를 통해 활성화할 수 있는데, 요즘은 SSD가 많아지면서 굳이 필요가 없어졌다. HDD를 사용한다면 이 값을 1 또는 2로 설정하는 것이 좋다.

### LRU 리스트 플러시

InnoDB는 **LRU 리스트 플러시 함수**를 통해 사용 빈도가 낮은 데이터 페이지들을 제거함으로써 새로운 페이지를 위한 공간을 마련한다.

LRU 리스트의 끝부분부터 최대 시스템 변수로 설정된 개수만큼 페이지들을 스캔하는데, 스캔하면서 더티 페이지는 디스크에 동기화하며 클린 페이지는 프리 리스트로 옮긴다.

### 버퍼 풀 상태 백업 및 복구

서버를 셧다운했다가 다시 시작했을 때 버퍼 풀이 없다면 (당연히) 쿼리 처리 성능이 아주 느려진다.

디스크의 데이터가 버퍼 풀에 적재된 상태를 **워밍업**이라고 하는데, 잘 워밍업된 상태에서는 쿼리 처리 속도가 몇십 배는 빨라짐 ㅋㅋ

그래서 MySQL 5.5 버전에서는 서버를 **다시 시작할 경우** 오픈하기 전에 **강제 워밍업**을 위해 주요 테이블과 인덱스에 **풀 스캔**을 한 번씩 실행하고 오픈했었다.

근데 5.6 버전부터는 **버퍼 풀 덤프 및 적재 기능**이 도입됨

서버를 재시작해야 하는 경우 시스템 변수를 통해 **InnoDB 버퍼 풀의 상태를 백업**할 수 있다. 다시 시작할 경우 시스템 변수를 이용해 **백업된 상태를 다시 복구**할 수 있음

근데 이 백업은 파일로 저장되는데 용량을 보면 실제 버퍼 풀에 비해 아주 작은 것을 알 수 있다
왜? 버퍼 풀의 LRU 리스트에서 적재된 **데이터 페이지의 메타 정보만 저장**하기 때문
→ 백업은 매우 빨리 완료되게 된다!!

근데 백업된 버퍼 풀의 내용을 다시 버퍼 풀로 복구하는 건 버퍼 풀의 크기에 따라 시간이 좀 걸리겠지? 백업된 내용에서 각 테이블의 데이터 페이지를 디스크에서 읽어와야 하니까

만약 너무 오래 걸려서 중간에 멈추고 싶으면 `innodb_buffer_pool_load_abort` 시스템 변수를 이용하면 됨

복구는 디스크 읽기가 아주 많이 발생하므로 이 도중에 서비스를 재개하면 안 좋잖아. 이 때 저 변수를 활성화해서 멈추면 된다~

근데 이거 까먹을 거잖아 ㅋㅋ InnoDB는 셧다운 되기 직전에 백업을 실행하고 시작되면 자동으로 복구할 수 있는 기능을 제공함. 어떻게? 시스템 변수 설정을 MySQL 서버의 설정 파일에 넣어서

### 버퍼 풀의 적재 내용 확인

5.6 버전부터 `information_schema` DB의 `innodb_buffer_page` 테이블을 이용해 버퍼 풀에 어떤 테이블의 페이지들이 적재돼 있는지 알 수 있다

근데 **버퍼 풀이 큰 경우** 이 테이블 조회가 **큰 부하**를 일으켜서 서비스 쿼리가 느려지는 문제도 있
그래서 실제 서비스에선 이 상태를 확인하는 것이 거의 불가능했었음

8.0 버전부터 이를 해결하기 위해 저 디비에 `innodb_cached_indexes` 테이블이 새로 추가됨
이를 이용하면 테이블의 인덱스별로 데이터 페이지가 얼마나 버퍼 풀에 적재돼 있는지 확인 가능

그리고 조금만 응용하면 테이블 전체 페이지 중 어느 정도 비율이 버퍼 풀이 있는지도 확인할 수 있다(쿼리는 책 120쪽)

### Double Write Buffer

InnoDB에서는 리두 로그 공간의 낭비를 막기 위해 **변경된 내용만 기록**하기 때문에 플러시할 때 **일부만 기록되는 문제**(하드웨어나 시스템 문제)가 발생하면 그 페이지는 복구할 수 없을 것
→ 이 현상을 파셜 페이지 또는 톤 페이지라고 함

이를 해결하기 위한 방식이 **Double-Write** 기법

1. 어떤 더티 페이지들을 디스크로 플러시할 때, 이 페이지들을 묶어서 DoubleWrite 버퍼에 기록한다
2. 각 더티 페이지를 파일의 적당한 위치에 하나씩 랜덤으로 쓰기를 실행
    1. 정상적으로 기록되면 더이상 필요가 없어짐
3. 만약 중간에 실패하고 꺼진다면?
4. 재시작될 때 DoubleWrite 버퍼의 내용과 데이터 파일의 페이지들을 전부 비교해서 다를 경우 이 버퍼의 내용을 데이터 파일의 페이지로 복사함

이는 역시 시스템 변수로 제어할 수 있음

**데이터의 무결성**이 매우 중요할 경우 활성화를 고려하자

만약 리두 로그 동기화 설정을 1이 아닌 값으로 설정했다면 비활성화하는 것이 좋음

## 언두 로그

> 언두 로그는 앞에서 설명했듯 변경되기 이전 버전의 데이터
> 
- **트랜잭션 보장**: 롤백이 발생해서 변경 이전의 값으로 복구해야 할 때 사용
- **격리 수준 보장**: 트랜잭션 격리 수준에 맞게 변경된 값이 아닌 이전의 값을 참조해야 할 때 사용

### 언두 로그 모니터링

5.5 이전 버전에서 **한 번 증가한 언두 로그 공간은 다시 줄어들지 않았다**

- 큰 용량의 테이블 전체를 변경(이를테면 삭제)하면 그만큼의 언두 로그가 필요함
- 이 때 뿐만 아니라, 트랜잭션이 오래 동안 실행될 때도 언두 로그의 양이 급격히 증가함
    - 트랜잭션이 완료된다고 해서 그 트랜잭션이 생성한 언두 로그를 즉시 삭제할 수 있는 건 아님
    ← 이전 트랜잭션이 오래 남으면 그만큼 언두 로그를 유지해야 하고, 점점 늘어날 것

5.7을 거치고 8.0이 되면서 이 문제는 해결

언두 로그를 돌아가면서 순차적으로 사용해 디스크 공간을 줄이고 때때로 MySQL 서버가 사용 공간을 자동으로 줄여 주기도 함

근데 그래도 트**랜잭션이 장시간 유지되는 건 성능 상 좋지 않다**

그래서 언두 로그가 얼마나 증가했는지 항상 **모니터링**하는 것이 좋다!

`SHOW ENGINE INNODB STATUS \G` 명령어로 확인 가능하며, 서버별로 언두 로그의 급증 여부를 모니터링하는 것이 좋다!!

> 언두 테이블스페이스: 언두 로그가 저장되는 공간
> 

5.6 버전 이전에는 언두 로그가 시스템 테이블스페이스(ibdata.ibd)에 저장됐었다. 근데 시스템 테이블스페이스의 언두 로그는 서버가 초기화될 때 생성되므로 확장의 한계 있음

5.6 버전에서 시스템 변수가 도입됐는데, 이 값을 조정하면 언두 로그를 시스템 테이블스페이스 대신 별도의 파일을 사용하게 된다.

근데 8.0 버전부터 이 변수는 deprecated 됨 ㅋㅋ. 언두 로그는 항상 시스템 테이블스페이스 외부의 별도 로그 파일에 기록되도록 개선되었다~

하나의 언두 테이블스페이스는 1~128개의 롤백 세그먼트를 가지고, 롤백 세그먼트는 1개 이상의 언두 슬롯을 가진다.

롤백 세그먼트는 페이지 크기를 16바이트로 나눈 값의 개수만큼 언두 슬롯을 가진다. (기본값인 16KB에선 1024개) 

또한 하나의 트랜잭션은 최대 4개의 언두 슬롯을 사용하게 된다. 대략 2개를 필요로 한다고 생각하면 됨

즉 이 언두 슬롯의 전체 개수를 계산하고 2로 나누면 최대 동시 처리 가능한 트랜잭션의 개수를 예측할 수 있을 것

기본값을 따랐을 때, 허용 가능한 동시 트랜잭션 수를 전부 쓸 일은 없겠지만, 부족하면 트랜잭션을 시작할 수 없으므로 그냥 그대로 두는 편이 좋음

언두 테이블스페이스 공간을 필요한 만큼만 남기고 운영체제로 반납하는 것을 `Undo tablespace truncate` 라고 합니다. 이는 자동, 수동 방식이 있음

- **자동 모드**: 트랜잭션이 커밋되어 불필요한 언두 로그들을 퍼지 스레드가 주기적으로 삭제함. 이게 **언두 퍼지**. 시스템 변수 값을 조정하면 이 작업의 빈도를 조절할 수 있음
- **수동 모드**: 언두 테이블스페이스를 비활성화하면 퍼지 스레드는 비활성 사애의 언두 테이블스페이스를 찾아서 잘라내고 운영체제에 반납함. 반납이 완료되면 다시 테이블스페이스 활성화.

## 체인지 버퍼

레코드가 변경되면 데이터 파일뿐 아니라 해당 테이블에 포함된 **인덱스도 업데이트**해주어야 함.

근데 인덱스 업데이트 작업은 랜덤하게 디스크를 읽어야 하므로(non-clustering이니까) 인덱스가 많으면 상당히 **많은 자원을 소모**하게 된다.
그래서 InnoDB는 변경해야 할 인덱스 페이지가 버퍼 풀에 있을 경우 바로 업데이트하지만 디스크에 업데이트해야 할 경우 **즉시 실행하지 않고 임시 공간에 저장**해 두고 바로 사용자에게 결과를 반환함으로써 성능을 향상함. 여기에 사용하는 임시 메모리 공간이 **체인지 버퍼**

근데 유니크 인덱스는 중복 여부를 체크해야 하므로 체인지 버퍼를 사용할 수 없음

이 체인지 버퍼는 백그라운드 스레드인 체인지 버퍼 머지 스레드가 병합한다. 5.5 이전에는 INSERT만 이 버퍼링이 가능했는데 8.0에서는 INSERT, DELETE, UPDATE 작업에서도 가능하도록 개선됐다. 또한 5.5 이전에는 기본적으로 기능이 활성화됐지만 5.5부터 시스템 변수를 통해 작업 종류별로 활성화할 수 있게 바뀌었다. 체인지 버퍼가 비효율적일 때 사용하지 않도록 설정할 수 있게 된 것.

체인지 버퍼는 기본적으로 버퍼 풀 메모리 공간의 25%까지 사용할 수 있게 설정돼있음. 필요하다면 50%까지 설정 가능.

## 리두 로그 및 로그 버퍼

리두 로그는 ACID 중 D(Durable, 영속성)과 연관돼있다. 서버가 비정상 종료됐을 때 데이터 파일에 기록되지 못한 데이터를 잃지 않게 해주는 안전장치임

대부분 데이터베이스 서버는 데이터 변경 내용을 **로그로 먼저 기록**함.

+ 거의 모든 DBMS에서 읽기 성능을 더 고려한 자료 구조를 가지므로 데이터 파일 쓰기는 디스크 랜덤 액세스가 필요하다. 그래서 변경된 데이터를 데이터 파일에 기록하는 건 큰 비용이 필요하다.

→ 이로 인한 성능 저하를 낮추기 위해 쓰기 비용이 낮은 자료 구조를 가진 리두 로그를 갖고 있고, 리두 로그를 버퍼링할 수 있는 버퍼 풀이나 로그 버퍼와 같은 자료 구조도 갖고 있음

만약 비정상 종료가 일어나면 두 종류의 일관되지 않은 데이터가 생길 수 있다

1. 커밋됐지만 데이터 파일에 기록되지 않은 데이터
→ 리두 로그에 저장된 데이터를 데이터 파일에 복사하기만 하면 됨
2. 롤백됐지만 이미 데이터 파일에 기록된 데이터
→ 리두 로그로는 해결할 수 없음. 언두 로그의 내용을 가져와 데이터 파일에 복사해야 함. 물론 커밋/롤백/실행 중인지 상태를 알기 위해 리두 로그가 필요하긴 함

트랜잭션이 종료되면 바로 디스크에 기록하는 것이 좋지만 실제로는 많은 부하 때문에 힘듬. InnoDB에선 어느 주기로 리두 로그를 동기화할지 시스템 변수로 조정 가능

리두 로그 파일들의 전체 크기는 버퍼 풀의 효율성을 결정하므로 신중히 결정해야 함

이 또한 시스템 변수로 리두 로그 파일의 크기와 개수를 결정할 수 있으며, 이 두 변수의 곱이 전체 리두 로그 파일의 크기임. 전체 크기가 버퍼 풀의 크기에 맞게 적절히 선택해야 효율적으로 디스크에 기록할 수 있게 된다.

근데 사용량이 많은 서버의 경우 리두 로그 기록 작업이 큰 문제가 되는데, 이를 보완하기 위해 ACID를 보장하는 선에서 버퍼링한다. 이 버퍼링에 사용되는 공간이 로그 버퍼

로그 버퍼는 기본값인 16MB 수준에서 설정하는 것이 적합하지만 경우에 따라 더 크게 설정해야 할 수도

### 리두 로그 아카이빙

8.0 버전부터 리두 로그를 아카이빙할 수 있는 기능이 생김!

리두 로그에 쌓인 내용을 계속 추적하면서 새로 추가된 리두 로그 엔트리를 복사함. 근데 복사하는 동안 추가되는 로그 엔트리도 백업해줘야 하는데 데이터 변경이 너무 많으면 복사하기도 전에 덮어쓰일 수 있음. 이렇게 복사하지 못한 리두 로그가 덮어쓰이면 백업은 실패하게 됨.
리두 로그 아카이빙 기능은 이래도 백업이 실패하지 않도록 함

이 기능을 사용하려면 아카이빙된 리두 로그가 저장될 디렉터리를 시스템 변수로 설정해야 하며 이 디렉터리엔 운영체제의 MySQL 서버를 실행하는 유저만 접근이 가능해야 함

이렇게 디렉터리가 준비되면 아카이빙이 시작하도록 `innodb_redo_log_archive_start UDF` 를 실행하면 됨

이 UDF(사용자 정의 함수)는 1~2의 파라미터를 입력할 수 있는데, 첫 파라미터는 리두 로그를 아카이빙할 디렉터리에 대한 레이블, 두 번째는 서브디렉터리의 이름인다. 서브디렉터리 이름은 입력하지 않을 경우 시스템 변수의 레이블에 해당하는 디렉터리에 별도 서브디렉터리 없이 리두 로그를 복사한다.

종료할 땐 `~~_stop UDF` 를 실행. 하지만 아카이빙 파일은 삭제되지 않으므로 원한다면 직접 삭제

만약 stop 전에 세션 연결이 끊어지면 아카이빙을 멈추고 파일도 자동으로 삭제해버림. 왜? 아카이빙된 리두 로그가 쓸모 없어지므로.

### 리두 로그 활성화 및 비활성화

원래 리두 로그는 항상 활성화돼 있다.

커밋된 데이터 파일은 즉시 디스크에 기록되지 않지만 리두 로그는 항상 디스크로 기록된다.

8.0 버전부터 수동으로 활성화/비활성화가 가능해졌다. 데이터를 복구하거나 대용량 데이터를 한 번에 적재할 경우 비활성화해서 적재 시간을 단축할 수 있다.

물론 이렇게 할 경우 끝나면 다시 활성화해주는 것을 잊지 말자.
리두 로그가 비활성화된 상태에서 서버가 비정상적으로 종료되면 마지막 체크포인트 이후 시점은 복구가 불가능하니까^^

## 어댑티브 해시 인덱스

> 사용자가 자주 요청하는 데이터에 대해 자동으로 생성하는 인덱스
> 

(당연히 시스템 변수를 이용해 비활성화할 수도 있음)

B-Tree는 여러 노드를 거쳐야 하는데 엄청 많은 스레드가 동시에 실행해야 할 경우 성능이 떨어질 수도

어댑티브 해시 인덱스는 B-Tree 검색 시간을 줄여주기 위해 도입되었음

자주 읽히는 페이지의 키 값을 이용해 해시 인덱스를 만들고, 필요할 때마다 해시 인덱스를 통해 저장된 데이터 페이지를 즉시 찾아갈 수 있다!

B-Tree에서 여러 노드를 거치며 리프 노드를 찾아가는 비용이 없어지기 때문에 CPU 일도 줄이고 성능도 빨라지게 되며, 결국 더 많은 쿼리를 동시에 처리할 수 있게 된다.

해시 인덱스는 **인덱스 키 값**과 해당 인덱스 키 값이 저장된 **데이터 페이지 주소**의 쌍으로 관리됨

인덱스 키 값은 또 **B-Tree 인덱스 id**와 **B-Tree 인덱스의 실제 키 값** 조합으로 생성됨

여기서 어댑티브 해시 인덱스는 하나이지만 B-Tree 인덱스는 여러 개이므로 인덱스의 고유 번호(id)가 필요하다.

데이터 페이지 주소는 실제 키 값이 저장된 데이터 페이지의 메모리 주소 == 버퍼 풀에 로딩된 페이지의 주소임
즉, 어댑티브 해시 인덱스는 버퍼 풀에 올려진 데이터 페이지에 대해서만 관리되고 버퍼 풀에서 나가면 어댑티브 해시 인덱스에서도 정보가 사라진다.

이전에는 어댑티브 해시 인덱스를 하나의 메모리 객체로 사용했기 때문에 경합이 심했다
8.0부터 이를 줄이기 위해 파티션 기능을 제공한다!

시스템 변수를 이용해 파티션 개수를 설정할 수 있으며, 기본은 8개. 어댑티브 해시 인덱스가 성능에 많은 도움이 된다면 이를 늘리는 것도 도움이 될 수 있음

근데 이거 성능 향상에 도움이 안 돼서 비활성화해야 할 때도 있음

- 디스크 읽기가 많은 경우
- 특정 패턴 쿼리가 많은 경우(조인이나 LIKE 패턴 검색)
- 매우 큰 데이터를 가진 테이블의 레코드를 폭넓게 읽는 경우

그리고 아래의 경우엔 도움이 많이 됨

- 디스크 데이터가 버퍼 풀 크기와 비슷한 경우(디스크 읽기가 많지 않은 경우)
- 동등 조건 검색(나 IN 연산자)이 많은 경우
- 쿼리가 데이터 중 일부 데이터에만 집중되는 경우

근데 이를 판단하기 쉽지 않지만, 어댑티브 해시 인덱스는 메모리 내에서 접근을 빠르게 하므로 디스크 읽기가 빈번한 경우엔 아무런 도움이 되지 않는다!!!!

또한 때때로 상당히 큰 메모리 공간을 사용할 수도 있고, 매번 어댑티브 해시 인덱스에 존재하는지 확인해봐야 하는 오버헤드도 생김

그리고 테이블을 삭제(DROP)하거나 변경(ALTER)하려고 하면 이 테이블이 가진 모든 데이터 페이지의 내용을 어댑티브 해시 인덱스에서 제거해야 함 → 상당히 많은 CPU 자원을 사용해 서버 처리 성능이 느려지게 된다

즉, 어댑티브한테 많이 도움받을 수록 테이블 삭제/변경 작업이 더 치명적이게 되는 것

도움이 되는지 오버헤드만 만드는지 판단해야 하는데, MySQL 서버의 상태 값들을 살펴보면 알 수 있다.

이를 통해 해시 인덱스 히트율을 알 수 있고 이 값을 해시 인덱스가 사용 중인 메모리 공간, 서버의 CPU 사용량과 종합해서 판단할 수 있음ㅋㅋ

### InnoDB와 MyISAM, MOMORY 스토리지 엔진 비교

이전에는 MyISAM이 기본 스토리지 엔진으로 사용되는 경우가 많았지만 5.5부터 InnoDB가 기본 스토리지 엔진으로 채택됨. 근데 서버의 시스템 테이블은 MyISAM 테이블을 사용했고, 전문검색, 공간 좌표 검색은 MyISAM에서만 지원됐었다.

근데 8.0부터는 모든 시스템 테이블이 InnoDB로 교체됐고, 위의 기능들도 전부 지원되도록 개선됐다.

→ MyISAM은 도태되는 상황이고 이후 버전에서는 사라질 것으로 예상됨

MyISAM만이 가지는 장점이 없는 상태다 ㅋㅋ

MEMORY 스토리지 엔진은 모든 처리를 메모리에서 하므로 빠르다고 예상할 수 있지만 동시 처리 성능이 중요한 온라인 트랜잭션 처리에서는 잠금 수준으로 인해 제대로 된 성능을 내지 못할 것

이거도 원래는 내부 임시 테이블의 용도로 사용됐지만 요즘 TempTable에 의해 대체되고 있으며 이 또한 향후 버전에서 제거될 것

## MyISAM 스토리지 엔진 아키텍처

### 키 캐시

InnoDB의 버퍼 풀과 비슷한 역할

인덱스만을 대상으로 작동하며, 인덱스의 디스크 쓰기 작업에 대해서만 부분적으로 버퍼링 역할을 함

키 캐시를 이용한 쿼리의 히트율을 99퍼 이상으로 유지하는 것이 매뉴얼, 미만이라면 키 캐시를 더 크게 설정하는 것이 좋음

### 운영체제의 캐시 및 버퍼

MyISAM 인덱스는 키 캐시를 이용해 디스크를 검색하지 않고 충분히 빠르게 검색할 수 있다

근데 디스크로부터의 I/O를 해결해 줄 어떠한 캐시나 버퍼링 기능도 갖고 있지 않다!

그래서 데이터 읽기/쓰기 작업은 항상 운영체제의 디스크 읽기/쓰기 작업으로 요청된다

물론 운영체제에는 디스크로부터 읽고 쓰는 파일에 대한 캐시나 버퍼링 매커니즘을 탑재하고 있으므로 매번 디스크 파일을 읽지는 않음

InnoDB처럼 데이터의 특성을 알고 전문적으로 캐시/버퍼링을 하진 못하지만 없는 것보단 나음

운영체제 캐시 공간은 남는 메모리를 사용하기 때문에 다른 애플리케이션에서 메모리를 모두 사용하면 캐시 메모리가 없어짐. 이렇게 되면 MyISAM 테이블에 대한 쿼리 처리가 느려진다.

그러므로 운영체제가 사용할 수 있는 캐시 공간을 위한 메모리를 마련해 두자

### 데이터 파일과 프라이머리 키(인덱스) 구조

MyISAM은 InnoDB와 달리 프라이머리 키에 의한 클러스터링 없이 데이터 파일이 힙 공간처럼 활용됨

즉, 프라이머리 키 값과 무관하게 INSERT 되는 순서대로 데이터 파일에 저장

그리고 저장되는 레코드는 모두 `ROWID` 라는 물리 주솟값을 가지는데 프라이머리 키와 세컨더리 인덱스는 모두 데이터 파일에 저장된 레코드의 `ROWID` 값을 포인터로 가짐

가변 길이, 고정 길이의 두 가지 방법으로 저장될 수 있음

- 고정 길이: 옵션을 명시하면 서버는 최대로 가질 수 있는 레코드가 한정된 테이블을 생성함
→ `ROWID` 값으로 4바이트 정수를 사용(레코드가 삽입된 순서)
- 가변 길이: 시스템 변수에 정의된 값만큼의 공간을 사용할 수 있음. 기본이 7이라 2~7바이트까지 가변적인 값을 갖게 된다. 첫 바이트는 길이를 저장하고 나머지는 실제 값을 저장

## MySQL 로그 파일

로그 파일을 이용하면 MySQL의 상태나 부하를 일으키는 원인을 쉽게 찾아서 해결할 수 있음

서버에 문제가 생기면 로그 파일들을 자세히 확인하는 습관이 도움이 된다

### 에러 로그 파일

실행되는 도중 발생하는 에러나 경고 메시지가 출력되는 로그 파일

- MySQL이 시작하는 과정과 관련된 정보성 및 에러 메시지
    - 설정 파일을 변경하거나 비정상적으로 종료된 이후 다시 시작하는 경우에는 반드시 에러 로그 파일을 통해 설정된 변수의 이름이나 값이 잘 적용됐는지 확인해야 함
    - 정상적으로 기동했는지 확인할 수 있고 변경하거나 추가한 파라미터에 대한 에러가 없다면 정상적으로 적용된 것
- 비정상적으로 종료된 경우 나타나는 InnoDB의 트랜잭션 복구 메시지
    - 비정상 종료 시 다시 시작되면서 완료되지 못한 트랜잭션을 정리하고 기록되지 못한 데이터를 기록하는 재처리 작업을 한다
    - 문제가 생겨 복구되지 못할 때 에러 메시지를 출력하고 다시 종료됨
    - 시스템 변수를 조정해서 다시 재시작해야 한다
- 쿼리 처리 도중 발생하는 문제에 대한 에러 메시지
    - 주기적으로 검토하면 데이터베이스에 숨겨진 문제점을 해결하는 데에 도움이 됨
- 비정상적으로 종료된 커넥션 메시지(Aborted connection)
    - 로그 파일을 보면 메시지가 상당히 많이 누적된 경우가 있다. 클라이언트 애플리케이션이 정상적으로 접속 종료를 못하고 종료된 경우 에러 로그 파일에 이런 내용이 기록된다.
    - 아주 많이 기록된다면 커넥션 종료 로직을 검토해볼 필요가 있다
- InnoDB의 모니터링 또는 상태 조회 명령의 결과 메시지
    - 테이블/락 모니터링, 엔진 상태를 조회하는 명령은 상대적으로 큰 메시지를 에러 로그 파일에 기록함
    - 모니터링을 활성화 상태로 두고 유지하면 에러 로그 파일이 매우 커져서 파일 시스템의 공간을 많이 사용해 버릴수 있음
    - 그러므로 모니터링 사용 후에는 비활성화해야 한다 ㅋㅋ
- MySQL의 종료 메시지
    - 가끔 MySQL이 아무도 모르게 종료되거나 재시작되는 경우가 있다
    - 이 경우 에러 로그 파일에서 종료할 때 출력한 메시지를 확인해야 한다
    - 누가 종료했다거나, 세그먼테이션 폴트로 비정상 종료됐다거나 등의 상황을 파악할 수 있다

### 제너럴 쿼리 로그 파일(제너럴 로그 파일, General log)

MySQL 서버에서 실행되는 쿼리로 어떤 것들이 있는지 목록을 뽑아서 검토하고 싶다면, 쿼리 로그를 활성화해서 쿼리 로그 파일에 기록되도록 한 후 그 파일을 검토하면 된다.

시간 단위로 실행됐던 쿼리 내용이 모두 기록된다.

슬로우 쿼리 로그와 다르게 실행되기 전에 요청을 받으면 바로 기록하므로 에러가 발생해도 로그 파일 기록된다

쿼리 로그 파일의 경로는 `general_log_file` 이라는 이름의 파라미터에 설정되어 있지만 파라미터를 통해 테이블에 저장할 수도 있다

### 슬로우 쿼리 로그

MySQL 쿼리 튜닝은

1. 서비스가 적용되기 전 전체적으로 튜닝하는 경우
2. 서비스 운영 중 전체적인 성능 저하를 검사하거나 정기적인 점검을 위한 튜닝

으로 나눌 수 있다

근데 후자의 경우 어떤 쿼리가 문제의 쿼리인지 판단하기가 어렵다
← 슬로우 쿼리 로그가 도움이 된다!

슬로우 쿼리 로그 파일엔 시스템 변수에 설정한 시간 이상의 시간이 소요된 쿼리가 모두 기록됨

MySQL이 쿼리를 실행한 후 실제 소요한 시간을 기준으로 기록할지 여부를 판단하므로 정상적으로 실행이 완료돼야 로그에 기록할 수 있다

즉, 기록된 쿼리는 일단 정상적으로 실행 완료됐지만 일정 시간보다 오래 걸린 쿼리인 것

옵션을 이용하면 파일로 기록할지 테이블로 기록할지 선택할 수 있음
근데 테이블로 설정해도 CSV 스토리지 엔진을 사용하므로 파일로 저장하는 것과 동일하게 작동된다(제너럴 로그도 마찬가지)

근데 내용을 보면 엔진 레벨, 스토리지 레벨의 잠금을 둘 다 갖고 있어서 내용이 혼란스럽다 ㅋ

`Lock_time` 의 경우 엔진 레벨의 테이블 잠금에 대한 대기 시간이지만 코드 실행 부분의 시간까지 포함되므로 매우 작은 값이면 무시해도 무방함
→ InnoDB 테이블의 슬로우 쿼리 로그에서 `Lock_time` 값은 튜닝이나 쿼리 분석에 별로 도움 안됨

상세한 내용은 책 151페이지 ㄱㄱ

일반적으로 슬로우, 제너럴 쿼리 로그는 내용이 상당히 많아 검토하기 어렵다.

Percona의 Precona Toolkit의 `pt-query-digest` 스크립트를 이용하면 빈도나 처리 성능별로 쿼리를 정렬해서 살펴볼 수 있음

아래의 상세 정보는 책 152~153을 참고해서 확인하자

### 슬로우 쿼리 통계

분석 결과의 최상단에 표시

모든 쿼리 대상으로 슬로우 쿼리 로그의 실행 시간, 잠금 대기 시간 등에 대해 평균, 최대, 최소 값을 표시

### 실행 빈도 및 누적 실행 시간순 랭킹

쿼리별 응답 시간과 실행 횟수를 보여주는데, 특정 명령 실행 시 옵션을 통해 정렬 순서를 변경할 수 있다

Query id는 실행된 쿼리 문장을 정규화해 만들어진 해시 값을 의미 → 같은 모양의 쿼리면 같은 id를 갖게 됨

### 쿼리별 실행 횟수 및 누적 실행 시간 상세 정보

Query id 별 쿼리 랭킹에 표시된 순서대로 자세한 내용 보여줌

랭킹별 쿼리에선 어떤 쿼리인지만을 표시하고 개별 쿼리의 정보를 확인하면 얼마나 실행됐는지, 응답 시간에 대한 히스토그램 등을 확인할 수 있다.
