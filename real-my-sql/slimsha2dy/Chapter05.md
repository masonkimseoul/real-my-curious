## 트랜잭션

트랜잭션은 **작업의 안전성**을 보장해 주는 것이다

한 **작업 셋**을 전부 처리하도록 하거나 전부 처리되지 않으면 복구하는 기능

- 잠금과 트랜잭션의 차이
    - **잠금(Lock)**: 동시성을 제어하기 위한 기능
    - **트랜잭션**: 데이터의 정합성을 보장하기 위한 기능

### MySQL에서의 트랜잭션

트랜잭션은 사실 **쿼리의 개수와 상관없이**(한 개여도) 논리적인 작업 셋 전체가 전부 적용되거나 전부 적용되지 않아야 함을 보장해 주는 것

MyISAM에서는 MySQL에서와 달리 오류가 발생했을 때 부분 업데이트(Partial Update)가 발생해 오류 발생 전까지의 데이터가 반영되어 있다.

이렇게 부분 업데이트가 발생하게 되면 실패한 쿼리로 인해 남은 레코드를 다시 삭제해야 함
→ 오히려 신경 쓸 부분이 많아짐

### 주의사항

DBMS의 커넥션처럼 **필요한 최소의 코드에만 적용**하는 것이 좋음

- 각 단위 프로그램이 커넥션을 소유하는 시간이 길어질수록 사용 가능한 여유 커넥션의 개수가 줄어듬
→ 커넥션을 가져가기 위해 기다려야 하는 상황이 발생할 수 있음
- 트랜잭션 안에서 원격 서버와 통신하는 작업을 하다가 통신이 불가능한 경우가 발생하면 서버가 위험해진다

따라서 트랜잭션이 꼭 필요한 부분에만 넣어주자

## MySQL 엔진의 잠금

**스토리지 엔진 레벨**과 **MySQL 엔진 레벨**의 잠금으로 나뉜다

- MySQL 엔진 레벨의 잠금
    - 모든 스토리지 엔진에 영향을 미친다
    - 테이블 데이터 동기화를 위한 테이블 락, 테이블의 구조를 잠그는 메타데이터 락, 네임드 락 등

### 글로벌 락

`FLUSH TABLES WITH READ LOCK`  명령으로 획득이 가능

MySQL **서버 전체**가 범위이며, MySQL이 제공하는 잠금 중 범위가 가장 큼
← 작업 대상 테이블이나 데이터베이스가 다르더라도 동일하게 영향을 미침

한 세션이 글로벌 락을 획득하면 해제될 때까지 다른 세션에서는 `SELECT` 를 제외한 대부분의 문장이 **대기 상태**로 남음

여러 DB에 존재하는 MyISAM/MEMORY 테이블에 대해 `mysqldump` 로 일관된 **백업**을 받아야 하는 경우 사용한다!

`mysqldump` 같은 백업 프로그램은 우리가 모르는 새에 이 명령을 내부적으로 사용하고 백업할 때도 있음 ㅋㅋ 이 백업을 사용한다면 옵션에 따라 서버에 어떤 잠금을 거는지 살펴보는게 좋다

근데 이제는 MyISAM이나 MEMORY 보다는 InnoDB의 사용이 일반화됐고 이노디비는 트랜잭션이 지원되므로 이러한 잠금을 걸 필요가 없다!

조금 더 가벼운 글로벌 락의 필요성 → 백업 툴들의 안정적 실행을 위해 **백업 락**이 도입됨

- 백업 락: 특정 세션에서 백업 락을 획득하면 모든 세션에서 다음 정보를 변경할 수 없게 됨
    - 데이터베이스 및 테이블 등 모든 객체 생성 및 변경, 삭제
    - REPAIR TABLE과 OPTIMIZE TABLE 명령
    - 사용자 관리 및 비번 변경
- 하지만 일반적인 테이블의 데이터 변경은 가능

### 테이블 락

개별 테이블 단위로 설정되는 잠금

- 명시적인 방법: `LOCK TABLES table_name [ READ | WRITE ]`
    - MyISAM과 InnoDB 동일
    - `UNLOCK TABLES` 명령으로 잠금 반납
    - 특별한 상황이 아니면 사용할 필요가 없다
- 묵시적인 방법: MyISAM이나 MEMORY 테이블에 데이터 변경하는 쿼리를 실행
    - 변경되는 테이블에 잠금을 걸고 변경 후 즉시 해제
    - InnoDB는 스토리지 엔진 차원에서 레코드 잠금을 제공하므로 X

### 네임드 락

함수를 이용해 **임의의 문자열**에 대해 잠금

테이블이나 레코드, 데이터베이스 객체가 대상이 아니다

사용자가 **지정한 문자열**에 대해 획득하고 반납하는 잠금

자주 사용되지 않음

**여러 웹 서버**가 **한 DB 서버**에 접근할 때 **동기화**가 가능

책 163페이지 확인

- 또한 많은 레코드에 대해 복잡한 요건으로 레코드를 변경하는 트랜잭션에 유용함
    - 배치 프로그램처럼 많은 레코드를 변경하는 쿼리는 데드락 발생 확률이 높음
    - 프로그램끼리 분류해서 네임드락을 걸고 쿼리를 실행하면 해결 가능 ㅋ

### 메타데이터 락

테이블, 뷰 같은 데이터베이스 객체의 이름이나 구조를 변경하는 경우 획득하는 잠금

명시적으론 불가

테이블의 이름을 변경하는 경우 자동으로 획득함

실시간으로 테이블을 바꿀 수도 있는 배치 프로그램에서도 자주 발생

## InnoDB 스토리지 엔진 잠금

레코드 기반 잠금을 통해 MyISAM보다 뛰어난 동시성 처리가 가능

근데 MySQl 명령으로 이 잠금 정보에 접근하기 까다로움

예전엔 `lock_monitor` 라는 방법과 `SHOW ENGINE INNODB STATUS` 밖엔 없었는데 내용 이해가 어려움

최근엔 트랜잭션, 잠금, 잠금 대기 트랜잭션 목록을 조회할 수 있어짐!
→ MySQL 서버의 `information_schema` 데이터베이스의 여러 테이블(167p)을 조인해서 조회하면 확인 가능 ㅋㅋ

또한 Performance Schema를 이용해 내부 잠금에 대한 모니터링 방법도 추가됨

### InnoDB 스토리지 엔진의 잠금

잠금 정보가 상당히 작은 공간으로 관리되므로 `레코드락 -> 페이지락 or 테이블락` 으로 레벨업되는 경우는 없음

일반 DBMS와 다르게 레코드 사이를 잠그는 갭 락이 존재함

### 레코드 락

다른 상용 DBMS와 달리 레코드 자체가 아닌 인덱스의 레코드를 잠금
← 인덱스가 없더라도 내부적으로 생성된 클러스터 인덱스를 통해 잠금

이는 꽤 차이가 크다

InnoDB에선 대부분 보조 인덱스를 이용한 변경 작업에 넥스트 키 락 또는 갭 락을 사용하지만, 프라이머리 키 또는 유니크 인덱스에 의한 변경 작업은 갭에 대해서 잠그지 않음

### 갭 락

레코드와 바로 인접한 레코드 사이의 간격만 잠그는 것

레코드 사이에 새로운 레코드가 생성되는 것을 제어함

이거만 쓰진 않고 넥스트 키 락의 일부로 자주 사용됨

### 넥스트 키 락

레코드 락 + 갭 락

일반적으로(REPEATABLE READ)의 경우 이 방식으로 잠금이 걸리는데, 이는 바이너리 로그에 기록되는 쿼리가 레플리카 서버에서 실행될 때 소스 서버의 결과와 동일한 결과를 보장하는 것이 목적

근데 이 락 때문에 데드락이 발생하거나 트랜잭션 대기가 자주 발생하므로 가능하다면 바이너리 로그 포맷을 ROW 형태로 바꿔서 락을 줄이는 것이 좋음
← 8.0에선 ROW 포맷이 기본 설정임

### 자동 증가 락

자동 증가하는 숫자 값을 추출하기 위해 `AUTO_INCREAMENT` 칼럼 속성을 제공

여러 레코드가 INSERT 되는 경우 저장된 순서대로 증가하는 일련번호 값을 가져야 함!
← 이를 위해 자동 증가 락을 사용

- 새로운 레코드를 저장하는 쿼리(INSERT, REPLACE)에서만 필요함
- 다른 잠금과 달리 트랜잭션 무시하고 `AUTO_INCREAMENT` 값을 가져오는 그 순간만 잠금
- 테이블에 단 하나만 존재하므로 두 INSERT가 동시에 실행되면 나머지 쿼리는 이 락을 기다려야 함
- 명시적 획득/해제 방법은 없음
- 아주 짧은 시간만 걸리는 거라 대부분 문제가 안됨
- 5.1 이상부턴 시스템 변수를 통해 다른 방식으로 변경 가능
    1. 0: 위의 설명
    2. 1: INSERT하는 SQL 중 MySQL 서버가 INSERT 레코드의 건수를 정확히 예측 가능하면 저 락 대신 래치(뮤텍스)를 이용해 처리함
        1. 이는 아주 짧은 시간만 잠금을 걸고 필요한 자동 증가 값을 가져오면 잠금이 해제됨
        2. INSERT … SELECT 같이 서버가 건수를 예측 못하면 위의 락을 사용
        3. 대량 INSERT가 수행될 대 여러 자동 증가 값을 한 번에 할당받아 레코드에 사용함
        4. 대신 이 값이 남으면 중간에 값이 누락된다 ← 그러므로 자동증가를 사용해서 이를 막음
    3. 2: 무조건 래치 사용
        1. 따라서 연속된 자동 증가 값을 보장하지 않음, 유니크만 보장
        2. 동시 처리 성능이 높아짐
- 참고로 AUTO_INCREAMENT의 잠금을 최소화하기 위해 INSERT 쿼리가 실패한다고 값이 다시 줄어들진 않음

### 인덱스와 잠금

변경해야 할 레코드를 찾기 위해 검색한 인덱스의 레코드를 모두 잠금

예를 들어

```sql
// Georgi가 성인 사람이 253명, 저게 성이고 Klassen이 이름인 사람 1명인 경우
UPDATE employees SET hire_date=NOW() WHERE first_name='Georgi' AND last_name='Klassen';
```

위의 쿼리를 실행하기 위해 사용되는 인덱스는 `first_name=’Georgi’` 
→ 253건의 레코드가 모두 잠기게 됨

만약 인덱스가 없다면 full scan을 하면서 모든 레코드를 잠근다

### 레코드 수준의 잠금 확인 및 해제

레코드 수준의 잠금은 레코드 각각에만 걸리므로 그 레코드가 자주 사용되지 않으면 오래 잠금이 걸려있어도 확인이 힘듬

`performance_schema` 의 테이블을 이용해 잠금과 잠금 대기 순서를 확인할 수 있다

상세한 방법은 173 페이지 확인

확인하고 `KILL` 명령어를 통해 스레드를 종료하면 해결할 수 있다

## MySQL의 격리 수준

> **격리 수준**: 여러 트랜잭션이 동시에 처리될 때 특정 트랜잭션이 다른 트랜잭션에서 변경/조회하는 데이터를 볼 수 있게 허용할지 말지를 결정하는 것
> 

4개의 격리 수준에서 순서대로 뒤로 갈수록 각 트랜잭션 간의 격리 정도가 높아지고 동시 처리 성능이 떨어지는 것이 일반적
→ 근데 사실 `SERIALIZABLE` 이 아니면 크게 성능의 개선이나 저하는 발생하지 않음

- SQL 표준에 따르면 `REPEATABLE READ` 격리 수준에선 `PHANTOM READ` 가 발생할 수 있지만 InnoDB는 특성 상 발생하지 않는다
- 일반적인 온라인 서비스 용도의 데이터베이스는 `READ COMMITED` , `REPEATABLE READ` 중 하나를 사용함
    - 오라클 같은 DBMS는 주로 `READ COMMITED` 를, MySQL에서는 `REPEATABLE READ` 를 주로 사용

### READ UNCOMMITED

각 트랜잭션에서의 변경 내용이 커밋/롤백 여부에 상관 없이 다른 트랜잭션에서 보임

근데 커밋 이전에 데이터를 읽었는데 롤백이 일어나면 잘못된 데이터를 알고 있는 문제가 발생 ⇒ **더티 리드**

정합성에 문제가 많으므로 사용하지 마셈 ㅋㅋ

### READ COMMITED

오라클 DBMS에서 기본이고 온라인 서비스에서 가장 많이 선택되는 격리 수준

- **커밋이 완료된 데이터**만 다른 트랜잭션에서 조회할 수 있음
    - 언두 영역에 백업된 레코드에서 가져옴 ㅋㅋ
- 근데 중간에 다른 트랜잭션이 커밋으로 데이터를 변경했는데, 트랜잭션이 이 데이터를 두 번 읽어서 일치하지 않는 문제가 발생할 수 있음 ⇒ `NON-REPEATABLE READ`
    - 일반적인 웹 프로그램에선 크게 문제되지 않을 수 있지만 위 요청이 금전적인 처리와 연결되면 문제가 생길 수 있음

### REPEATABLE READ

**InnoDB에서 기본**적으로 사용되는 격리 수준

- 바이너리 로그를 가진 MySQL 서버에서는 최소 `REPEATABLE READ` 이상의 격리 수준을 사용해야 함
- InnoDB는 롤백 가능성을 대비해 언두 공간에 데이터를 백업하고 변경함 == MVCC
    - 이 언두 공간의 데이터를 읽어온다

근데 이건 `READ COMMITED` 도 마찬가지임 ㅋㅋ

언두 영역에 백업된 레코드의 여러 버전 가운데 몇 번째 이전 버전까지 찾아 들어가야 하느냐의 차이

이노디비 트랜잭션은 고유한 트랜잭션 번호(순차증가)를 가지고 언두 영역에 백업된 모든 레코드에는 변경을 발생시킨 트랜잭션의 번호가 포함됨

불필요하고 판단하는 시점에 주기적으로 삭제 ← `REPEATABLE READ`에선 MVCC를 위해 실행 중인 가장 오래된 트랜잭션 번호보다 앞선 데이터는 삭제할 수 없음

정확히는 특정 트랜잭션 번호의 구간 내에서 백업된 언두 데이터가 보존되어야 함

- `PHANTOM READ`: 변경 작업에 의해 레코드가 보였다 안 보였다 하는거
    - 일반적인 DBMS의 경우 두 `SELECT` 문 사이에 삽입이 발생하면 읽어온 데이터의 갯수가 달라질 수 있음
    - InnoDB의 경우 자신 이후에 실행된 트랜잭션의 데이터가 있다면 언두로그를 참고해서 데이터를 조회함
        
        ![t1](https://github.com/user-attachments/assets/9d612321-eb40-4769-b602-b36d4c73947c)

        - 자기보다 나중 번호가 삽입한 데이터는 무시하면 되므로 `PHANTOM READ` 는 발생하지 않음
    - 근데 `SELECT ... FOR UPDATE` 나 `SELECT ... LOCK IN SHARE MODE` 처럼 쓰기 잠금을 거는 조회 명령의 경우 `PHANTOM READ` 가 발생한다 왜?
    ← 언두 레코드에는 잠금을 걸 수 없으므로 언두 영역이 아닌 현재 레코드의 값을 가져오기 때문
        - 언두 로그는 append only 형태이므로 잠금 장치가 없음
    - 근데 그렇다 해도 InnoDB에는 갭 락과 넥스트 키 락이 있으므로 문제가 발생하지 않는다
        
        ![t2](https://github.com/user-attachments/assets/2e0a87f7-8b61-4901-a022-164674be5829)

        - 하지만 사용자 B의 첫 SELECT가 잠금이 없다면 사용자 A의 트랜잭션은 바로 커밋되므로 이런 경우에만 `PHANTOM READ` 가 발생한다!
- 정리
    - SELECT FOR UPDATE 이후 SELECT: 갭락 때문에 팬텀리드 X
    - SELECT FOR UPDATE 이후 SELECT FOR UPDATE: 갭락 때문에 팬텀리드 X
    - SELECT 이후 SELECT: MVCC 때문에 팬텀리드 X
    - SELECT 이후 SELECT FOR UPDATE: 팬텀 리드 O

### SERIALIZABLE

가장 단순하고 엄격하지만 동시 처리 성능이 떨어짐

InnoDB에서 순수한 SELECT 작업은 아무런 레코드 잠금도 없이 실행됨

하지만 이 격리 수준에선 읽기 작업도 공유 잠금을 획득해야 하고 다른 트랜잭션에서는 그 레코드를 변경할 수 없음

`PHANTOM READ` 가 발생하지 않지만 InnoDB에서는 `REPEATABLE READ` 에서도 이미 발생하지 않으므로 굳이 사용할 필요가 없음 ㅋㅋ
