## 9.1 개요
옵티마이저: DBMS에서 쿼리의 최적 실행 계획을 수립하는 작업을 담당하는 요소

### 9.1.1 쿼리 실행 절차
1. 파싱
	- 사용자로부터 요청된 SQL 문장을 잘게 쪼개서 Parse Tree 형성
2. 테이블 선택
	- Parse Tree를 확인하면서 어떤 테이블부터, 어떤 인덱스를 활용하여 읽을지 선택
3. 데이터 가져오기
	- 결정된 테이블의 읽기 순서나 선택된 인덱스를 이용해 스토리지 엔진으로부터 데이터 가져옴

### 9.1.2 옵티마이저의 종류
옵티마이저는 크게 두 가지로 나눌 수 있다.
- 규칙기반 최적화(RBO): 옵티마이저에 내장된 우선순위에 따라 실행 게획을 수립
	- 통계 정보를 별도로 반영하지 않는다.
- 비용기반 최적화(CBO): 통계정보 등을 사용하여 최소 비용을 산출
    - 요즘은 대부분의 RDBMS는 비용기반 최적화를 사용하고 있다.

## 9.2 기본 데이터 처리
- RDBMS 마다 데이터를 가공하는 방법은 천차만별이다.
- MySQL에서 데이터를 정렬, Grouping 등을 처리하는 방법을 설명한다.

### 9.2.1 풀 테이블 스캔과 풀 인덱스 스캔
**풀 테이블 스캔**: 인덱스를 사용하지 않고 테이블을 처음부터 끝까지 읽어서 처리한다.
- **테이블 레코드 건수가 너무 적어서** 인덱스를 통해 읽는 것보다 테이블을 직접 읽는 것이 빠를 때
- 인덱스를 사용할 적절한 `WHERE`, `ON` 절 조건이 없을 때
- 통계를 기준으로 **일치하는 데이터 건수가 너무 많을 때**
- InnoDB는 풀 테이블 스캔 시 백그라운드 스레드를 이용하여 앞으로 필요할 것 같은 페이지를 미리 읽어 버퍼 풀로 가져온다. (Read Ahead)  
**풀 인덱스 스캔**: 인덱스를 처음부터 끝까지 읽어서 처리한다.

```sql
select count(*) from employees;
```
위의 쿼리는 풀 테이블 스캔을 할 것처럼 보이지만 레코드 건수만 필요로 한다면 용량이 작고 빠른 인덱스를 선택한다.

```sql
select * from employees;
```
그러나 위와 같이 인덱스에 없는 테이블 레코드가 필요한 쿼리는 풀 테이블 스캔을 한다.

### 9.2.2 병렬 처리
MySQL 8.0 이후부터 하나의 쿼리에 대해 여러 스레드가 병렬 처리를 할 수 있게 되었다.

> [!INFO] 병렬 처리의 의미  
> 여기서 말하는 '병렬 처리'란 하나의 쿼리를 여러 스레드가 작업을 나누어 동시에 처리한다는 것을 의미한다. 여러 스레드가 동시에 각각의 쿼리를 처리하는 것은 MySQL 서버 초기 버전에서도 가능했다.

`innodb_parallel_read_threads` 라는 변수로 하나의 쿼리를 최대 몇개의 스레드가 처리할지 설정할 수 있다.

### 9.2.3 `ORDER BY` 처리(Using filesort)
정렬을 처리하는 방법은 **인덱스를 이용하는 방법**과 쿼리가 실행될 때 **Filesort라는 별도의 처리를 이용**하는 방법으로 나눌 수 있다.
1. 인덱스를 이용한 정렬
	- 장점: 인덱스는 이미 정렬되어 있으므로 조회가 매우 빠르다.
	- 단점: `INSERT`, `UPDATE`, `DELETE` 작업 시 부가적인 인덱스 추가, 삭제 작업이 필요하므로 느리다.
2. Filesort를 이용한 정렬
	- 장점: 인덱스를 생성하지 않아도 되므로 삽입, 갱신, 삭제가 상대적으로 빠르다.
		- 정렬해야 할 레코드가 많지 않다면 Filesort는 메모리에서 처리되므로 충분히 빠르다.
	- 단점: 정렬 작업이 쿼리를 실행할 때 처리되므로 레코드 대상 건수가 많아질수록 느리다.

- 인덱스를 사용하지 못하는 경우
    - 정렬 기준이 너무 많아서 모두 인덱스를 생성할 수 없을 때
    - `GROUP BY`의 결과 또는 `DISTINCT` 같은 처리 결과를 정렬할 때
    - `UNION`의 결과와 같이 임시 테이블의 결과를 다시 정렬할 때
    - 랜덤하게 결과 레코드를 가져올 때

실행계획의 Extra 컬럼에 'Using filesort' 메시지 포함 여부를 통해 Filesort 사용 여부를 확인할 수 있다. 

#### 9.2.3.1 소트 버퍼
> MySQL에서 정렬을 수행하기 위해 할당받는 별도의 메모리 공간

- 최대 사용 가능한 소트 버퍼의 크기는 `sort_buffer_size` 변수로 설정할 수 있다.
- 만약 $recordCntToSort > sortBuffer.size$ 인 경우 소트버퍼에서 부분 정렬을 수행한 후 디스크에 쓰고, 다시 해당 버퍼만큼 읽어서 정렬을 수행하고 병합하고 하는 과정을 반복해야 한다.
	- Multi Merge, External Sort(외부정렬)
- 소트 버퍼의 크기가 너무 작으면 디스크 읽기 쓰기가 빈번해진다.
- 소트 버퍼의 크기가 너무 크면 동시 접속이 잦은 환경에서 운영체제는 메모리 부족 현상을 겪을 수 있다.
    - OS의 OOM-Killer는 메모리가 부족하면 메모리를 가장 많이 사용하는 프로세스를 강제로 종료할 것 → 그게 MySQL Server일 확률이 높다.

#### 9.2.3.2 정렬 알고리즘
레코드를 정렬할 때 레코드 전체를 소트 버퍼에 담아서 정렬할지, 정렬 기준 컬럼만 소트 버퍼에 담을지에 따라 **싱글 패스**와 **투 패스** 두 가지 정렬 모드로 나눌 수 있다.  
쿼리가 어떤 정렬 모드를 수행하는지는 다음과 같이 옵티마이저 트레이스 기능으로 확인할 수 있다.

```sql
mysql> select * from information_schema.optimizer_trace;
...(생략)
"sort_algorithm": "std::stable_sort"
"sort_mode": "<fixed_sort_key, packed_additional_fields>"
...
```

정렬 모드는 3가지로 나뉘어진다.
- `<sort_key, row_id>`: 정렬 키와 레코드의 Row ID만 가져와서 정렬한다.
- `<sort_key, additional_fields>`: 정렬 키와 레코드 전체를 가져와서 정렬한다. 레코드 칼럼은 고정 사이즈로 메모리에 저장한다.
- `<sort_key, packed_additional_fields>`: 정렬 키와 레코드 전체를 가져와서 정려한다. 레코드 칼럼은 가변 사이즈로 메모리에 저장한다.

첫 번째 방식은 투 패스 정렬방식이며, 나머지 두 방식은 싱글 패스 방식이다.

##### 9.2.3.2.1 싱글 패스 정렬방식
> 정렬에 필요하지 않은 칼럼까지 소트 버퍼에 담아서 정렬을 수행한다.

```sql
SELECT emp_no, first_name, last_name FROM employees ORDER BY first_name;
```
<img width="564" alt="image" src="https://github.com/user-attachments/assets/8283bc8b-630f-47b5-8db2-d107b1d0aa77">

위 쿼리 기준으로, 처음 `employees`테이블을 읽을 때 정렬에 필요하지 않은 `last_name` 칼럼까지 전부 읽어서 소트 버퍼에 담고 정렬을 수행한다.  
정렬 완료 후 소트버퍼 내용을 그대로 클라이언트에게 넘겨 준다.

##### 9.2.3.2.2 투 패스 정렬방식
> 정렬 대상 칼럼과 PK 값만 소트 버퍼에 담아서 정렬을 수행한 후, 정렬된 순서대로 다시 PK를 참조하여 나머지 칼럼을 가져온다.

<img width="548" alt="image" src="https://github.com/user-attachments/assets/65be993e-e359-447f-bdcc-521043a8bc07">

싱글 패스 정렬 방식이 도입되기 전부터 사용하던 방식으로, MySQL 8.0에서는 여전히 특정 조건에서는 투 패스 정렬 방식을 사용한다.

투 패스는 테이블을 두 번 읽어야 하므로 상당히 불합리하지만, 싱글 패스는 한 번만 읽어도 된다.  
하지만 싱글 패스 정렬 방식은 소트 버퍼의 공간을 많이 사용한다.

최근에는 일반적으로 싱글 패스를 많이 쓰지만 다음의 경우 투 패스 정렬방식을 사용한다.
- 레코드의 크기가 `max_length_for_sort_data` 값보다 클 때
- BLOB, TEXT 타입의 칼럼이 SELECT 대상에 포함 될 때

> [!WARNING] 정렬 쿼리 사용 시 주의점  
> SELECT 쿼리에서 꼭 필요한 칼럼만 조회하지 않고 모든 칼럼(`*`)을 조회하도록 개발할 때가 많다. 하지만 이는 정렬 버퍼를 몇 배에서 몇십 배까지 비효율적으로 사용할 가능성이 크다.  
> 이는 꼭 정렬 버퍼에만 영향을 미치는 것이 아니라 임시 테이블이 필요한 쿼리에서도 영향을 미친다.

#### 9.2.3.3 정렬 처리 방법
쿼리에 `ORDER BY` 문이 포함되면 다음의 세 가지 방법 중 하나로 처리된다. 일반적으로 아래쪽에 있는 정렬 방법으로 갈수록 처리 속도는 떨어진다.

| 정렬 처리 방법                                  | 실행 계획의 Extra 칼럼 내용       |
| ----------------------------------------------- | --------------------------------- |
| 인덱스 사용                                     | 별도 표기 없음                    |
| 조인에서 드라이빙 테이블만 정렬                 | "Using filesort"                  |
| 조인에서 조인 결과를 임시 테이블로 저장 후 정렬 | "Using temporary; Using filesort" |

먼저 옵티마이저는 인덱스를 이용해서 정렬을 할 수 있을지 여부를 체크한다. 인덱스를 사용할 수 있으면 인덱스를 사용하고, 그렇지 않으면 레코드를 정렬버퍼에 넣고 정렬을 수행한다. 이 때 MySQL 서버는 정렬 대상 레코드를 최소화하기 위해 다음 두 가지 방법 중 하나를 수행한다.
- 조인의 드라이빙 테이블만 정렬한 다음 조인을 수행
- 조인이 끝나고 결과 레코드 모두를 가져와서 정렬을 수행

##### 9.2.3.3.1 인덱스를 이용한 정렬
<img width="513" alt="image" src="https://github.com/user-attachments/assets/07f27e0c-24e7-4f87-bf50-b4cc89bed17f">

인덱스를 이용한 정렬은 이미 인덱스 자체가 정렬돼 있기 때문에 추가 작업 없이 순서대로 읽기만 하면 된다. 조인을 하더라도 Nested-Loop 방식으로 실행되기 때문에 조인으로 인해 순서가 흐트러지지 않는다.

정렬에서 인덱스를 이용하려면 다음 두 조건을 만족해야 한다.
1. `ORDER BY` 에 명시된 컬럼이 제일 먼저 읽는 테이블(조인의 경우 드라이빙 테이블)에 속해야 한다.
2. `ORDER BY` 절의 순서대로 생성된 인덱스가 있어야 한다.

##### 9.2.3.3.2 조인의 드라이빙 테이블만 정렬
일반적으로 조인이 수행되고 나면 레코드 수가 상당히 증가한다. 따라서 조인을 실행하기 전에 첫 번째 테이블의 레코드를 먼저 정렬한 다음 조인을 실행하는 것이 정렬의 차선책이다.

이 방법(드라이빙 테이블만 정렬)으로 정렬이 수행되려면 **조인에서 첫 번째로 읽히는 테이블(드라이빙 테이블)의 칼럼만으로 `ORDER BY` 절을 작성**해야 한다.
```sql
select *
from employees e, salaries s
where s.emp_no=e.emp_no
and e.emp_no between 100002 and 100010
order by e.last_name;  // 드라이빙 테이블 e
```

검색은 인덱스 레인지 스캔으로 처리할 수 있지만, `ORDER BY` 절에 명시된 칼럼은 `employees`의 PK와 전혀 연관이 없으므로, 인덱스를 이용한 정렬은 불가능하다.  
하지만 `ORDER BY` 절의 정렬 기준 칼럼이 드라이빙 테이블(`employees`)에 포함된 칼럼이므로, 옵티마이저는 드라이빙 테이블만 검색해서 정렬을 먼저 수행하고, 그 결과와 `salaries` 테이블을 조인한다.

##### 9.2.3.3.3 임시 테이블을 이용한 정렬
하나의 테이블만을 정렬하거나, 조인의 드라이빙 테이블만 정렬하여 처리할 수 있는 경우(9.2.3.3.2)에는 임시 테이블이 필요하지 않다.  
하지만 그 외 패턴의 쿼리에서는 항상 조인의 결과를 임시 테이블에 저장하고 그 결과를 다시 정렬하는 과정을 거친다.
- 이 방법은 **가장 느린 정렬 방법**이다.
<img width="406" alt="image" src="https://github.com/user-attachments/assets/5d3c8d7f-32fe-4f14-b9d2-57ff25f55fd2">

```sql
select *
from employees e, salaries s
where s.emp_no=e.emp_no
and e.emp_no between 100002 and 100010
order by s.salary;  // 바로 위 쿼리에서 ORDER BY 절만 바뀌었다.
```
`ORDER BY` 절의 정렬 기준 칼럼이 드라이빙 테이블이 아니라 드리븐 테이블(`salaries`)에 있는 칼럼이다. 정렬이 수행되기 전에 `salaries` 테이블을 읽어야 하므로 이 쿼리는 **조인된 데이터를 가지고 정렬할 수밖에 없다.**  
쿼리의 실행 계획 Extra 칼럼에 Using temporary; Using filesort라는 코멘트가 남는다.
- 이는 임시 테이블에 조인 결과를 저장하고 그 결과를 정렬했다는 의미이다.

##### 9.2.3.3.4 정렬 처리 방법의 성능 비교
일반적으로 `LIMIT`절은 서버가 처리할 작업량을 줄일 수 있다고 여겨진다. 하지만 데이터를 처리하는 방식에 따라 `LIMIT`으로 처리량이 줄 수도있고 줄지 않을 수도 있다.
- 대표적으로 `ORDER BY`나 `GROUP BY` 같은 작업은 `WHERE` 조건을 만족하는 레코드를 `LIMIT` 건수만큼만 가져와서는 처리할 수 없다.
	- 즉, `WHERE` 조건이 인덱스를 잘 활용하도록 튜닝해도 잘못된 `GROUP BY`나 `ORDER BY` 때문에 쿼리가 느려지는 경우가 자주 발생한다.

###### 9.2.3.3.4.1 스트리밍 방식
> 서버 쪽에서 레코드가 검색될 때마다 바로바로 클라이언트로 결과를 전송해주는 방식이다.  
> LIMIT 제한을 걸면 처리량을 줄이고 마지막 레코드를 가져오는 시간을 줄일 수 있다.

웹 서비스와 같은 OLTP(Online Transactional Processing) 환경에서는 쿼리의 요청-첫 응답까지의 시간이 중요한데, 스트리밍 방식으로 처리되는 쿼리는 쿼리가 얼마나 많은 레코드를 조회하느냐에 상관없이 빠른 응답 시간을 보장해 준다.

###### 9.2.3.3.4.2 버퍼링 방식
> `ORDER BY`나 `GROUP BY` 같은 처리는 `WHERE` 조건에 만족하는 모든 레코드를 가져와서 정렬하거나 그루핑해서 차례로 응답을 보내야 하므로 결과 스트리밍이 불가능하다.  
> 이와 같은 처리(스트리밍의 반대를 버퍼링 방식이라고 한다.

다시 말해, 버퍼링 방식으로 처리되는 쿼리는 먼저 결과를 모아서 MySQL 서버에서 일괄 가공해야 하므로 모든 결과를 스토리지 엔진으로부터 가져올 때까지 기다려야 한다. 그래서 LIMIT과 같은 결과 건수를 제한하는 조건은 성능 향상에 도움이 되지 않는다.
- 네트워크로 전송되는 레코드 수만 줄일 뿐, MySQL 서버가 해야 하는 작업량에는 변화가 없음

`ORDER BY`의 처리 방법 3가지 중 **인덱스를 활용한 정렬 방식**만 스트리밍 형태의 처리이며, 나머지는 모두 버퍼링된 후에 정렬된다.

> [!NOTE] 클라이언트 도구에 따른 스트리밍 처리  
> 스트리밍 처리는 어떤 클라이언트 도구나 API를 사용하느냐에 따라 방식에 차이가 있을 수 있다.  
> 대표적으로 JDBC는 MySQL 서버로부터 받는 레코드를 일단 내부 버퍼에 모두 담아두었다가 마지막 레코드가 전달되면 클라이언트의 어플리케이션에 반환한다.  
> 이러한 동작의 이유는 전체 처리(스루풋)시간이 짧고, MySQL 서버와의 통신 횟수가 적어 자원 소모를 줄일 수 있기 때문이다.

##### <span style="background:#d4b106">조인과 함께 ORDER BY + LIMIT이 사용될 경우, 정렬 처리 방법별 차이</span>(질문)
```sql
SELECT *
FROM tb_test1 t1, tb_test2 t2
WHERE t1.col1=t2.col1
ORDER BY t1.col2
LIMIT 10;
```

`tb_test`에는 100개의 레코드, `tb_test2`에는 1000개의 레코드가 있다고 가정하자.

두 테이블의 조인 결과를 1000건이라고 가정하면 `LIMIT` 10일 때 정렬 처리 방법별로 읽어야 하는 레코드 건수와 정렬을 수행해야 하는 레코드 건수는 다음과 같다.

**tb_test1이 드라이빙되는 경우**

| ------------------------ | ----------------------------- | ----------------------------------------- | ------------------------------------------- |

	- t1을 정렬하기 위해 100건 모두 읽고 정렬해야 함.
	- 이후 정렬된 t1에서 가장 작은 레코드와 t2와 조인하는데, LIMIT 10이므로 t2는 10건만 읽으면 됨

| ------------------------ | ----------------------- | ---------------------------------------- | ------------------------------------------- |
| 인덱스 사용              | t2: 10건<br>t1: 10건    | 10번                                     | 0건 (인덱스 사용. 이미 정렬됨)              |
| 드라이빙 테이블만 정렬   | t2: 1000건<br>t1: 10건  | 10번                                     | 1000건(t2의 레코드 수만큼 정렬 필요)        |
| 임시 테이블 사용 후 정렬 | t2: 1000건<br>t1: 100건 | 1000번<br>(t2의 레코드 수만큼 조인 발생) | 1000건(조인된 결과 레코드 건수를 전부 정렬) |
- 인덱스 사용
	- 인덱스를 사용하려면 ORDER BY에 명시된 컬럼이 드라이빙 테이블에 있어야 한다.
		- <span style="background:#d4b106"><u>그럼 여기는 ORDER BY t2.col2 인 쿼리로 봐야 하나?</u></span>
			- 맞는 듯
	- 인덱스는 이미 정렬됨. LIMIT 10 만족을 위해서는 t2를 10개 읽어야 함. 자연스럽게 t1도 10개가 읽힘.
- 드라이빙 테이블만 정렬
	- t2를 정렬하기 위해 1000건 모두 읽고 정렬해야 함.
	- 이후 정렬된 t2에서 가장 작은 레코드부터 하나씩 t1과 조인하는데, LIMIT 10이므로.. 이후로는 인덱스 사용 시나리오와 같음
- 임시 테이블 사용
	- t2의 모든 레코드(1000개)와 t1을 조인하여 `t2 join t1` 테이블을 구축한 후, 조인된 테이블(레코드 1000건)을 정렬해야 함

- 테이블간의 조인이 아니라 하나의 결과 row에 대해 조인조건이 일치하는 row들을 매칭시키는 연산 횟수인듯


> [!NOTE]  
> 어느 테이블이 먼저 드라이빙되어 조인되는지도 중요하지만, 어떤 정렬 방식으로 처리되는지는 더 큰 성능 차이를 만든다.  
> 가능하다면 인덱스를 사용한 정렬로 유도하고, 그렇지 못하다면 최소한 드라이빙 테이블만 정렬해도 되는 수준으로 유도하는 것도 좋은 튜닝 방법이라고 할 수 있다.


> [!NOTE]  
> 인덱스를 사용하지 못하고 별도로 Filesort 작업을 거쳐야 하는 쿼리에서 `LIMIT` 조건이 아무런 도움이 되지 못하는 것은 아니다.  
> 정렬 대상 레코드가 1,000건인 쿼리에 `LIMIT 10` 조건이 있다면 1,000건의 레코드를 모두 정렬하는 것이 아니라 상위 10건만 정렬이 채워지면 결과를 반환한다.  
> 하지만 MySQL 서버는 퀵 소트와 힙 소트를 사용하므로, 상위 10건 정렬을 위해 10+a 의 연산이 필요할 수도 있다.  
> 결론적으로, 인덱스를 사용하지 못하는 쿼리를 페이징 처리에 사용하는 경우 LIMIT으로 5~10건만 조회한다고 해도 기대만큼 아주 빨라지지는 않는다.

### 9.2.4 GROUP BY 처리
`GROUP BY`는 `ORDER BY`와 같이 스트리밍된 처리를 할 수 없게 만든다.  
`GROUP BY having ~` 절은 그룹 결과에 대한 필터링이므로 원초적으로 인덱스를 사용해서 처리될 수 없다.
- `HAVING` 절을 튜닝하려고 인덱스를 생성하거나 다른 방법을 고민하지 말자

GROUP BY 작업도 인덱스를 사용하는 경우와 그렇지 못한 경우가 있다.
- 인덱스 이용
    - 인덱스 스캔: 인덱스를 차례로 읽는 방식
    - 루스 인덱스 스캔: 인덱스를 건너뛰면서 읽는 방식
- 인덱스 이용 X
	- 임시 테이블 사용

#### 9.2.4.1 인덱스 스캔을 이용하는 GROUP BY(타이트 인덱스 스캔)
`ORDER BY`와 마찬가지로,
1. 조인의 드라이빙 테이블에 속한 칼럼만 이용해 그루핑하고
2. `GROUP BY` 칼럼으로 이미 인덱스가 있다면

그 인덱스를 차례대로 읽으면서 그루핑 작업을 수행하고 그 결과로 조인을 처리한다.  
`GROUP BY`가 인덱스를 사용하여 처리된다 하더라도 집계함수 등의 그룹값을 처리해야 해서 임시 테이블이 필요한 경우도 있다.

#### 9.2.4.2 루스 인덱스 스캔을 이용하는 Group by
> 인덱스 레코드를 건너뛰면서 필요한 부분만 읽어서 가져오는 방식
- 실행 계획 Extra 칼럼에 "Using Index for group-by" 코멘트가 표시된다.

```sql
SELECT emp_no
FROM salaries
WHERE from_date='1985-03-01'
GROUP BY emp_no;
```
`salaries` 테이블의 인덱스는 `(emp_no, from_date)`로 생성되어 있다고 하자.  
위 쿼리에서 WHERE 조건은 인덱스 레인지 스캔을 사용할 수 없지만, GROUP BY 절은 인덱스를 활용할 수 있다.

**MySQL 서버의 처리 순서**
1. `(emp_no, from_date)` 인덱스를 차례대로 스캔하면서 `emp_no`의 첫 번째 유일한 값 "10001"을 찾아낸다.
2. `(emp_no, from_date)` 인덱스에서 `emp_no`가 "10001"인 것 중에서 from_date 값이 "1985-03-01"인 레코드만 가져온다.
3. `(emp_no, from_date)` 인덱스에서 `emp_no`의 그 다음 유니크한 값을 가져온다.
4. 3번 단계에서 결과가 더 없으면 처리를 종료하고 결과가 있다면 2번 과정으로 돌아가서 반복을 수행한다.

**루스 인덱스 스캔의 특징**
- 단일 테이블에 대해 수행되는 `GROUP BY` 처리에만 사용할 수 있다.
- Prefix Index(**단일** 칼럼값의 앞쪽 일부만으로 생성된 인덱스. **복합 인덱스랑 다른개념!**)는 사용할 수 없다.
- 인덱스 레인지 스캔에서는 유니크한 값의 수가 많을수록 성능이 향상되지만, 루스 인덱스 스캔에서는 반대이다.
	- 인덱스 레인지 스캔은 유니크한 값이 많을수록 걸러낼 수 있는 레코드가 늘어난다.
	- 루스 인덱스 스캔은 유니크한 값을 순회해야 하므로 많을수록 느려진다.

루스 인덱스 스캔이 사용될 수 있을지 없을지 판단하는 것은 꽤 어렵다.  
`(col1, col2, col3)`으로 인덱스가 생성되었을 때, 이는 모두 루스 인덱스 스캔을 사용할 수 있다.
```sql
select col1, col2 from tb_test group by col1, col2;

select distinct col1, col2 from tb_test;

select col1, min(col2) from tb_test group by col1;

select col1, col2 from tb_test where col1 < const group by col1, col2;

select max(col3), min(col3), col1, col2 from tb_test where col2 > const group by col1, col2;

select col2 from tb_test where col1 < const group by col1, col2;

select col1, col2 from tb_test where col3 = const group by col1, col2;
```

다음 쿼리는 루스 인덱스 스캔을 사용할 수 없는 쿼리 패턴이다.
```sql
-- // MIN() 과 MAX() 이외의 집합 함수가 사용됨
SELECT col1, SUM(col2) FROM tb_test GROUP BY col1;

-- // GROUP BY 절에 사용된 칼럼이 인덱스 구성 칼럼의 왼쪽부터 일치하지 않음
SELECT col1, col2 FROM tb_test GROUP BY col2, col3;
-- 이런 경우는 (col1, col2, col3)으로 그룹지은 다음 어플리케이션에서 스트림으로 처리하는게 더 빠를 수도 있나?
-- 경우에 따라. 그럴 수도 있겠다.

-- // SELECT 절의 칼럼이 GROUP BY와 일치하지 않음
SELECT col1, col3 FROM tb_test GROUP BY col1, col2;
```

#### 9.2.4.3 임시 테이블을 사용하는 Group By
`GROUP BY`의 기준 칼럼이 드라이빙 테이블에 있든 드리븐 테이블에 있든 관계없이, **인덱스를 전혀 사용하지 못할 때에는 임시테이블을 만든다.**
- 내부적으로 `GROUP BY` 절의 칼럼들로 구성된 유니크 인덱스를 가진 임시 테이블을 만들어서 중복 제거와 집계 합수 연산을 수행한다.

### 9.2.5 DISTINCT 처리
`DISINTCT` 처리는 크게 두 가지로 나뉠 수 있다.
- 집계함수(`MIN()`, `MAX()`, `COUNT()`, ...)과 함께 사용되는 경우
- 그렇지 않은 경우

#### 9.2.5.1 SELECT DISTINCT...
> 단순히 `SELECT` 되는 레코드 중에 유니크한 레코드만 가져오고자 하는 쿼리.
- `GROUP BY`와 동일한 방식으로 처리된다.

```sql
select distinct emp_no from salaries;
select emp_no from salaries group by emp_no; -- 두 쿼리는 같은 작업을 수행한다.
```

> [!WARNING] DISTINCT 키워드의 사용법
> `DISTINCT` 키워드로 가장 흔하게 실수하는 것이 있다. 
> `DISTINCT`는 `SELECT` 하는 모든 대상 컬럼에 대해 유니크하게 조회하는 것이지, 특정 칼럼만 유니크하게 조회하는 것이 아니다.
> 즉, `SELECT DISTINCT(first_name), last_name FROM employees;`
> 와 같이 함수처럼 사용할 수 없다!
> 

#### 9.2.5.2 집계 함수와 함께 사용된 DISTINCT
> 집계함수가 없는 `SELECT` 쿼리에서 `DISTINCT`는 조회하는 모든 칼럼의 조합이 유니크한 것들만 가져온다.
> 반면, 집계 함수 내에서 `COUNT(DISTINCT s.salary)` 와 같이 사용되면 그 집계함수으 인자로 전달된 칼럼값이 유니크한 것들을 가져온다.
- 집계함수와 함께 사용할 때에는 임시 테이블을 사용한다. (실행계획에는 표시 X)

```sql
select count(distinct s.salary)
from employees e, salaries s
where e.emp_no = s.emp_no
and e.emp_no between 10001 and 100100;
```
- 위의 쿼리를 실행했을 때 조인한 결과에서 salary를 저장하기 위한 임시테이블을 만든다.
- 임시 테이블의 salary 칼럼은 유니크 인덱스가 생성된다.
	- 따라서 레코드 건수가 많아질 경우 쿼리가 상당히 느려진다.

> [!NOTE] 집계함수와 함께 `DISTINCT`가 사용되면 항상 임시 테이블을 생성하는가?
> 인덱스된 칼럼에 대해 `DISTINCT` 처리를 수행할 때는 인덱스를 풀 스캔하거나 레인지 스캔하면서 임시 테이블 없이 수행한다.
- 인덱스는 이미 정렬되어 있으므로 중복 제거에 활용하는 것

```sql
1. SELECT COUNT(DISTINCT emp_no) FROM employees;
2. SELECT COUNT(DISTINCT emp_no) FROM dept_emp GROUP BY dept_no;
```

1. employees의 emp_no 칼럼에 인덱스 생성 시 (정렬된) 인덱스를 읽으면서 중복 제거 수행 가능
2. 두 가지 경우가 있음
	1. `dept_no`는 PK이므로 `dept_emp`의 `emp_no` 칼럼에만 인덱스 생성
		- `GROUP BY`, `DISTINCT` 연산은 각각 인덱스를 타므로 빠르지만, 각 연산이 별도로 수행되어야 함
		- `GROUP BY`의 결과를 임시 테이블에 저장해 놓고, 거기서 다시 `DISTINCT` 연산을 수행?
	2. `(dept_no, emp_no)` 복합 인덱스 사용
		- `GROUP BY` 와 `DISTINCT` 연산을 동시에 최적화 가능
		- 커버링 인덱스 적용으로 성능 향상 → 테이블 접근 불필요

### 9.2.6 내부 임시 테이블 활용
> MySQL 엔진이 스토리지 엔진으로부터 받아온 레코드를 정렬하거나 그루핑할 때는 내부적인 임시 테이블(Internal temporary table)을 사용한다.
- 내부적인(internal)이라 표현하는 이유는 `CREATE TEMPORARY TABLE` 명령어로 만든 임시 테이블과는 다르기 때문
- 내부적인 임시 테이블은 메모리에 생성됐다가 테이블의 크기가 커지면 디스크로 옮겨짐
	- 다른 세션이나 쿼리에서는 볼 수 없고 쿼리가 완료되면 자동으로 삭제됨

#### 9.2.6.1 메모리 임시 테이블과 디스크 임시 테이블
메모리는 TempTable이라는 스토리지 엔진을 사용한다. (MySQL 8.0 이후부터)
- 최대 사용 가능한 메모리 크기는 1GB이며, 초과하는 경우 디스크로 기록한다.
- 이 때 두 가지 방식으로 저장할 수 있다.
	1. MMAP 파일로 기록 (기본값, InnoDB 테이블로 전환하는 것 보다 오버헤드가 적음)
	2. InnoDB 테이블로 기록
디스크에 저장되는 임시 테이블은 MySQL 8.0 이후부터 InnoDB 스토리지 엔진을 사용한다.****

> [!INFO] MySQL 서버가 디스크 임시 테이블을 다루는 방법
> MySQL 서버는 디스크의 임시 테이블을 생성할 때, **파일 오픈 후 즉시 파일 삭제를 실행한다.**
> 이렇게 함으로써 MySQL 서버가 종료되거나 해당 쿼리가 종료되면 임시 테이블이 즉시 사라지도록 보장할 수 있고, MySQL 서버 내부의 다른 스레드 또는 MySQL 서버 외부의 사용자가 해당 임시 테이블을 위한 파일에 변경을 가하거나 조회할 수 없게 한다.

#### 9.2.6.2 임시 테이블이 필요한 쿼리
다음과 같은 쿼리는 MySQL 엔진에서 별도의 데이터 가공이 필요하므로 내부 임시 테이블을 생성하는 대표적인 케이스이다.
- `ORDER BY`와 `GROUP BY`에 명시된 칼럼이 다른 쿼리
- `ORDER BY`와 `GROUP BY`에 명시된 칼럼이 조인의 순서상 첫 번째 테이블이 아닌 쿼리
- `DISTINCT`와 `ORDER BY`가 동시에 쿼리에 존재하는 경우 또는 `DISTINCT`가 인덱스로 처리되지 못하는 쿼리
- `UNION`이나 `UNION DISTINCT`가 사용된 쿼리(select_type이 union result인 경우)
	- UNION과 UNION DISTINCT는 같음. 합집합 + 중복제거.
- 쿼리의 실행 계획에서 select_type이 `DERIVED`인 쿼리

임시 테이블을 사용하는지 여부는 실행 계획의 Extra 칼럼에 "Using temporary" 메시지가 표시되는지 확인하면 알 수 있다.
- 단, 위 예시에서 마지막 3개 패턴은 임시 테이블을 사용함에도 "Using temporary"가 표시되지 않는다.
1~4 번째 예시는 유니크 인덱스를 가지는 내부 임시 테이블이 만들어지고, 5번째 쿼리 패턴에서 생성하는 내부 임시 테이블에는 유니크 인덱스가 없다.
- 유니크 인덱스가 있는 테이블은 그렇지 않은 쿼리보다 상당히 느리다.

#### 9.2.6.3 임시 테이블이 디스크에 생성되는 경우
내부 임시 테이블은 기본적으로 메모리에 만들어지지만, 다음의 조건을 만족하면 디스크 기반의 임시 테이블을 사용한다.
- `UNION`이나 `UNION ALL`에서 `SELECT`되는 칼럼 중, 길이가 512바이트 이상인 크기의 칼럼이 있는 경우
- `GROUP BY`나 `DISTINCT` 칼럼에서 512바이트 이상인 크기의 칼럼이 있는 경우
- 메모리 임시 테이블의 크기가 temp_table_max_ram 시스템 변수 값보다 큰 경우 (TempTable 엔진 기준)

#### 9.2.6.4 임시 테이블 관련 상태 변수
일반적으로 실행 계획에서 "Using temporary"가 표시된 것으로 임시 테이블이 사용되었다는 것을 알 수 있지만, 해당 임시 테이블이 메모리에서 처리됐는지 디스크에서 처리됐는지는 알 수 없다.

이를 확인하려면 `SHOW SESSION STATUS LIKE 'Created_tmp%';` 로 확인한다.
- Created_tmp_tables: 내부 임시 테이블의 개수를 누적하는 상태 값
- Created_tmp_disk_tables: 디스크에 내부 임시 테이블이 만들어진 개수를 누적하는 상태 값

> [!NOTE] 상태 변수 조회 시 주의점
> 누적 값이므로 테스트 쿼리 실행 전 FLUSH STATUS 명령을 통해 현재 세션의 상태 값을 초기화한 후 조회해야 한다.
